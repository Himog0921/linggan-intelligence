DR-B1-002

缺口：CaptureSubmissionV2 / RawRecord 外部结构无唯一来源
证据：
  - docs/architecture/content-workbench-v2-design-freeze.md:548-556（§6 只用自然语言列出概念字段名，无 JSON 层级、无 base64 字段名、无 target 结构、无 protocolVersion V2 取值）
  - src/ 全库 rg "CaptureSubmissionV2" = 0 结果；rg "captureSubmissionV2" = 0 结果
  - 四类入口当前各有完全不同的 V1 数据格式：
    · execution:  src/lib/services/execution-sync-service.ts:172-201（commit_raw_snapshot operation，checksumAlgorithm/checksumValue/contentLength/storageKey 散落在 operation 上，records[] 嵌套在 operation 内）
    · manual_import: src/lib/services/plugin-manual-import-service.ts:9-13（PluginManualImportRecords { notes[], comments[], authors[] }）
    · recovery: src/lib/services/plugin-local-recovery-service.ts:53-60（PluginLocalRecoveryExport { journal[], deadLetters[] }）
  - 无任何 TypeScript 类型定义 CaptureSubmissionV2 的 JSON 层级
为什么无法唯一推出：
  冻结规范 §6 写的 capturePackage 是概念性的"bytea base64 + checksum"，但没有定义：
  (a) JSON 层级——字段是平铺还是嵌套对象？capturePackage 是一个含 base64+checksum 的子对象，还是 checksumAlgorithm/checksumValue/contentLength 直接在顶层？
  (b) base64 字段名——叫 data / payload / bytes / base64Content / packagePayload？
  (c) target 的准确结构——当前 V1 用 observedTargetKey/expectedTargetKey 两个字符串；V2 的 target 是什么结构？它到 RawSnapshot.targetKey 的确定性映射规则是什么？
  (d) RawRecord[] 的来源——嵌套在 capturePackage 内？还是顶层独立字段？字段名是 records 还是 rawRecords？
  (e) protocolVersion 的 V2 取值——当前 V1 是 "3"（execution-sync-service.ts:114），V2 取值未在任何权威资料中定义
  任意选择一组 JSON key 就构成一组不同的外部协议。工单明确禁止"冻结规范只写出概念字段，不代表可以自行发明 JSON key"。
可证伪验收条件：
  给出 CaptureSubmissionV2 的完整 TypeScript 类型定义，其中每个 JSON key 能追溯到冻结规范行号或已确认 DEC；或审核方在权威资料中补充完整的外部 JSON 合同。插件端或 API 路由中有对应实现或真实 fixture。

DR-B1-005

缺口：execution 状态推进语义与并发重试参数均无来源
证据：
  - src/lib/services/raw-snapshot-ingest-service.ts:497-561（当前 execution 链路在同一 ReadCommitted 事务中同时创建 RawSnapshot/RawRecord + 推进 ExecutionJob/ExecutionTaskRuntime/TaskAttempt/monitor + 创建 OutboxEvent）

  - src/lib/services/raw-snapshot-ingest-service.ts:618（isolationLevel: ReadCommitted，非 SERIALIZABLE）
  - src/ 全库 rg "SERIALIZABLE" = 0 结果（现有最高为 RepeatableRead：author-archive-audit-service.ts:784）
  - docs/architecture/v2/01-decisions.md:37（DEC-B1-016 只确认"使用 SERIALIZABLE 事务并重试序列化/唯一冲突，重复包返回既有快照"，未给出最大重试次数、可重试错误准确范围、重试耗尽返回语义）
  - 冻结规范 §7 B1（L562-563）只说 EvidenceIngress 事务内 INSERT 四类对象 + 幂等，未定义 EvidenceIngress 与执行控制平面的分离机制
为什么无法唯一推出：
  (a) execution 控制平面：当前代码在 Evidence 事务内同时推进执行状态（释放租约、ExecutionJob→raw_committed、TaskAttempt→success、Runtime→completed）。DEC-B1-004 要求"Capture、Evidence 状态职责分离"，但硬切后 EvidenceIngress 只负责 Evidence 四对象，由谁在何时以什么事务边界推进执行状态、是否仍发出 raw_snapshot.committed OutboxEvent、EvidenceIngress 成功但执行状态推进失败时如何补偿——这些在冻结规范和决策文档中均无来源。工单 4.4 明确要求"不得把现有 V1 commitRawSnapshot 的行为直接复制进 EvidenceIngress，除非冻结合同明确授权。"
  (b) 并发重试：DEC-B1-016 确认了 SERIALIZABLE + 重试方向，但工单 4.6 明确要求找到最大重试次数、可重试错误准确范围、重试耗尽后返回语义，且"找不到时不得自行选择'重试三次'等经验值。"这些参数在任何权威资料中都没有定义。
可证伪验收条件：
  审核方明确给出：(1) EvidenceIngress 与执行控制平面的事务边界、状态推进责任方、OutboxEvent 处置规则的完整合同；(2) SERIALIZABLE 重试参数（最大次数、可重试错误准确范围、重试耗尽返回语义）。
