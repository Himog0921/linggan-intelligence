# 最终目标

在一次受控维护窗口中：

1. 冻结所有媒体相关写入；
2. 将每一条历史 MediaAsset 完整纳入 MediaLibrary；
3. 将可证明的业务关系导入新关系模型；
4. 将不能证明关系的历史媒体完整保留为 unassigned / needs_review，而不是遗漏或猜造；
5. 所有页面、API、AI、Archive、Cover Library、Publication、导出、CLI 只读取新的统一 MediaLibrary ReadModel；
6. 恢复运营后，旧 MediaAsset 冻结为只读审计档案；
7. 不删除旧表、旧文件或审计资料；删除另开后续项目。

“完整迁移”分两层，必须同时满足：

- 媒体事实完整：每条旧 MediaAsset 恰好有一条新架构导入记录，含物理状态、来源和血缘；
- 关系语义诚实：只有有证据的 ContentMediaUsage、TopicMediaSelection、PublicationMedia 才能建立。没有证据的关系明确标为未分配或冲突，绝不猜。

目标：维护窗口之后不再有任何新旧不一致。

HC-1 先修代码机制，不直接修改历史事实。

## 3. HC-2：先扩展模型，再导入

新增仅扩展的 Prisma migration，建立不可变历史导入账本，例如 MediaLegacyImport。

每条旧 MediaAsset 必须恰好一条 MediaLegacyImport，至少有：

- workspaceId
- legacyMediaAssetId（唯一）
- mediaItemId / mediaBlobId
- importBatchId
- importState
- relationshipState
- evidenceKind / evidenceFingerprint
- reason
- 受控 legacySnapshot
- importedAt / verifiedAt

最低状态：

importState：
available、missing_file、failed_legacy、invalid_metadata、review_required

relationshipState：
proven、unassigned、conflicted、not_applicable

同时实现最终统一 ReadModel，明确只返回：

deliverable
missing
unassigned_historical
failed

旧 URL 不能再是页面、导出或 AI 的权威媒体输入。

严禁 prisma migrate dev、prisma migrate reset、prisma db push。

## 4. HC-3：正式维护窗口与冻结基线

仅当 HC-0、HC-1、HC-2 已合并部署、且预检与演练通过后执行。

顺序：

1. 启用维护锁；
2. 排空可完成任务；不能完成的保留为可恢复状态并记录；
3. 确认所有写入口静止；
4. 执行并验证可恢复数据库备份；
5. 固定 cutoff：时间、Git SHA、migration 列表、相关表计数；
6. 在 gongyong 正式数据重跑完整只读基线、M3、M4、M5 审计；
7. 保存不可覆盖的 JSON 审计产物。

若存在活动写入、备份不可读、媒体基线失败、磁盘容量不足，停止并保持维护，不执行导入。

## 5. HC-4：一次性全量历史导入

这是正式写入阶段，必须专用 runner，不能复用旧 backfill 脚本。

Runner 必须具备：

- 固定 cutoff；
- importBatchId；
- dry-run；
- 明确 --apply；
- 分页 cursor；
- checkpoint；
- 幂等；
- 可中断、可续跑；
- checksum / 文件可读性核验；
- 每批完整审计输出；
- 不泄露 URL、凭据或文件路径。

对每条旧 MediaAsset：

- 可读且校验通过：导入为 available；
- 文件缺失：导入为 missing_file，并保持 Replica=missing；
- 旧失败、非法元数据、冲突：导入为对应失败/复核状态；
- 没有业务关系证据：仍导入稳定 Item/Origin 身份，但 relationshipState=unassigned。

硬验收：

MediaAsset 总数 = MediaLegacyImport 总数

且每条 legacyMediaAssetId 恰好一次。
