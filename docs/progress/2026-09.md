## 2026-09-03 · DESIGN-012 第六轮：修表格互动列的垂直错位

- **根因**：`.ev-engagement` 基础样式带 `margin-top:8px`——那是研读视图里它位于原声引文下方所需的间距。表格布局覆盖了 display、gap、字号，唯独没覆盖这条 margin，于是整块被下推 8px，行内其余字段（标题 / 作者 / 材料 / 发布时间 / 最近观察）都由 `.ev-work-row` 的 `align-items:center` 垂直居中，只有互动数字偏低。表格布局下归零。
- **教训**：把一个为某个布局写的组件搬到另一个布局时，要覆盖的不只是显式改动的属性，还有它在原布局里携带的**位置性**样式（margin / padding / align-self）。这类偏移不会报错，只会看起来"差一点"。
- **同时向 Mog 说明了材料色块的配色语义**（未改 UI，仅解释）：绿=已取得、黄褐=部分取得、橙红=失败或受限、蓝=处理中、浅灰=尚未取得或未知、白底描边=本作品不适用且不计入分母。
- **检查器里的材料比值一并删除**：Mog 指出概览的「材料 2 / 5」还在。理由与表格同源——色块画出每一维的状态、其下的标签命名它们，比值是同一件事的第三次编码。上一轮把它留在检查器的理由（「那里是逐条评估的地方」）不成立：逐条评估时看的是哪一维缺，不是缺几个。研读视图卡片的比值暂留，Mog 未提。

## 2026-09-03 · DESIGN-012 第五轮：表格材料列去数字、并入状态列

Mog 就上一轮提出的「材料 2/4 的价值跟意义是什么」拍板方案 A。

- **表格删除比值数字，只留进度条，并把状态列并入材料列**：7 列回到 6 列，材料列由 112px 加宽到 `minmax(176px,.8fr)`。依据是三个元素（数字 / 进度条 / 状态词）在编码同一事实（`2/4`↔`当前未知`、`3/5`↔`部分取得`），而进度条是其中**行与行之间形状会变化**的那一个——扫读时最容易发现「这行和别行不一样」。数字的精确性在扫读面上没有用武之地：判断「这条有没有正文」不需要知道是 2/4 还是 3/5。

- **验证**：`cargo test --workspace` 28 个目标全通过；`node --check` 通过；治理检查单独运行（不接管道）通过；`:3100` 实测 6 列布局，`1/4`、`3/5`、`2/5` 三条的进度条形状在扫读中可辨。

## 2026-09-03 · RUNTIME-SCRIPTS-001 部署脚本纳入仓库

- **为什么改**：RUNTIME-CONSOLIDATION-001 换掉了部署模型，但脚本只住在 `~/Library/.../runtime-launchers/`，仓库里只有描述它们的 runbook。后果是这台机器重装或换机器时，这套东西得照着手册手工重建——手册说了怎么做，却没有可执行的东西。
- **落地**：新增 `scripts/runtime/`，三个文件。`sync.sh` 承担同步、迁移闸门与锁内构建；`launch.sh` 是三个服务的统一入口，参数为二进制名；`install.sh` 建运行目录、写 launchd 配置并启动，幂等。全新机器的完整步骤缩为 clone → 填 `.env` → 起库 → 迁移 → `install.sh`。

## 2026-09-02 · TOPIC-WORKSPACE-REAL-001 最终审查发现的 canonical identity 并发收口

- 审查发现：Topic 表将 `canonical_key` 与 `idempotency_key` 都定义为全局唯一身份，但原事务 advisory lock 键同时包含 domain 且仅覆盖 canonical；两个不同 Domain 并发提交同一 canonical key，或两个不同 Topic 并发复用同一幂等键时，会持有不同锁，后到事务可能被数据库 unique constraint 打断并被 API 误报为 unavailable。这会把可解释的业务拒绝变成基础设施故障。
- 根本修复：锁的作用域改为两类唯一 identity，且以稳定字典序取得，避免并发请求共享两把锁时相互等待。任意 Domain 的同 key 写入先串行；第一个写入形成 Topic，第二个读取到既有 identity 后由显式 domain 不变量拒绝。任何同幂等键复用则返回明确 idempotency conflict；两类业务冲突都不再交给 raw constraint。隔离 PostgreSQL 两个并发回归分别要求恰一笔成功、一笔 `Topic domain cannot change` 或 `IdempotencyConflict`，最终行数均为一。
- 严格审查结论：按 `origin/main...current integration HEAD` 复查完整 Topic 包的结构、模块归属、数据库不变量、边界复用、前端状态、文件增长和可读性。领域/持久化在新的 687 行模块内，loopback API 与页面控制器各自独立，没有把 Topic 逻辑散入 shared Shell 或 Work Resource read；`WorkspaceVersionRefs` 消除了 receipt 写入的长位置参数列表和 `too_many_arguments` 豁免。两种唯一身份竞争在同一审查内收口后，6 项 Topic PostgreSQL proof、full workspace、语法/格式/diff 与治理检查全部通过。结论为 PASS；既有 API 16 项 dead-code warning 未由本卡制造，也未被伪装为已解决。
