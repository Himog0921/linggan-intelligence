## 2026-09-07 · 外部领域读自己的数据源（Issue #130 第二步）

- **为什么必须紧跟上一步**：领域选择器上线后，切到外部领域，列表仍在读证据侧——一个能切换却不改变任何东西的控件比没有更糟，它会让人以为自己正在看考研自习的内容。
- **两条查询路径，不共享接口**：新增 `GET /api/local/cross-industry/samples?domain=…`，读 `cross_industry_sample`。规格的接口红线是「不得为跨行业给证据库接口增加任何参数或字段」——本领域继续走 `/api/local/work-resources`，一个字段都没动。隔离因此不依赖任何人记得在某处加条件。
- **当前领域由服务端随页面下发**（`body[data-corpus-domain*]`），前端据此选路径。不让前端自己解析地址：地址里的 `domain` 可能是无效值，回落判定服务端已经做过一次，前端再判一次就会出现两处规则，早晚不一致。
- **外部领域不带证据侧的检索条件过去**：本页的检索词与筛选描述的是证据侧字段，对样本侧无意义。带一个不会生效的条件过去，比不带更容易让人以为筛过了。
- **空态分开说**：外部领域的空是「这个领域还没采集过内容」，不是「当前查询没有匹配」。用证据侧那句会把「一条都还没有」说成「你筛掉了」，两者的下一步动作完全不同。
- **读本领域会被明确拒绝而非返回空列表**：`home_domain_reads_evidence`。本领域的材料在证据侧，它在跨行业表里「没有样本」不是关于数据的事实，而是问错了地方；空列表会被读成「还没采过」。
- **缺失一律 UNKNOWN，不折成 0**：跨行业样本大量来自列表面，互动数缺失是常态。把它显示成 0 会把「没看到」说成「确实是零」——本项目刚在评论数上踩过这个坑。真实观察到的 0 仍是 KNOWN，两者分得开。
- **来路字段永远存在**：`provenance` 里的关键词、排序、来源观察目标即使为空也显式给出，不省略。省略会让调用方无法区分「这条没有采样口径」和「这个接口不返回口径」。
- **验证**：`cargo fmt --check`、`cargo check --workspace --tests`、33 项 crate 单元测试（新增 3 项：未知计数不折零、空标题非空串、来路字段恒在）、`node --check` 通过。
- **未做**：跨行业采集入口与落库分流仍未实现，所以外部领域现在恒为空态——这正是当前的诚实状态。散点图、徽章、随手记出口未做。

## 2026-09-07 · 领域选择在地址上留得住

- **现象**：领域选择器上线后，切到外部领域，随后任何一次列表交互都会把它悄悄换回本领域。
- **根因**：`syncUrl()` 用 `explicitParams()` 从零重建地址，而那个函数只收本页面自己的查询条件（检索词、排序、窗口、lane、媒体类型）。`domain` 不在其中，于是每一次同步都把它抹掉——领域变成「选一次、下一次交互即失效」。
- **实现**：`syncUrl` 原样带回地址里的 `domain`。它由整个语料模块承载而非本页面所有，页面无权在重建地址时把它丢掉。
- **切换语义**：选择器表单显式指定 `action="/corpus/evidence"`，提交时只带 `domain`。换领域是换观察对象，上一个领域下的检索词、筛选与选中的作品都不该跟过来——它们说的是另一批材料。
- **一处误判（如实记录）**：验证时用 `textContent` 读面包屑，读出了 `<noscript>` 里的按钮标签，我一度当成「标签被渲染成了文本」。浏览器并不渲染 noscript 内容，截图里面包屑是干净的。**这是验证方法的问题，不是缺陷**——今天第二次栽在同类事情上（前一次是把客户端渲染的空壳 HTML 当成「功能没生效」）。
- **验证**：`cargo check -p linggan-api` 通过。真实浏览器复验在部署后进行。

## 2026-09-07 · 跨行业观察地基：观察领域、采集链路复用与数据库层隔离（Issue #130 第一步）

- **定位**：系统此前只观察 ADHD 一个领域。本步把「领域」提升为一等对象——语料页的每个子页都在某一个**当前观察领域**下工作，换领域即换观察对象，页面结构不变。领域选择器住在面包屑层，管整个语料页（Mog 2026-09-07 定，理由：跨行业采集用的就是插件同一套能力，数据结构一致）。
- **采集链路完全复用**（Mog 2026-09-07 澄清后的方案）。外部领域的博主与关键词就是普通的观察目标，走同一套 目标 → 准入 → 工单 → 租约 → 任务 → Package 的路，插件不需要知道领域的存在。**领域只在落库那一刻决定材料去哪张表。** 这条路径是三选一的结果：只靠前端按领域过滤最省事，但那与「一个接口加参数」同构——漏写一次即破且无声，将来任何读证据的地方（选题评估、Topic 分析、AI 判断、导出）忘了加条件，外部领域内容就会被当作本领域证据使用；为跨行业重建一套采集链路则代价过高。复用链路 + 落库分流两者兼得。
- **migration `0041_observation_domain`**：新增 `observation_domain`（领域配置，字段极简）、`cross_industry_sample`（跨行业样本，带 `target_ref` 指回带回它的观察目标）、`cross_industry_note`（随手记，带全文检索索引）、`cross_industry_keyword` 与 `cross_industry_keyword_round`（关键词生命周期与每轮新增率）；`collection_observation_target` 增列 `domain_ref`。初始三条领域：ADHD（本领域）、考研自习、自闭症干预。
- **既有目标全部回填为本领域**：它们是在只有 ADHD 的时候建立的，标成别的会改写历史。列保持可空 + 读取时回落——「没标过」与「标了本领域」是两件事，只是当前处置相同。
- **隔离由数据库自己守住**：`CHECK (is_own_domain = false)` 与复合外键 `(domain_ref, is_own_domain)` 互相咬合。`is_own_domain` 字段本身不承担隔离，只服务切换器展示与复合键组成。跨行业样本不进 `linggan_material_content`——那是证据侧的作品身份表，共用一张表等于把参照物混进证据。
- **采样口径要么整套要么没有**：博主监控带回的样本没有排序口径可言，给它编一个会让复核基于不存在的事实；关键词来源则必须带全套（含**实际取得数**——采不满是已知会发生的情况，只记目标数会让基数错）。半套由 CHECK 拒绝。
- **隔离实测（干净空探针库，未碰生产库）**：① 写入 ADHD 领域的跨行业样本 → 外键拒绝；② 显式把 `is_own_domain` 改成 `true` 绕过 → CHECK 拒绝；③ 博主来源无口径 → 成功；④ 关键词来源整套口径 → 成功；⑤ 半套口径 → CHECK 拒绝。探针库已清理。
- **读模型与选择器**：新增 `observation_domain.rs`（领域读取 + 当前领域解析）。地址里没写、写了非 uuid、写了不存在或已停用的领域，一律回落到本领域——读不出来的参数不该让页面空着，更不该让人以为自己正在看某个外部行业。本领域的 `sample_count` 恒为 `None`：它的材料在证据侧，填 0 会把「不适用」说成「一条都没有」。少于两个领域时选择器整个不渲染。

## 2026-09-06 · 深度建档四处系统性修复：重复发租、僵尸工单、配额口径、在途提示

一次走查暴露出四个互相咬合的问题，都不是补丁能了结的，逐条按根因改。

- **重新发租不再重跑已完成的步骤**。任务在模型上属于租约（主键 `(lease_ref, sequence_no)`），租约一释放，它名下的 pending 任务就永久失效——派发查询硬性要求租约存活。所以重新发租只能重造一套，这是模型选择而非遗漏。但「重造」不等于「重做」：工单冻结的作品清单不变，已完成的步骤是不可变历史，两者相减才是这次该干的活。新增 `remaining_steps_for_work_order`，按「作品 + 能力」去重。**实测代价**：一张三篇作品的工单发了 9 次租约、生成 108 个步骤去完成本该 12 步的活，同一篇正文被真实重复抓取 9 次，每次都实扣配额；全目标 264 个任务行里 176 个（66.7%）是冗余。去重键不用任务 id，因为它每次生成都是新随机值——`linggan_runtime_task` 上那条 `UNIQUE(task_spec_hash)` 也正因如此从来拦不住重复（哈希输入里就含着这个随机 id）。剩余为空时不再发空租约，改为直接结单并返回 `WorkOrderAlreadySatisfied`；`undo_failed_queue_claim` 的 `WHERE queue_state='leased'` 守卫保证这个结单不会被调用方回滚掉。
- **释放租约与交还工单收敛为一个函数**。抽出 `requeue_work_orders_after_release`，过期路径与插件顶替路径共用。此前 `teardown_installation` 只释放租约、不改工单队列态，工单就永久停在 `leased` 且名下无活租约——共享 claim 只找 `queued`，没有任何工位能再接手，也没有巡检回收它，还继续占着该来源的批量并发额度。**实测后果**：工单 `f7942504` 因此卡死，而渐进建档的候选查询只排除「排队中」和「有活租约」两种状态、看不见这第三种，于是它冻结的作品被重新选进新工单——同两篇作品被冻结了两次。新函数带 `NOT EXISTS 活租约` 守卫，重复调用安全。
- **每日配额改为按笔记篇数计，不再按记录条数**（Mog 2026-09-06 决定）。一篇笔记当天无论被读过几次、读回多少评论与回复，都只占一格。旧口径被评论吞掉：实测 accepted 记录里回复占 54%、评论占 26%，正文详情只有 4%，于是「今天最多两百篇」实际变成「今天最多两三篇」。配额守的是平台访问，而读评论发生在那篇笔记已经打开的页面上，不是又一次访问。只统计需要打开详情页的采集（`content_detail`/`comments`/`replies`）；发现面一次列表访问带回几十篇，按篇计费等于用一次访问的风险扣掉几十格。笔记身份取 `sourceObject.type='content'`——评论记录的 sourceObject 指向所属笔记而非评论自身，按 externalId 去重天然得到「碰过几篇笔记」。**实测口径变化**：同一天同一工位，175 条记录 → 61 篇笔记。函数与字段的文档注释一并同步，不留旧口径描述。
- **「建档进行中」的提示不再永不可达**。`advance_progressive_archive` 的候选查询同时排除「已有详情的」和「已在别的批次在途的」，此前两种情况都报 `no_missing_accepted_work`，于是正在跑的批次被说成「没有可继续的内容」，人看到的是「点了没反应」；`detail_batch_in_flight` 这个理由在全仓库没有任何一处会产生。现按是否真有在途批次分别返回。
- **回归守门**：`daily_quota_counts_notes_not_records`（钉住去重、包类型收窄、笔记身份三条）、`remaining_steps_skip_what_this_work_order_already_finished`（钉住四 lane 展开顺序与按「作品+能力」过滤后的剩余）。
- **验证**：`cargo fmt --check`、`cargo check --workspace --tests`、27 项 crate 单元测试通过。
- **未做**：未部署、未复验真实链路；既有 2 个僵尸工单与历史冗余任务行不做追溯清理，新逻辑只保证不再新增。配额口径变更会让在用工位的当日已用数立刻下降（175→61 量级），这是口径变化不是配额放宽。

## 2026-09-06 · 规则版本检查错误拦停 agent 发起的深度建档

- **现象**：南瓜哒哒的渐进建档在 person 发起的目录步骤完成后再无进展。工单已准入、租约已签发、任务 `pending`、插件心跳正常、工位接活开着、日额度 79/200、执行链接齐全。页面上的「继续完善」按钮点击后也毫无反应。**从服务端复现一次 claim，回执是 `rule_revision_changed`。**

- **排查记录（供后来者）**：本次定位前有四次误判 —— 插件领活线一次性唤醒、工单缺容量绑定、账号资格 TTL 过期、插件本地无凭据（后者实为读错字段名 `credential`/`installationCredential`）。共同原因是**被拒绝的 claim 不写任何审计表**，只能从外部现象反推；直到从服务端直接复现一次 claim、拿到 `decision` 字段，根因才在一步内确定。建议为 ControlBlocked 类拒绝补一行可审计记录。

## 2026-09-06 · 账号资格有效期与工位存活判定解耦

- **现象**：南瓜哒哒的深度建档在 2026-09-06 停摆八小时。工单已准入、租约已签发、22 个任务 `pending`、插件 `0.8.40` 心跳每分钟正常、工位接活开着、日额度 79/200、三篇作品各有带 `xsec_token` 的合格执行链接 —— 九项控制检查里八项通过，唯独账号资格 `expires_at` 早已越过。容量选择因此跳过每一个候选工单，共享 claim 一律回「无可派工作」。**这条拒绝不写 `collection_work_order_lease_task_dispatch_failure`，所以外部看不到任何失败痕迹**，队列看起来是空的。

- **实现**：拆出 `ACCOUNT_ELIGIBILITY_TTL_MINUTES = 360`，仅用于资格观察的有效期；`CONTROL_FRESHNESS_MINUTES` 保持 20，继续只回答「这个浏览器还在不在」。平台登录本身以天计，六小时对它仍是保守断言。
- **边界（这拓宽的是耐心，不是信任）**：本改动不产生、不续期、不推断任何资格观察，只延长可以据此行动的窗口。派发一旦返回账号状态，插件仍会强制一次新的被动读取；真实失败仍然终止执行。`observed_at` 记录的依然是真实观察时刻。
- **回归守门**：新增 `account_eligibility_outlives_installation_liveness`，断言两个常量不得再被合并，并把各自的取值钉死，附上本次事故的成因说明。
- **验证**：`cargo fmt --check`、`cargo check --workspace --tests`、24 项 crate 单元测试通过。
- **未做**：既有的过期观察不会被追溯延长 —— 恢复仍需要一次新的资格观察（打开一张小红书页面即可）。未部署、未做真实链路复验，留待合并后单独记录。

## 2026-09-06 · Browser Producer 0.8.40：零评论不再显示为未知，手动批量带回评论

- **为什么改（一）**：真实笔记「救命，原来ADHD真的没法感知自己的"努力"」的 SSR `interactInfo` 是 `likedCount:"84"`、`collectedCount:"55"`、`commentCount:""` —— **XHS 用空字符串表示零，不是 `"0"`**。`firstPresentValue` 把空串与「字段缺席」同等对待，于是真实的零被降级成 `UNKNOWN`，投影里再也说不出「这篇没有评论」。同一个包里另一处 `pageCommentCount: 0` 是对的，证明零确实被读到过，只是在互动数这条路径上丢了。

## 2026-09-02 · TOPIC-WORKSPACE-REAL-001 最终审查发现的 canonical identity 并发收口

- 审查发现：Topic 表将 `canonical_key` 与 `idempotency_key` 都定义为全局唯一身份，但原事务 advisory lock 键同时包含 domain 且仅覆盖 canonical；两个不同 Domain 并发提交同一 canonical key，或两个不同 Topic 并发复用同一幂等键时，会持有不同锁，后到事务可能被数据库 unique constraint 打断并被 API 误报为 unavailable。这会把可解释的业务拒绝变成基础设施故障。
- 根本修复：锁的作用域改为两类唯一 identity，且以稳定字典序取得，避免并发请求共享两把锁时相互等待。任意 Domain 的同 key 写入先串行；第一个写入形成 Topic，第二个读取到既有 identity 后由显式 domain 不变量拒绝。任何同幂等键复用则返回明确 idempotency conflict；两类业务冲突都不再交给 raw constraint。隔离 PostgreSQL 两个并发回归分别要求恰一笔成功、一笔 `Topic domain cannot change` 或 `IdempotencyConflict`，最终行数均为一。
- 严格审查结论：按 `origin/main...current integration HEAD` 复查完整 Topic 包的结构、模块归属、数据库不变量、边界复用、前端状态、文件增长和可读性。领域/持久化在新的 687 行模块内，loopback API 与页面控制器各自独立，没有把 Topic 逻辑散入 shared Shell 或 Work Resource read；`WorkspaceVersionRefs` 消除了 receipt 写入的长位置参数列表和 `too_many_arguments` 豁免。两种唯一身份竞争在同一审查内收口后，6 项 Topic PostgreSQL proof、full workspace、语法/格式/diff 与治理检查全部通过。结论为 PASS；既有 API 16 项 dead-code warning 未由本卡制造，也未被伪装为已解决。
