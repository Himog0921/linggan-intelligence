## 2026-08-20 · DISC-001 Gate 6 后台运行与安全运维架构草案

- 新增 [`../architecture/runtime-operations-architecture.md`](../architecture/runtime-operations-architecture.md)，明确 API、worker、业务计划、Durable Work、外部副作用与业务结果分责；`HTTP 202/200`、`job succeeded`、日志或 UI 状态都不能单独证明业务闭环。
- 业务模块拥有工作输入、幂等结果、重试资格和后续工作；通用 runner 仅提供 claim/lease/epoch fence、有限重试、接管、stop、dispatch 和可观测性。没有建立万能 Workflow、任意 JSON job 或巨型 dispatcher。

- 调度器只把已批准 schedule revision 变成到期 occurrence/need，再走正常准入；人工决定会结束当前运行，确认后以新授权启动新 work/invocation，不占用长期 lease。
- 明确 transient、resource、lost-authority、invalid-input、deterministic-bug、external-unknown、policy-denied 等不同失败后果；所有重试有次数/总时长/停止，旧 epoch 迟到提交由数据库围栏拒绝。
- 隐私处置采用“立即阻断读取/输出 + 各消费者异步传播回执”；传播失败时 Case 不得显示完成。业务历史、运行台账、安全审计、日志/trace 和指标五类记录分开。
- 部署仍是 API/worker 两个进程、一个 PostgreSQL 主库；对象存储仅在首个真实 Artifact 需要时引入，不提前增加 Redis、Kafka、Temporal、Camunda、微服务或 Kubernetes。

## 2026-08-20 · DISC-001 Gate 4 Attempt、恢复与 Evidence 接入关系审计

- 审计范围：固定 V2 服务端 Execution Job/Task Attempt/lease/capture identity，插件 task poller、Collection Run、strict outbox、capture journal、batch checkpoint、terminal packager，以及服务端 Evidence Ingress、执行控制 finalizer 和 B2 durable worker；全程只读，不访问真实平台。
- 已证明：同一任务可有多次服务端 Attempt，每次开始产生新 Attempt/capture/lease 身份；普通续租不换 Attempt；严格 outbox 冻结生产时身份；同 capture/hash 的重传是 replay；不同 hash 是显式 conflict；Package、Record、Artifact、receipt 与 durable work 在同一事务接入；Evidence 已提交而执行控制待完成会明确返回可重试状态。
- P0 来源缺口一：插件在 `pluginRunId` 相同时可以保留旧本地 Collection Run，同时接纳新的服务端 Attempt。旧 Attempt 的未接纳记录/checkpoint 因而可能被新 capture 身份继续打包；固定 V2 没有证明 Attempt↔Collection Run 一一对应。
- P0 来源缺口二：checkpoint 恢复会把仍能重新发现的旧目标排在前面、移除本轮未发现的旧目标并追加新目标；它能节省部分重复访问，但没有冻结观察成员、Coverage 或可比范围。checkpoint 写入失败也可能不阻断采集。
- P0 来源缺口三：Evidence authority 检查先于 Evidence 写事务，Ingress 没有使用下游已有的 transaction fence 模式；现有源码/测试未覆盖验证后、提交前 authority 刚好变化的交错，标记 `SOURCE_INCOMPLETE`。
- P0 来源缺口四：下游会隔离预期的单条 rejected/quarantined 结果，但全部 Record 仍在一个派生事务中；未预期异常会回滚整包派生并触发 package 级重试/死信，不能宣称任意坏 Record 都不影响其他 Record。
- 辅助发现：本地 capture journal 同 `entryId` 重写不会比较 payload hash，且 journal 写失败不一定阻断 outbox；它是恢复辅助，不是最终幂等、冲突或 Accepted Evidence 证明。outbox 的批量传输也不是 Capture Package 分块。
- 当时提交确认的最小关系：Work Order 1:N Attempt；Attempt 使用独立 Capture Identity，第一版最多一个终态 Package；网络 replay 与执行 retry 分开；checkpoint 仅为运行状态；新 Attempt 不得改挂旧 Attempt 的未接纳材料；Package 接入全包原子、接纳后按 Record/Object 隔离；authority 与 Evidence 写入共享 transaction fence 或等价原子边界。
- 后续确认：上述关系已于 2026-08-20 获用户确认，并写入共同语言和领域不变量；本次确认仍未修改业务代码、数据库、migration、插件或历史来源。
- 验证结果：相关插件定向运行发现 107 项，其中 105 项通过；`workbench-xhs-batch-run-helper` 与 `xhs-batch-record-delta` 两个文件因历史快照缺少 `dexie` 在加载阶段失败，不是业务断言失败，也未被伪装为通过。固定 workbench 快照没有 `node_modules`，本轮没有安装依赖或冒充重跑数据库集成测试。`git diff --check`、项目治理、641 项固定来源校验和与 bootstrap、Rust workspace 测试全部通过；Rust 现有 2 项单元测试通过、0 失败。
- 提交状态：未提交、未推送。
