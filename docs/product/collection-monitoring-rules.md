# 采集监控产品规则（博主监控 / 关键词监控）

> 状态: 草案
> 最后核对: 2026-08-26
> 适用范围: 观察目标的生命周期、深度建档、巡检频率、爆款追踪、插件推送协同，覆盖 `COLLECTION-001`（Issue #66）的前两条交付线
> 事实来源: Mog 于 2026-08-26 的结构化设计讨论逐题确认、三路只读调研的实测证据（见 §8）、`capture-control-contract`（Draft PR #17）、`domain-invariants.md`、小红书字段实测文档
> 冲突时以谁为准: 用户最新确认、AGENTS.md、`domain-invariants.md`、采集控制合同；本文件不授权任何真实采集执行

**本文件不是实现授权。** 它定义规则，不代表调度器、工位、观察目标实体或授权链已经存在——§7 列明了全部前置。

---

## 1. 这些规则要解决的问题

用户的原始描述：

> 我如果要监控一个博主或一个关键词，希望在日常巡查之前，先采集到库内 200 条以内的作品，然后进入日常巡查节奏。我的动作是：添加观察目标 → 在观察目标页面正常展示博主信息或关键词 → 在这个页面可以点击是否监控、是否深度建档、是否暂停或启动。

规则要回答的是：这些动作各自意味着什么、什么时候允许发生、系统凭什么说"这条爆了"。

## 2. 观察目标的生命周期

### 2.1 两个来源，一个入口状态

```
[插件推送]  或  [手动添加]
        ↓
    已入库 · 待决          只有身份信息：ID / 昵称 / 头像 / 粉丝数 / 简介
        ↓                  不消耗任何采集配额
   ┌────┴────┬──────────┐
   ↓         ↓          ↓
深度建档   启用监控     忽略
        （必须先建档）
```

**「已入库 · 待决」是必须的状态。** 插件推送发生在用户浏览时，不应立刻消耗平台访问。这一态正是 `INV-36` 里「申请不等于授权」的落点。

### 2.2 页面上只有两个操作

| 操作 | 形态 | 说明 |
|---|---|---|
| **深度建档** | 一次性动作 | 不是开关。跑完就结束，不会让新作品自动深采 |
| **启用 / 暂停** | 开关 | 对应监控的启停 |

**「是否监控」与「暂停/启动」是同一个开关的两种说法，不做成两个控件。**

### 2.3 强依赖：深度建档完成才能启用监控

理由：轻巡检需要基线。没有基线，第一次巡检会把看到的全部当成新内容；爆款判定也没有分布可比。

## 3. 深度建档

### 3.1 内容与触发

- 内容 = **200 条作品列表 + 详情 + 评论**
- **手动触发**，不自动开始
- 200 是**上限不是目标**：博主只有 30 条就是 30 条，不补、不重试、不算失败

### 3.2 未达 200 的原因必须区分记录

| 原因 | 语义 |
|---|---|
| 作品数量本就少于 200 | 正常完成 |
| 触发平台风控提前终止 | 部分完成，可恢复 |
| 配额 / 时间用尽 | 部分完成，可续采 |

采集控制合同 §3.1 的原文支持这一条：**"最大配额、时间预算和风险预算的差额不是现实对象。"** 未达上限的差额不得被表达为失败数量、零数据或完成百分比。

### 3.3 「完成」的判定

阻塞启用监控的只有**列表阶段**，详情与评论允许部分失败：

| 阶段 | 是否阻塞启用监控 |
|---|---|
| 作品列表 | **必须完整** |
| 详情 | 允许部分失败 |
| 评论 | 允许部分失败 |

**但这一条的前提取决于 `DECISION-01`**（见 §6）：若爆款判定采用多维互动分，基线数据只有详情页才有，届时"完成"必须卡到详情阶段。

理由：不这样拆的话会出现死结——某几条作品的详情因内容失效永远采不到 → 建档永远不算完成 → 监控永远启不动。

## 4. 巡检频率

### 4.1 频率由新内容出现的速率决定，不由价值决定

**价值只决定去留（提议退役，人裁决），不决定频率。**

这一条是刻意与旧系统分道的。旧系统用「评估分」调频率，存在一个闭合的正反馈：降频 → 采到的少 → 产出分更低 → 再降频，而恢复需要"连续 2 周评分回升"——降频后本就更难攒够产出。新设计中频率不依赖产出分，这个循环不成立。

### 4.2 初始频率从建档数据当场算出

深度建档采的 200 条**每条都带绝对发布时间**（详情页 `note.time`）。建档完成的那一刻即可算出发布间隔中位数：

```
发布间隔中位数 ÷ 2 = 初始巡检间隔
```

除以 2 的理由：要不漏掉一个事件，采样得比事件本身快一倍。用**中位数**而非平均数，因为一次爆发式连发会把平均数拉垮。

**冷启动问题因此不存在**——这是「建档必须先完成」这条规则带来的红利。

### 4.3 24 小时是兜底值，不是默认值

仅在发布时间大面积缺失、算不出中位数时使用。

### 4.4 上下限是硬约束

- **下限**（最快）：保护平台、防风控
- **上限**（最慢）：即使月更也要定期看一眼，**否则他复活了你不知道**

具体数值见 `DECISION-02`。

### 4.5 关键词沿用同一套

调研确认：在旧系统里博主监控与关键词监控**在数据层和判定层本来就是同一套**，只在采集入口和初始化阶段分叉。此前认为"关键词被套上博主模型"的判断是错的。

关键词的差异只有两处：没有深度建档概念；判定基线是"该关键词命中池的分布"而非"某个博主的分布"。

## 5. 爆款追踪

### 5.1 采样：起量后 1 / 3 / 7 / 12 / 24 小时，共 5 次

这五个数字是**时间点**，不是间隔，总跨度 24 小时。

采用对数间隔的理由：传播曲线前陡后平，前 3 小时的信息密度远高于第 20–24 小时之间。均匀采样把同样成本花在信息量差一个数量级的地方。

对比旧系统的固定 1 小时 × 72 次：采集次数降到 **7%**，曲线形状信息几乎不丢。

### 5.2 24 小时后退出，交回常规巡检

不做延长。长尾爆款的后半程只有粗粒度数据，这是刻意的取舍——否则一篇作品会永久占住并发额度。

### 5.3 追踪对象是单篇作品的详情，不是重采博主

成本差一个量级。插件侧已有 `detail_probe` 策略协议可直接对应。

### 5.4 判定必须用增速，不能用增量

**这是本文件与旧系统分歧最大的一条，也是必须新写的一条。**

旧系统用相邻观察的**绝对增量**做判定，不除以时间间隔。而我们的采样是**变间隔的**：

| 采样点 | 距上一点 | 该点 delta 覆盖时长 |
|---|---|---|
| 第 1h | 1h | 1 小时增量 |
| 第 3h | 2h | 2 小时增量 |
| 第 24h | 12h | **12 小时增量** |

沿用绝对增量会导致**越靠后的采样点越容易被判为"更爆"**——纯粹因为它覆盖的时间更长。

**规则：判定量 = 加权互动分差值 ÷ 实际时间间隔。**

### 5.5 判定基线的四条硬要求

旧系统的 P95 实现有六个缺陷（§8.3），以下四条是新设计必须做到的：

1. **样本必须排除爆款追踪自身产生的观察。** 否则密集采样的高 delta 会成批灌回样本池，抬高基线形成自我抑制——旧系统正是如此。
2. **样本窗口按时间取最近 N 条，不得按 ID 字典序截断。** 旧系统 `take: 400` 配 `platformContentId asc` 排序，导致基线只由 ID 靠前的作品贡献。
3. **不得只保留正 delta。** 旧系统丢弃负增长与持平，使基线单向抬升。
4. **表层与详情的互动分不得混入同一分布。** 见 §5.6。

### 5.6 表层与详情的量纲必须分开

实测证明两级数据能力不同：

| 数据源 | 赞 | 藏 | 评 | 转 | 发布时间 |
|---|---|---|---|---|---|
| **博主主页列表** | ✅ | ❌ | ❌ | ❌ | **❌** |
| **搜索页列表** | ✅ | ✅ | ✅ | ✅ | ✅（相对文本） |
| 详情页 | ✅ | ✅ | ✅ | ✅ | ✅（绝对） |

若采用加权公式 `likes + collects×1.5 + comments×2 + shares×2`：

- 博主线表层的加权分实际 **= likes**，权重最高的两项恒为 0
- 详情探针能拿到全部四项

**两者混入同一分布在数学上不成立。** 表层判定与详情判定必须各自持有分布，或统一降维到共同可得的指标。具体取哪种见 `DECISION-01`。

### 5.7 博主线与关键词线不共用阈值

- **关键词线**：四维复合判定可用，甚至可做"收藏/点赞比"这类结构性信号
- **博主线**：只有 Δ点赞可用，**必须明确不承诺收藏与评论**

后果要写在界面上：博主线不展示收藏/评论列，避免看到一串 0 误判为"没人收藏"。

**收藏型爆款（实测样本：赞 1059 / 藏 1315）在博主线的表层巡检中不可见**，这是当前平台能力决定的，不是实现缺陷。要覆盖它只能提高详情探针配额。

### 5.8 起量时间必须标记为「观测到的」

24 小时巡检意味着一篇 6 小时就爆的作品，我们 24 小时后才发现。记录的起量时间**必然晚于真实起量**。

这个失真无法消除，但必须在数据上标记——否则将来拿这批数据做预测算法时，会把"我们晚发现了 8 小时"误读成"这篇作品前 8 小时没涨"。

### 5.9 采样点缺失时跳过，不顺延

某次采样因产能不足未执行：**跳过，继续等下一个时间点**，缺失点显式记录为「未采集」。

理由：时间轴对齐比点数完整重要。顺延会让第 12 小时的点变成第 14 小时，歪掉的时间轴会污染整个数据集；缺一个点只是少一个样本。

### 5.10 并发满时不追，不做抢占

5 点采样把每篇成本降到旧方案的 7%，同等产能能追的篇数多 14 倍，并发打满几乎不会发生。因此不实现抢占逻辑：**名额满了就不追，记录为「因产能未追踪」**。

### 5.11 关键词的单篇追踪规则

1. 判定基线用**该关键词下的分布**，不是博主的
2. 增长只用**我们自己的两次观测差**，绝不用 `publishedAt` 推算——老帖刚被搜到时按发布时间算增速会得出荒谬数字
3. **首次命中就已高互动的作品：只记录，不追踪。** 我们不知道它是刚爆还是三年前爆的，没有增长曲线可追
4. 只追「我们看着它涨起来」的
5. 并发上限比博主更严（候选池大得多，每次搜索几十上百条）

## 6. 待 Mog 决定（`DECISION_REQUIRED`）

以下四项**不得静默选择默认值**。前两项是采集控制合同 §11 的硬要求。

### DECISION-01 · 爆款判定用单维还是多维

- **A. 单维（仅点赞）**：表层与详情量纲统一，博主线和关键词线可比；代价是丢掉收藏/评论信号，收藏型爆款只能靠详情探针发现
- **B. 多维（加权四指标）**：判定更准；代价是博主线表层不可用，"建档完成"必须卡到详情阶段（§3.3 随之改变）
- **C. 分线处理**：博主线单维、关键词线多维，两条线各自持有分布、不互相比较

**这一项决定 §3.3 的完成标准。**

### DECISION-02 · 巡检频率的上下限具体值

- 下限（最快）：多久一次会触发平台风控？
- 上限（最慢）：一个月更博主，最长多久必须看一眼？

### DECISION-03 · 工位与产能

采集控制合同 §11 原文要求 Mog 定：**工位和账号资格、并发、频率、页数、时长、字节、每日预算**。

Mog 已确认「后续多个插件必然要引入工位概念与管理」。产能分配规则（§5.10 依赖它）**阻塞于工位对象的建立**，建议独立立项。

### DECISION-04 · 首批 known set / quota / 探针样本范围

采集控制合同 §11 的第二项硬要求。

## 7. 前置与阻塞

本文件的规则**没有一条能在当前代码上直接运行**。前置如下：

| 前置 | 现状 |
|---|---|
| 采集控制合同（PR #17） | **Draft，未合并**，正文写明 "must not be merged or treated as real execution authorization" |
| 观察目标实体 | 不存在——无表、无类型、无 API |
| 授权链（申请→授权→准入→工单） | 申请、授权、准入**全缺**；工单表存在但生产代码零 INSERT |
| 调度器 | 不存在，worker 是 3 行 stub。**当前不存在"派发"动作**，任务由插件自己 POST 创建 |
| 工位与产能 | 概念不存在（`DECISION-03`） |
| `capture_attempt.work_order_id` UNIQUE | 巡检需要同一 Work 多次 Attempt，**需要迁移** |

### 7.1 「点按钮即采集」必须改造

当前设计把四段责任链压成一次点击，违反 `INV-36`（"任何前一步都不能被报告为后一步成功"）、`INV-37`、`INV-38`。

改造方案（**不改变用户体验**）：

| 用户操作 | 实际产生 |
|---|---|
| 点「深度建档」 | **Acquisition Request + 目标状态=已设立**，不是 Work Order |
| Mog 批准一次长期授权 | 一行可撤回、有期限的记录，覆盖**一类**目标 |
| 服务端派发前 | 跑一次 Admission（用户不可见），能返回复用 / 合并 / 延后 / 拒绝 |

按钮仍然只点一次，四段责任都留痕，不需要每次采集都问一遍。

## 8. 调研证据摘要

### 8.1 必须修的红线

**`collects` / `shares` 缺失时静默变成 `0`**，只有 `comments` 有 `publicCommentCountKnown` 这样的可判别标记。

这违反"未知不等于 0"的核心不变量，症状是**监控从不报警**——最难被发现的失败形态。修法现成：照抄 `publicCommentCountKnown` 的写法。

### 8.2 身份去重必须先建唯一索引

旧系统 `MonitorConfig` **没有任何唯一索引**，手工创建完全无去重检查，同一博主可建任意多个监控、各自持有独立基线。失败模式是**静默产生平行的重复监控**，不是报错。

插件推送必然遇到重复推送，**唯一索引必须在推送功能之前建立**。

`Author` 表的双唯一索引 `(workspaceId, authorEntityId)` + `(workspaceId, platform, platformAuthorId)` 是做对了的，可直接继承这个思路。

### 8.3 旧系统爆款判定的六个缺陷（不可继承的理由）

1. `surgeScore` 是死字段，实际用加权互动分的相邻差值
2. 绝对增量，零时间归一化
3. P95 不排除爆款自身，且密采观察会灌回样本池
4. 只保留正 delta，基线单向抬升
5. `take: 400` 按 contentId 字典序截断，不是取最近
6. 冷启动无兜底，少于 4 条正 delta 直接放弃判定

### 8.4 可继承的

| 机制 | 说明 |
|---|---|
| **删除监控不删数据** | 软删配置，作品数据原样保留——符合"Observation 只追加" |
| 淘汰建议三种处置 | eliminate / whitelist / ignore（24 周冷却） |
| 容量限流 + 排队 | 单监控 3 / 工作区 20 |
| 插件的两级判定协议 | `author_baseline` / `author_patrol` / `keyword_patrol` / `detail_probe` + `scanLimit` / `detailProbeLimit` / `surfaceOnly`，带测试，**不要重新发明** |
| 表层记录标记为 seed 级证据 | 明确"表层数据不能当真值" |

### 8.5 插件推送的通道已就绪

`author_profile` 包类型服务端已认（`PACKAGE_KINDS`），三段式投递 + 持久化 outbox + 幂等重试已跑通。博主身份字段齐全：ID / 昵称 / 头像 / 粉丝数 / 简介。

**只差一个轻量入口**——现在触发这条通道必须走一次全量采集，而「待决观察目标」只需要身份字段，应跳过原始载荷。

## 9. 产出交给谁

Mog 于 2026-08-26 确认：**爆款情报的出口是首页 + 飞书通知。** 具体进首页的规则与 UI 留到下一阶段首页规划时展开。

一条需要在那时一并考虑的取舍：**飞书通知会把爆款判定的时效性要求推高**。若一篇作品在第 1 小时就判定为爆款并推送，这个判定必须足够准，否则会被误报淹没。这将反过来影响阈值选择——宁可漏报还是宁可误报。

## 10. 未证明边界

- 本文件全部规则**未在真实数据上验证过**。频率公式、判定阈值、采样点选择都需要真实运行数据校准，第一版的具体数值一定是错的——重要的是它们可调且每次调整留记录。
- 平台字段能力来自 2026-07-01 的实测文档与当前解析代码。**平台随时可能改变返回字段**，§5.6 的表格需要定期复验。
- 关键词与博主"在数据层是同一套"的结论来自旧系统实现，**不等于新项目必须如此**。
- 爆款采样数据用于后期预测算法的价值单独立项，**当下不为此预留任何字段**——预留是最容易变成技术债的做法。
