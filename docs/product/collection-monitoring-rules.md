## 0. 2026-09-05 当前观察与调度合同

本节优先于下文中关于“先建档才能巡查”“用建档完整度决定是否观察”“动态频率”的历史叙述；这些旧设计不再是当前规则。

### 0.1 五个业务对象，一条执行链

```text
观察目标 Target + 生效规则 Rule
          ↓
调度器 Scheduler（到期时只创建 Work Order）
          ↓
统一 Work Order 池（即时 / 定时 / 批量）
          ↓
合格工位主动认领 + 原子 Lease
          ↓
Attempt → immutable CapturePackage → SubmissionReceipt → 材料投影
```

- **Target** 只回答“观察谁”；**Rule** 只回答“多久一次”；**Scheduler** 只把到期规则变成 Work Order；**Station** 只在自己合格时认领；**Result** 只记录实际观察到什么。
- 所有需要浏览器执行的来源——人工观察、定时观察、关键词、深度建档、缺口补采——都走 `AcquisitionRequest → AdmissionDecision → WorkOrder → Lease → RuntimeTask → Attempt → CapturePackage → SubmissionReceipt`。任何模块不得直接向某一工位塞任务。
- `deep_archive` 是批量 lane，不是自动观察的前置、暂停条件或新的目标生命周期。它可以独立排队并在浏览器执行后逐步产生目录/详情材料。

### 0.2 建档完整度影响解释，不阻断观察

`UNKNOWN`、`PARTIAL`、风险终止或尚未建档都可以形成真实观察结果；它们只限制“能否声称覆盖完整/变化完整”，绝不阻止已经保存且启用的规则继续产生未来 Work Order。失败、部分接纳或未知覆盖也不得把规则静默关闭。

因此，以下状态没有产品意义，数据库必须拒绝或迁移修复：

```text
target.lifecycle = monitoring
target.monitoring_enabled = true
active automatic rule = none
```

保存/暂停/恢复规则时，immutable rule revision、target 的 active pointer、`monitoring_enabled`、lifecycle、`monitor_schedule_anchor_at` 与 `monitor_next_run_at` 同一事务更新。页面只能读该耐久计划点，不能用“上次派出 + 某个旧间隔”自行推算。

### 0.3 简单、确定的定时规则

首版规则只接受一个固定全天间隔：6 小时、12 小时、24 小时、2 天或 7 天。启用时记录 `anchor_at`；调度器只查询 `automatic_enabled && next_run_at <= now` 的有效规则，在写入 Work Order 的同一事务把下次计划从先前计划点推进。漏过多个周期时只补一张 Work Order，并累计 missed count，不回填 N 张历史任务；人工观察不改未来计划点。

每个创作者巡查 Work Order 固定为 `creator_patrol`：作者主页资格核验加最近 30 条作品观察。规则 UI 只配置“是否自动观察 + 间隔”，不暴露日历、工作日/周末、窗口、fallback 或动态频率。

### 0.4 多工位的统一排程

队列按**执行紧迫程度**而非来源模块分三条技术 lane：

| lane | 包含 | 初始软并发政策 |
|---|---|---|
| immediate | 用户等待的立即复采/人工观察 | 最多 3 个工位，空闲时优先 |
| scheduled | 到期的创作者或关键词规则 | 可使用全部其余空闲工位 |
| batch | 深度建档、缺口补采、研究批次 | 最多 3 个工位；其中深度建档初期可另限 1 |

这不是静态工位分组。工位每次 claim 前都要过：任务到期、工位接活/新鲜度/最低版本/能力、账号绑定与资格、额度、风险/节流、授权 scope、目标冲突。合格候选按 lane 的权重与虚拟完成量公平选择，并用 `FOR UPDATE SKIP LOCKED` 原子抢占；一个工位初期最多执行一个有效浏览器任务。OCR、ASR、媒体下载和分析是后续独立 worker，不占浏览器 claim。

## 1. 这些规则要解决的问题

用户最新确认：

> 观察目标是我持续观察的创作者，以及围绕这个创作者持续生长的作品档案。「建立档案」代表先扫描该创作者主页当前可见的前 200 篇作品链接，建立去重目录，然后逐步补齐详情、评论与已授权的数据化处理。巡查发现的新作品与数据变化继续回流同一档案。

规则要回答的是：这些动作各自意味着什么、什么时候允许发生、系统凭什么说"这条爆了"。

## 2. 观察目标的生命周期

### 2.1 两个来源，一个入口状态

```
[插件推送]  或  [手动添加]
        ↓
    已入库 · 待决          只有身份信息：ID / 昵称 / 头像 / 粉丝数 / 简介
        ↓                  不消耗任何采集配额
   ┌────┴────┬──────────┐
   ↓         ↓          ↓
深度建档   设置观察规则  忽略
        （两者可独立排队）
```

**「已入库 · 待决」是必须的状态。** 插件推送发生在用户浏览时，不应立刻消耗平台访问。这一态正是 `INV-36` 里「申请不等于授权」的落点。

### 2.2 页面操作随档案状态变化

| 操作 | 形态 | 说明 |
|---|---|---|
| **建立档案** | 初始动作 | 发起 200 篇上限的主页目录建立，并写入版本化渐进补齐意图 |
| **查看进度** | 在途动作 | 只打开真实进度，不重复提交同一范围 |
| **继续完善** | 恢复动作 | 对已知缺详情作品以小批次继续补齐，已有 Work 与在途范围必须去重 |
| **管理巡查** | 规则入口 | 打开版本化规则弹窗；保存后才能声称已启用、暂停或恢复 |

**「是否监控」与「暂停/启动」是同一个开关的两种说法，不做成两个控件。**

### 2.3 建档和巡查互不阻断

巡查唯一的前置是一个可解析的目标身份与一条有效、启用的规则；不需要目录、详情、评论、OCR、ASR 或任何“baseline ready”布尔结论。建档结果仍决定目录去重、历史分析和覆盖声明，但不能成为持续观察的许可证。

## 3. 深度建档

### 3.1 内容与触发

- 第一阶段 = **主页当前可见的前 200 篇作品链接上限**，按稳定平台 Work ID 去重
- 第二阶段 = 对已知缺详情作品小批次补齐详情，单篇最多带回 30 条评论；媒体、OCR、ASR 仍受原授权与处理能力约束
- **手动触发**，不自动开始
- 200 是**上限不是目标**：博主只有 30 条就是 30 条，不补、不重试、不算失败

### 3.2 未达 200 的原因必须区分记录

| 原因 | 语义 |
|---|---|
| 作品数量本就少于 200 | 正常完成 |
| 触发平台风控提前终止 | 部分完成，可恢复 |
| 配额 / 时间用尽 | 部分完成，可续采 |

采集控制合同 §3.1 的原文支持这一条：**"最大配额、时间预算和风险预算的差额不是现实对象。"** 未达上限的差额不得被表达为失败数量、零数据或完成百分比。

### 3.3 「完成」必须分层表达

没有建档阶段会阻塞启用监控；列表、详情与评论的状态只约束各自的完整性表述：

| 阶段 | 对自动观察的影响 |
|---|---|
| 作品目录 | 记录当前有界扫描是到达可见末端、上限，还是因风险/时间/配额部分停止；不阻塞 |
| 详情 | 允许部分失败；不阻塞 |
| 评论 | 允许部分失败；不阻塞 |

「Work Order 完成」不等于「档案完整」。页面分别披露已发现作品、已取详情、当前可分析和具体缺口，不合成总完整度百分比。

理由：不这样拆的话会出现死结——某几条作品的详情因内容失效永远采不到 → 建档永远不算完整 → 观察却永远启不动。

## 4. 巡查频率

### 4.1 频率由新内容出现的速率决定，不由价值决定

**价值只决定去留（提议退役，人裁决），不决定频率。**

这一条是刻意与旧系统分道的。旧系统用「评估分」调频率，存在一个闭合的正反馈：降频 → 采到的少 → 产出分更低 → 再降频，而恢复需要"连续 2 周评分回升"——降频后本就更难攒够产出。新设计中频率不依赖产出分，这个循环不成立。

### 4.2 首版由人选明确固定间隔

规则只保存一个人的明确选择（6 小时至 7 天的闭集选项），从启用时刻锚定。历史发布时间可用于后续分析或提出建议，但首版不自动改写规则、不创建动态 cadence，也不把缺失时间转换成“兜底授权”。

### 4.3 24 小时是首版默认选择

新建规则默认 24 小时，人与系统都能明确说明它来自默认值，而不是伪称由创作者历史计算。

### 4.4 上下限是硬约束

- **下限**（最快）：保护平台、防风控
- **上限**（最慢）：即使月更也要定期看一眼，**否则他复活了你不知道**

具体数值见 `DECISION-03`（下限 6 小时 / 上限 7 天）。

### 4.5 关键词共享调度原则，不共享创作者档案界面

调研确认：在旧系统里博主监控与关键词监控**在数据层和判定层本来就是同一套**，只在采集入口和初始化阶段分叉。此前认为"关键词被套上博主模型"的判断是错的。

关键词没有创作者身份、作品档案、详情进度或创作者生命周期语义。首层表格与对象工作区必须按类型分开，仅共享平台、分组、巡查规则和时间边界。

## 5. 爆款追踪

### 5.1 采样：起量后 1 / 3 / 7 / 12 / 24 小时，共 5 次

这五个数字是**时间点**，不是间隔，总跨度 24 小时。

采用对数间隔的理由：传播曲线前陡后平，前 3 小时的信息密度远高于第 20–24 小时之间。均匀采样把同样成本花在信息量差一个数量级的地方。

对比旧系统的固定 1 小时 × 72 次：采集次数降到 **7%**，曲线形状信息几乎不丢。

### 5.2 24 小时后退出，交回常规巡查

不做延长。长尾爆款的后半程只有粗粒度数据，这是刻意的取舍——否则一篇作品会永久占住并发额度。

### 5.3 追踪对象是单篇作品的详情，不是重采博主

成本差一个量级。插件侧已有 `detail_probe` 策略协议可直接对应。

### 5.4 判定必须用增速，不能用增量

**这是本文件与旧系统分歧最大的一条，也是必须新写的一条。**

旧系统用相邻观察的**绝对增量**做判定，不除以时间间隔。而我们的采样是**变间隔的**：

| 采样点 | 距上一点 | 该点 delta 覆盖时长 |
|---|---|---|
| 第 1h | 1h | 1 小时增量 |
| 第 3h | 2h | 2 小时增量 |
| 第 24h | 12h | **12 小时增量** |

沿用绝对增量会导致**越靠后的采样点越容易被判为"更爆"**——纯粹因为它覆盖的时间更长。

**规则：判定量 = 加权互动分差值 ÷ 实际时间间隔。**

### 5.5 判定基线的四条硬要求

旧系统的 P95 实现有六个缺陷（§8.3），以下四条是新设计必须做到的：

1. **样本必须排除爆款追踪自身产生的观察。** 否则密集采样的高 delta 会成批灌回样本池，抬高基线形成自我抑制——旧系统正是如此。
2. **样本窗口按时间取最近 N 条，不得按 ID 字典序截断。** 旧系统 `take: 400` 配 `platformContentId asc` 排序，导致基线只由 ID 靠前的作品贡献。
3. **不得只保留正 delta。** 旧系统丢弃负增长与持平，使基线单向抬升。
4. **表层与详情的互动分不得混入同一分布。** 见 §5.6。

### 5.6 表层与详情的量纲必须分开

实测证明两级数据能力不同：

| 数据源 | 赞 | 藏 | 评 | 转 | 发布时间 |
|---|---|---|---|---|---|
| **博主主页列表** | ✅ | ❌ | ❌ | ❌ | **❌** |
| **搜索页列表** | ✅ | ✅ | ✅ | ✅ | ✅（相对文本） |
| 详情页 | ✅ | ✅ | ✅ | ✅ | ✅（绝对） |

若采用加权公式 `likes + collects×1.5 + comments×2 + shares×2`：

- 博主线表层的加权分实际 **= likes**，权重最高的两项恒为 0
- 详情探针能拿到全部四项

**两者混入同一分布在数学上不成立。** `DECISION-01` 选择了统一降维到共同可得的指标（点赞），因此这个分裂问题不再存在——代价是收藏与评论信号在表层判定中完全不参与。

### 5.7 博主线与关键词线不共用阈值

- **关键词线**：四维复合判定可用，甚至可做"收藏/点赞比"这类结构性信号
- **博主线**：只有 Δ点赞可用，**必须明确不承诺收藏与评论**（`DECISION-01` 之后，关键词线也统一只用点赞，此处差异仅剩"分布来源不同"）

后果要写在界面上：博主线不展示收藏/评论列，避免看到一串 0 误判为"没人收藏"。

**收藏型爆款（实测样本：赞 1059 / 藏 1315）在博主线的表层巡查中不可见**，这是当前平台能力决定的，不是实现缺陷。要覆盖它只能提高详情探针配额。

### 5.8 起量时间必须标记为「观测到的」

24 小时巡查意味着一篇 6 小时就爆的作品，我们 24 小时后才发现。记录的起量时间**必然晚于真实起量**。

这个失真无法消除，但必须在数据上标记——否则将来拿这批数据做预测算法时，会把"我们晚发现了 8 小时"误读成"这篇作品前 8 小时没涨"。

### 5.9 采样点缺失时跳过，不顺延

某次采样因产能不足未执行：**跳过，继续等下一个时间点**，缺失点显式记录为「未采集」。

理由：时间轴对齐比点数完整重要。顺延会让第 12 小时的点变成第 14 小时，歪掉的时间轴会污染整个数据集；缺一个点只是少一个样本。

### 5.10 并发满时不追，不做抢占

5 点采样把每篇成本降到旧方案的 7%，同等产能能追的篇数多 14 倍，并发打满几乎不会发生。因此不实现抢占逻辑：**名额满了就不追，记录为「因产能未追踪」**。

### 5.11 关键词的单篇追踪规则

1. 判定基线用**该关键词下的分布**，不是博主的
2. 增长只用**我们自己的两次观测差**，绝不用 `publishedAt` 推算——老帖刚被搜到时按发布时间算增速会得出荒谬数字
3. **首次命中就已高互动的作品：只记录，不追踪。** 我们不知道它是刚爆还是三年前爆的，没有增长曲线可追
4. 只追「我们看着它涨起来」的
5. 并发上限比博主更严（候选池大得多，每次搜索几十上百条）

## 6. Mog 已决（2026-08-26）

四项原 `DECISION_REQUIRED` 已全部拍板。

### DECISION-01 · 爆款判定用单维 ✅ 已定

**采用单维：只用点赞。**

连带效果：

- 表层与详情的量纲统一，博主线与关键词线可比（§5.6 的分布分裂问题消失）
- §3.3「完成只卡列表阶段」的结论**成立并保留**——点赞在博主主页列表就能拿到
- 代价明确接受：**收藏型爆款在表层判定中不可见**，只能靠详情探针发现。实测样本赞 1059 / 藏 1315 那类内容，博主线不会主动报出来

### DECISION-02 · 建档「完成」的判定 ✅ 已定

Mog 原话：**作品链接都要拿到，但允许少量的数据缺失。**

据此细化：

| 项 | 要求 |
|---|---|
| **作品链接（`platformContentId` + URL）** | **必须完整**——这是身份，缺了就无法去重、无法追踪、无法回指 |
| 点赞数 | 必须有（爆款判定基线的唯一输入，见 DECISION-01） |
| 标题、封面、作者名 | 允许缺失 |
| 详情、评论 | 允许部分失败 |

判定式：**列表阶段每一条都必须拿到链接与点赞；其余字段缺失不阻塞。**

缺失必须记为 unknown 而非 0（见 §8.1 红线）。

### DECISION-03 · 巡查频率上下限 ✅ 已定（采用建议初值）

| | 值 | 理由 |
|---|---|---|
| **下限（最快）** | 6 小时 | 保守值，沿用旧系统默认巡查间隔——它在真实环境跑了数月未触发风控 |
| **上限（最慢）** | 7 天 | 月更博主也能在一周内发现"他复活了" |

**这两个数第一版一定不准，重要的是可调且每次调整留记录。** 需要真实运行数据校准。

### DECISION-04 · 工位与产能 ✅ 已定

**独立立项**，不进本规则的实施范围。

Mog 已确认后续多个插件必然要引入工位概念与管理。产能分配（§5.10 依赖它）在工位对象建立前保持阻塞。

### 评论采集的层级（Mog 于 2026-08-27 确认）

| 项 | 规则 |
|---|---|
| 一级评论 | 采，插件硬上限 30 条（能力注册表 `cap=30`） |
| **楼中楼（二级回复）** | **采，但「展开更多」操作最多点 2 次** |

展开次数是上限不是目标：点满 2 次仍未见底时，如实记为「回复未取尽」，**不得表述为「该评论没有更多回复」**——这是同一条「未知不等于零」的红线。

不设展开上限会让单条热门评论的回复流吃掉整次任务的时间预算，而回复的边际价值随深度快速下降。

**与插件侧的语义对齐（Issue #78）**：插件的单篇深采用 `0` 表示「公开自然结束」——不设上限、一直展开到平台没有更多。因此 **2 次这个限制必须由 Linggan 侧作为明确目标值下发**，不能让插件走默认值。楼中楼走**深采通道**，不占标准详情的 30 条窗口，两者在插件里已是独立能力。

### 媒体保留策略（Mog 于 2026-08-27 确认）

| 媒体类型 | 保留 |
|---|---|
| 图片 | **长期保存** |
| 视频 | **转录成功后保留 180 天** |
| 抽帧关键帧 | **按图片规则长期保存**（见下） |

四条执行细则，缺一条这个策略就无法执行：

**① 180 天从「转录成功之日」起算，不是采集之日。**

转录失败的视频**还没提取到任何价值**。按采集日倒计时会出现「转录一直失败 → 180 天后原片被删 → 这个视频彻底白采」。

因此：**转录未成功的视频不进入保留倒计时。** 它要么最终转录成功（此时开始计时），要么被明确判定为放弃（此时才可删）。

**② 删的是字节，不是记录。**

媒体字节是 Artifact 不是 Observation，字节可以删，**记录必须留**。清理后该条媒体记录标记为「**字节已按保留策略清理**」，而不是消失。

否则半年后看到一条转录文本却找不到来源，第一反应是「数据丢了」，然后去排查一个不存在的故障。**「主动清理」与「本来就没有」必须能分辨**——这是「未知不等于零」的同一条红线。

**③ 抽帧关键帧按图片规则长期保存。**

转录只保住了**声音**，画面信息全丢。而 ADHD 领域的视频里画面常是关键——教具怎么摆、表格长什么样、孩子的行为演示。

既然抽帧已进首批，让抽帧产物长期留存，则 180 天后原片清理时仍保有两种主要信息：

```
转录文本（说了什么） + 关键帧图片（画面是什么）
```

代价极小——几张图与一个视频的体积差两个数量级。

**④ 图片的「长期」需要磁盘水位告警兜底。**

「长期保存」不等于无限，**Mac mini 的磁盘会满**。在这个部署形态下满盘不只是「存不下新图」：数据库、日志、转录临时文件全在同一块盘上，**满盘会让整个系统停摆**，与转录卡死是同一类事故。

因此需要磁盘水位告警（建议 80%），而不是等它满。真到满盘那天再定清理策略，就是在事故里做决定。

### 外部 Agent 的读取口径（Mog 于 2026-08-27 确认）

**外部 Agent 通过后续的 CLI 读取系统情报内容，不直接访问数据库。**

这一条回应合同 §11 的「哪些用户可见页面或外部 Agent 可读何种材料」。CLI 是一个可审计、可限流、可逐步放开的窄口，也满足合同那条「控制层 ACK 不能替代用途、脱敏或访问授权」。

**遗留待决（CLI 设计时处理）**：Agent 能读到哪一层——

| 层 | 例子 |
|---|---|
| 情报结论 | 「这个话题在升温」 |
| 观察与证据 | 支撑该结论的具体笔记与指标 |
| 原文 | 笔记正文、评论原文 |
| 媒体 | 图片字节、视频、转录全文 |

Mog 说的是「读取系统的**情报内容**」，指向前两层。但 Agent 验证一个结论时往往需要看原文，就会触及第三层。**该边界留到 CLI 设计时定**，届时可调研内容工作台 `cw` CLI 的既有口径。

### 派生处理：进首批

**OCR、转录、抽帧、embedding 全部进首批范围。**

这一条把合同 §11 的「派生是否进首批」从未决转为已定。

Mog 于 2026-08-27 明确：**这些都是采集，只是服务不同需求，不需要为每一层单独做风险论证。** 此前本节写过「派生会让传播面成倍扩大」——那是多租户/公有云的风险模型，套用错了：本项目单机部署、单人使用，派生产物与原始媒体在同一台主机的同一个库里，访问者是同一个人，传播面并未扩大。该论述已删除。

唯一真正独立的问题是「**外部 Agent 能读何种材料**」，它在合同 §11 里单列，不属于派生的决策范围。

### 单工位每日上限

**200 篇笔记 / 天。评论不设独立上限。**

（Mog 于 2026-08-27 修订：原定的「500 评论/天」取消。评论是笔记的附属产物，笔记到顶时评论自然停止，第二个闸门只会带来两套计数与两处口径漂移的风险。）

计数单位是**实际入库的笔记条数**，不是任务数——一次建档可能入库 200 条笔记却只算一个任务，按任务数计会算错。

### 转录必须做并发限制

**内容工作台在这里吃过亏——本地会卡死。** 转录是本地重负载任务，不设并发上限会拖垮整台机器，进而让所有采集一起停摆。

这条不是优化项，是**可用性前提**：一次卡死影响的不只是转录，是整个主机上的全部任务。具体上限取自内容工作台的实际配置与它当时的修复经过（见 §6.3）。

## 6.3 内容工作台方案调研结论（2026-08-27）

Mog 确认调度器策略、媒体存储与部署形态沿用内容工作台。调研其实际实现后，结论分三类：**必须重新设计的、必须改掉的、可直接继承的**。继承的是设计与参数，**不迁移任何旧代码**。

### 必须重新设计：每日配额的计数单位

**旧项目做不到按产物条数计。** 它只有一个 `dailyTaskCount`，一个任务算 1，不区分产出类型——一次建档可能入库 200 条笔记，旧计数只记 1。

新设计：**按实际入库的笔记条数计，上限 200 / 天**，评论不设独立闸门（2026-08-27 修订）。

计数单位是**产物条数**而非任务数——这正是旧项目缺的能力。

另外两条来自旧项目的教训：

- 配额的**权威实现只能有一处**。旧项目有两份 200（一份管派单硬编码、一份管页面显示读插件上报值），判据还不同，会出现「页面显示已达上限但仍在派单」。展示层必须读同一个函数。
- 限额**必须可配置**。旧项目的 `dailyLimitForPlatform()` 收了 platform 参数却硬返回常量，是半成品。

配额维度**不沿用**旧项目的按账号计。此处曾写「按平台账号计，不按工位」，与本文 §单工位每日上限（Mog 于 2026-08-27 确认「200 篇笔记 / 天」按工位）直接冲突；按本文头部「冲突时以用户最新确认为准」，**以按工位为准**，该条继承建议作废（2026-08-27 修订）。

旧项目可继承的仍有三条，与计数主体无关：触顶后**工位被 claim 过滤而非置为离线**（它没坏，只是今天不再接单），队列任务**原地不动等次日窗口重置**而不是失败重排，窗口按 **Asia/Shanghai 自然日**、惰性归零 + 定时主动重置双保险。

平台账号仍是一个独立对象（§工位与平台账号），但它回答的是「以哪个观察身份看到」，**不承担每日配额**。

### 必须改掉：重活不能跑在调度事务里

旧项目的调度 tick 用 `$transaction(timeout: 120s)` 持有 advisory lock，**而媒体下载（可达 120s）与 whisper 转录（可达 15 分钟）就在这个事务里跑**。任何超过 120 秒的 tick 都会丢锁并以异常收场。

**新项目必须把「调度决策」与「重执行」拆成两个独立进程/任务池。** 调度 tick 只做轻量状态推进与入队。

连带的第二条：旧项目把下载、转录、OCR 塞进同一个串行 outbox 循环，**转录一堵，图片下载全停**。新设计按资源类型分独立队列与独立并发度——转录独占（并发 1），下载是 IO 密集（可并发数十）。

### 转录并发：五轮修复换来的四条硬约束

Mog 说的「吃过亏」，完整根因链是：①最初无并发限制 → ②槽位泄漏（whisper 子进程先死，锁占满 6 小时）→ ③Promise 永挂（孙进程占住 stdio）→ ④代理抖动拖垮整批（一次事故 147 条转录全 dead）→ ⑤**孤儿进程绕过限流**（npm 中间层让服务变孤儿，KeepAlive 拉新实例反复 spawn whisper，卡死 16GB 机器）。

四条必须继承：

1. **并发限制必须跨进程。** 进程内 semaphore 在孤儿进程、重启窗口、独立 worker 面前是假的——第 ⑤ 条就是这么发生的。
2. **锁的存活判据要绑定真正干活的那个进程**，不是绑定服务进程。否则子进程死了锁还占着。
3. **默认离线模型**（`HF_HUB_OFFLINE=1` 等价物）。模型已在本地时子进程完全不碰外网。
4. **BUSY 背压不消耗重试次数。** 排队等待和执行失败是两回事，否则排队会把任务耗成死信。

参数：并发默认 **1**（旧项目注释原话「Mac mini 建议保持 1」），转录超时 15 分钟，槽位锁最大存活 6 小时。

### 可直接继承的设计

| 设计 | 要点 |
|---|---|
| **两段式租约** | `reserved`（预约）→ `in_progress`（执行），各有独立 TTL / epoch / token。「已派给工位」与「工位真的开始了」是两件事 |
| **TTL 按任务画像分档** | 轻扫 2 分钟 vs 完整详情 10 分钟，不搞一刀切 |
| **回收器的 TOCTOU 二次校验** | UPDATE 的 WHERE 必须重验租约仍已过期，否则会杀掉刚续租的活任务 |
| **拉模式 + 补货门槛** | 工位上报剩余工作量，低于目标 30% 才补货；服务端下发下次轮询间隔 |
| **失败策略单表 + 纯函数** | 一处定义 scope / retryable / 退避 / 上限 / 归因。未知错误码 fallback 为「重试 1 次」，不是无限重试也不是直接归档 |
| **媒体内容寻址** | 路径即 `{sha256}.{ext}`；先 staging 后原子 rename；边流边算 hash 边卡上限，大文件不进内存 |
| **generation 语义** | 签名 URL 在下载途中被刷新时，老任务不得用旧字节物化新来源 |
| **媒体两层去重** | 稳定标识符管身份，sha256 管字节。只用 URL 会因签名变化重复下载，只用 hash 会丢失来源关系 |
| **构建指纹守门** | 源码变了而构建产物是旧的 → 拒绝启动 |
| **直接 exec 目标进程** | 不套 npm/shell 中间层，让 supervisor 能杀到真正的服务进程 |

### 部署形态

**launchd**（非 pm2）两个服务：应用 + cloudflared tunnel，均 `KeepAlive`。Cloudflare Tunnel 把域名映射到 `localhost:3000`。CI/CD 是 GitHub Actions + Mac mini 自托管 runner。**生产库是部署机本机 Docker Postgres**，不是云库。

### 明确不继承的历史包袱

单体 28 步 tick（应按节奏拆成独立循环）、影子状态表（UI 直接读权威表）、两套并行的租约常量与两套 claim 实现、只做装饰不生效的 lane 配额、`nextRetryAt` 写了却没有 sweeper 扫描、三份重复的时区转换实现、`.catch(() => undefined)` 式的吞错（旧项目累计 519 条媒体登记失败只存在于日志里，无人知晓）。

## 8. 调研证据摘要

### 8.1 必须修的红线

**`collects` / `shares` 缺失时静默变成 `0`**，只有 `comments` 有 `publicCommentCountKnown` 这样的可判别标记。

这违反"未知不等于 0"的核心不变量，症状是**监控从不报警**——最难被发现的失败形态。修法现成：照抄 `publicCommentCountKnown` 的写法。

### 8.2 身份去重必须先建唯一索引

旧系统 `MonitorConfig` **没有任何唯一索引**，手工创建完全无去重检查，同一博主可建任意多个监控、各自持有独立基线。失败模式是**静默产生平行的重复监控**，不是报错。

插件推送必然遇到重复推送，**唯一索引必须在推送功能之前建立**。

`Author` 表的双唯一索引 `(workspaceId, authorEntityId)` + `(workspaceId, platform, platformAuthorId)` 是做对了的，可直接继承这个思路。

### 8.3 旧系统爆款判定的六个缺陷（不可继承的理由）

1. `surgeScore` 是死字段，实际用加权互动分的相邻差值
2. 绝对增量，零时间归一化
3. P95 不排除爆款自身，且密采观察会灌回样本池
4. 只保留正 delta，基线单向抬升
5. `take: 400` 按 contentId 字典序截断，不是取最近
6. 冷启动无兜底，少于 4 条正 delta 直接放弃判定

### 8.4 可继承的

| 机制 | 说明 |
|---|---|
| **删除监控不删数据** | 软删配置，作品数据原样保留——符合"Observation 只追加" |
| 淘汰建议三种处置 | eliminate / whitelist / ignore（24 周冷却） |
| 容量限流 + 排队 | 单监控 3 / 工作区 20 |
| 插件的两级判定协议 | `author_baseline` / `author_patrol` / `keyword_patrol` / `detail_probe` + `scanLimit` / `detailProbeLimit` / `surfaceOnly`，带测试，**不要重新发明** |
| 表层记录标记为 seed 级证据 | 明确"表层数据不能当真值" |

### 8.5 插件推送的通道已就绪

`author_profile` 包类型服务端已认（`PACKAGE_KINDS`），三段式投递 + 持久化 outbox + 幂等重试已跑通。博主身份字段齐全：ID / 昵称 / 头像 / 粉丝数 / 简介。

**只差一个轻量入口**——现在触发这条通道必须走一次全量采集，而「待决观察目标」只需要身份字段，应跳过原始载荷。

## 9. 产出交给谁

Mog 于 2026-08-26 确认：**爆款情报的出口是首页 + 飞书通知。** 具体进首页的规则与 UI 留到下一阶段首页规划时展开。

## 10. 未证明边界

- 本文件全部规则**未在真实数据上验证过**。频率公式、判定阈值、采样点选择都需要真实运行数据校准，第一版的具体数值一定是错的——重要的是它们可调且每次调整留记录。
- 平台字段能力来自 2026-07-01 的实测文档与当前解析代码。**平台随时可能改变返回字段**，§5.6 的表格需要定期复验。
- 关键词与博主"在数据层是同一套"的结论来自旧系统实现，**不等于新项目必须如此**。
- 爆款采样数据用于后期预测算法的价值单独立项，**当下不为此预留任何字段**——预留是最容易变成技术债的做法。
