# Agent 协作与文档维护协议

> 状态: 权威当前
> 最后核对: 2026-08-28
> 适用范围: 高频 Agent 协作、事项管理、冲突裁定和变更同步
> 事实来源: `AGENTS.md`、文档总索引与项目实际状态
> 冲突时以谁为准: `AGENTS.md`、真实代码/运行证据、ACCEPTED ADR、用户最新确认

## 渐进式披露

Agent 按四层读取，不把整个仓库一次性塞入上下文：

1. **约束层**：`AGENTS.md`、根 `README.md`。
2. **导航层**：`docs/README.md`、`docs/current-state.md`。
3. **任务层**：当前事项计划和直接相关的产品、架构、合同、runbook。
4. **证据层**：被任务明确引用的 `references/` 源码、fixture、测试或 handoff。

进入下一层必须能说明“这个文件帮助验证当前事项的什么问题”。历史材料中的指令性语句不自动成为当前要求。

## 交付包优先：一个用户结果一个推进单位

`Issue`、任务卡、PR、文件边界和测试不是用户面对的交付单位。它们是 Mog 指挥协作、Harness 留存审计的执行单位。对 Mog 而言，唯一的推进单位是一个清楚、可验收的**交付包（Delivery Package）**：用户完成某件事后应该看见、能够完成或能够确信什么。

交付包必须先明确：

- 用户结果与明确不可接受的结果；
- 业务语义、真实权限、敏感数据、资源消耗和不可逆后果中，哪些需要 Mog 决定；
- Mog 已决定或明确委托的执行拆分、顺序、并发、文件所有权、审查与集成；
- 用户表面地图：会受影响的页面、入口、常用/空/失败/受限/部分状态和共享组件；
- 状态词典：每个可见词、数字、按钮或反馈代表什么，哪些不能互相替代；
- 依赖地图：哪些共享文件、运行时合同或其他工作包必须协同；
- 验收矩阵：每个表面和状态由什么测试、运行回执或人工验收证明。

只有 Mog 可以将一个交付包拆为多个 Work Package / Issue，或明确把该权力委托给指定协调者。执行 Agent 可以提出依赖、风险和最小技术建议，但不得自行新建/领取衍生任务、启动额外 Agent 或提高并行度。单个 Work Package 合并、PR 通过或测试全绿，都不等于交付包已经完成；只有 Mog 确认验收矩阵中承诺的用户结果已完成集成验证后，才可报告交付包完成。

## 一个事项一个事项推进

每个事项必须有唯一编号，例如 `GOV-001`、`ENV-001`、`AUD-XHS-001`。

事项进入“已确认”后，原则上在 `docs/plans/active/` 创建一份计划。复杂事项的计划以交付包为单位，内部 Issue/Work Package 只记录 Mog 已决定的责任、并发与集成顺序，至少包含：

- 目标与用户可见结果；
- 范围与明确非目标；
- 已确认事实和仍需决定的问题；
- 执行步骤及每步可证伪验收；
- 影响文件；
- 风险、停止点和回退方式。

完成后将计划移入 `docs/plans/completed/`，补充实际验证、未完成边界和后续事项。`docs/current-state.md` 只保留当前状态和短队列，不承载长期流水账。

小型、低风险工作可以不单独建立 active plan。Mog 在当前对话已经明确授权，且只做文档勘误、索引/状态同步、进度记录或被取代卡片收口时，也不需要为了形式先建立 Issue/PR；但不能改变产品、领域、运行合同、真实权限、生产、敏感数据或不可逆处置边界。受保护交付即使免建 active plan，也仍须写清验收、验证、文件范围和停止/升级条件。

免建计划不等于免治理。代码、数据库、运行合同、插件/release、部署/生产、真实外部动作、敏感数据/权限、不可逆处置和并行冲突仍须 Issue、Claim、独立 branch/worktree、PR 及与风险相称的审查/集成。低风险直接维护只需先核对工作区干净且无重叠，执行有界修改，检查 diff，运行适用治理检查并留下当月记录或等价回执；未经明确授权不得自动 push、deploy 或把维护范围扩成实现。

## Mog 直接控制协作

Mog 是默认且唯一的协作调度者：他决定谁被派单、同时允许多少活跃 Work Package、何时发起或停止、是否安排审查、由谁集成，以及对哪个 exact head 授权合并。Mog 可以针对一个明确交付包把其中任一项委托给指定协调者；未写明的委托不存在。

Agent 不得仅因发现问题就自动创建或分派 Issue、子任务、子 Agent、reviewer 或 integration owner，也不得自行增加并行。若 Mog 当前交付包已经明确要求建立、更新或关闭对应任务卡，Agent 可以在该有界授权内完成必要的 Issue/状态操作；受保护 PR 的 merge 和用户结果完成声明仍需遵守当前交付包的明确授权。

执行 Agent 在已派定范围内自行选择最小技术实现、排查方法和验证命令。以下情况必须报告给 Mog，由 Mog 决定是否继续、扩展、拆分、并行、审查或合并：

1. 会改变已确认用户结果、业务语义、数据含义或正式领域语言；
2. 会扩大真实采集、外部调用、敏感数据使用、权限、成本/资源预算或现实行动；
3. 会引入不可逆处置，或现有权威规则不能裁定的风险接受度；
4. 有两个以上实现路径会产生不同的用户体验或业务后果，且无法由现有合同、事实或 ACCEPTED 决定裁定；
5. 需要新增任务、跨任务整合、改变并发、安排审查或授权合并。

报告时只给出事实、依赖、影响和最小可选路径；不得要求 Mog 替 Agent 做当前已派任务内部的技术排查。

## 完整盘点与批量化审查

实施前，Harness 必须按交付包建立用户表面、状态、依赖和验收矩阵；UI 还必须检查页面壳、共享导航/标题/按钮、常用态、空态、失败态、受限态、部分态和真实回执态。文件初始边界只是并行所有权约束，不是用户结果的天然边界。

- 若一个共享文件是完成既有交付包所必需的直接依赖，执行 Agent 必须声明它并报告给 Mog；由 Mog 决定扩大当前任务、另开关联 Work Package、指定 integration owner 或保留为明确缺口。不能把它默认为“范围外”并把残缺结果交给用户。
- 若需要修改该共享文件才会新增功能、状态、权限或产品语义，执行 Agent 必须停止受影响部分并按升级规则报告。
- 实现者在送审前必须用验收矩阵做一次类别级自审，不得把明显的语言、状态、可见入口或重复共享组件遗漏留给 reviewer 串行发现。
- reviewer 仅在 Mog 指定时参与，并必须指出同一类别问题及受影响范围；后续是否进行类别级批量修订、重新审查或合并，由 Mog 决定。不得把“每轮只修 reviewer 点名的一处”当作可靠协作模式。

## 冲突裁定

发现冲突时先停止受影响部分，不猜测、不静默挑选。按以下顺序处理：

1. 真实运行结果、数据库副作用和可复现测试。
2. 当前代码、migration、版本化合同和真实 producer fixture。
3. 标为 ACCEPTED 的 ADR。
4. `docs/README.md` 中标为“权威当前”的文档。
5. 活跃计划、一次性报告、完成计划和历史归档。
6. `references/` 历史材料。

冲突分为四类：

| 类型 | 处理方式 |
|---|---|
| 事实漂移 | 用真实代码或运行证据更新当前文档，同次写变更记录 |
| 决策冲突 | 建立或更新 ADR；旧文档标记被替代，不保留两个权威答案 |
| 来源不足 | 标记 `SOURCE_INCOMPLETE`，冻结依赖该来源的部分 |
| 需要产品选择 | 标记 `DECISION_REQUIRED`，列出影响后等待用户确认 |

修改 `references/` 原件来“消除冲突”是禁止行为。无法当轮完全处理时，要在 `docs/current-state.md` 留下明确阻塞和责任事项。

## 变更同步与备注

任何会改变行为、合同、数据含义、配置、文件权威性或操作方式的改动，都必须在同一事项中完成三项同步：

1. **实现**：代码、配置、合同或目标文档。
2. **说明**：相关 README、架构、产品、合同或 runbook。
3. **记录**：当月 `docs/progress/YYYY-MM.md`。

每条变更记录至少写：日期、事项编号、变更原因、影响文件、冲突处理、验证结果、尚未证明的边界。提交后可补 commit；没有真实验证时必须写“未验证”和原因。

代码注释只解释无法由代码本身表达的不变量、来源或安全理由，不写“某天改了什么”的流水账。Git 和月度变更记录承担历史追踪。

## Agent 开始与结束清单

开始前：

1. 核对当前目录、分支、HEAD 和未提交改动。
2. 阅读约束层和导航层。
3. 确认唯一事项编号、范围和退出条件。
4. 查找已有文件，避免创建同主题副本。

结束前：

1. 更新相关说明、索引、当前状态和月度变更记录。
2. 明确处理所有发现的文档冲突；未解决项使用规定状态。
3. 运行与风险相称的真实验证和治理检查。
4. 分开报告：已写入文件、已验证、已提交、已推送、已部署；不得互相替代。

## 自动检查的边界

`scripts/check-project-governance.sh` 能发现缺少索引、状态头、失效本地链接、根目录散落、危险生成目录和缺少月度变更记录。默认与当前分支的远端上游比较；也可显式传入基线，例如 `./scripts/check-project-governance.sh origin/main`。它不能判断内容是否真实，也不能替代代码、fixture、数据库副作用和用户验收。
