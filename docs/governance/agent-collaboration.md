# Agent 协作与文档维护协议

> 状态: 权威当前
> 最后核对: 2026-08-21
> 适用范围: 高频 Agent 协作、事项管理、冲突裁定和变更同步
> 事实来源: `AGENTS.md`、文档总索引与项目实际状态
> 冲突时以谁为准: `AGENTS.md`、真实代码/运行证据、ACCEPTED ADR、用户最新确认

## 渐进式披露

Agent 按四层读取，不把整个仓库一次性塞入上下文：

1. **约束层**：`AGENTS.md`、根 `README.md`。
2. **导航层**：`docs/README.md`、`docs/current-state.md`。
3. **任务层**：当前事项计划和直接相关的产品、架构、合同、runbook。
4. **证据层**：被任务明确引用的 `references/` 源码、fixture、测试或 handoff。

进入下一层必须能说明“这个文件帮助验证当前事项的什么问题”。历史材料中的指令性语句不自动成为当前要求。

## 交付包优先：一个用户结果一个推进单位

`Issue`、任务卡、PR、文件边界和测试不是用户面对的交付单位。它们是 Harness 为了可靠完成工作而使用的内部执行单位。对 Mog 而言，唯一的推进单位是一个清楚、可验收的**交付包（Delivery Package）**：用户完成某件事后应该看见、能够完成或能够确信什么。

交付包必须先明确：

- 用户结果与明确不可接受的结果；
- 业务语义、真实权限、敏感数据、资源消耗和不可逆后果中，哪些需要 Mog 决定；
- Harness 自主决定的实现拆分、顺序、文件、测试、审查和集成；
- 用户表面地图：会受影响的页面、入口、常用/空/失败/受限/部分状态和共享组件；
- 状态词典：每个可见词、数字、按钮或反馈代表什么，哪些不能互相替代；
- 依赖地图：哪些共享文件、运行时合同或其他工作包必须协同；
- 验收矩阵：每个表面和状态由什么测试、运行回执或人工验收证明。

Harness 可以把一个交付包拆为多个 Work Package / Issue，但不得把这种内部拆分变成要求 Mog 逐项决定技术路径的理由。单个 Work Package 合并、PR 通过或测试全绿，都不等于交付包已经完成；只有验收矩阵中承诺的用户结果完成集成验证后，才可报告交付包完成。

## 一个事项一个事项推进

每个事项必须有唯一编号，例如 `GOV-001`、`ENV-001`、`AUD-XHS-001`。

事项进入“已确认”后，原则上在 `docs/plans/active/` 创建一份计划。复杂事项的计划以交付包为单位，内部 Issue/Work Package 只记录责任和集成顺序，至少包含：

- 目标与用户可见结果；
- 范围与明确非目标；
- 已确认事实和仍需决定的问题；
- 执行步骤及每步可证伪验收；
- 影响文件；
- 风险、停止点和回退方式。

完成后将计划移入 `docs/plans/completed/`，补充实际验证、未完成边界和后续事项。`docs/current-state.md` 只保留当前状态和短队列，不承载长期流水账。

小型、低风险、单 Issue/单 PR 工作可以不单独建立 active plan，但必须同时满足：已有 SCOPE/ACCEPTED 治理规则/用户明确授权；不改变产品、领域、系统架构、真实权限、生产或敏感数据边界；不跨多个 Issue/PR；Issue 已完整写明验收、验证计划、文件范围、停止/升级条件和完成报告要求。任一条件不满足，仍必须先建 active plan。

免建计划不等于免治理。任何仓库写入仍须 Issue 分配、Claim、独立 branch/worktree、draft PR、非实现者独立审查、稳定 task-id 的 integration owner、当月记录，以及 merge 后重新核验和手工关闭 Issue。纯只读调查/审查不需要 worktree/PR；一旦写回仓库即适用上述链路。

## Harness 自主与升级边界

Harness 默认自行决定任务粒度、实现顺序、文件分配、测试层级、审查安排和集成方式。不得把这些技术选择包装成 `DECISION_REQUIRED` 交给 Mog。需要升级给 Mog 的只包括：

1. 会改变已确认用户结果、业务语义、数据含义或正式领域语言；
2. 会扩大真实采集、外部调用、敏感数据使用、权限、成本/资源预算或现实行动；
3. 会引入不可逆处置，或现有权威规则不能裁定的风险接受度；
4. 有两个以上实现路径会产生不同的用户体验或业务后果，且无法由现有合同、事实或 ACCEPTED 决定裁定。

升级时只提出最小的业务选择，并说明不选择时 Harness 将如何安全停在当前边界。不得要求 Mog 判断文件、分支、数据库实现、测试命令、Agent 分工或故障排查假设。

## 完整盘点与批量化审查

实施前，Harness 必须按交付包建立用户表面、状态、依赖和验收矩阵；UI 还必须检查页面壳、共享导航/标题/按钮、常用态、空态、失败态、受限态、部分态和真实回执态。文件初始边界只是并行所有权约束，不是用户结果的天然边界。

- 若一个共享文件是完成既有交付包所必需的直接依赖，Harness 必须声明它、安排关联 Work Package 或交由 integration owner；不能把它默认为“范围外”并把残缺结果交给用户。
- 若需要修改该共享文件才会新增功能、状态、权限或产品语义，才应停止受影响部分并按升级规则处理。
- 实现者在送审前必须用验收矩阵做一次类别级自审，不得把明显的语言、状态、可见入口或重复共享组件遗漏留给 reviewer 串行发现。
- reviewer 发现同一类别问题时，必须指出该类别与受影响范围；Harness 应完成类别级盘点和一次有界批量修订，再审查新的 exact head。不得把“每轮只修 reviewer 点名的一处”当作可靠协作模式。

## 冲突裁定

发现冲突时先停止受影响部分，不猜测、不静默挑选。按以下顺序处理：

1. 真实运行结果、数据库副作用和可复现测试。
2. 当前代码、migration、版本化合同和真实 producer fixture。
3. 标为 ACCEPTED 的 ADR。
4. `docs/README.md` 中标为“权威当前”的文档。
5. 活跃计划、一次性报告、完成计划和历史归档。
6. `references/` 历史材料。

冲突分为四类：

| 类型 | 处理方式 |
|---|---|
| 事实漂移 | 用真实代码或运行证据更新当前文档，同次写变更记录 |
| 决策冲突 | 建立或更新 ADR；旧文档标记被替代，不保留两个权威答案 |
| 来源不足 | 标记 `SOURCE_INCOMPLETE`，冻结依赖该来源的部分 |
| 需要产品选择 | 标记 `DECISION_REQUIRED`，列出影响后等待用户确认 |

修改 `references/` 原件来“消除冲突”是禁止行为。无法当轮完全处理时，要在 `docs/current-state.md` 留下明确阻塞和责任事项。

## 变更同步与备注

任何会改变行为、合同、数据含义、配置、文件权威性或操作方式的改动，都必须在同一事项中完成三项同步：

1. **实现**：代码、配置、合同或目标文档。
2. **说明**：相关 README、架构、产品、合同或 runbook。
3. **记录**：当月 `docs/progress/YYYY-MM.md`。

每条变更记录至少写：日期、事项编号、变更原因、影响文件、冲突处理、验证结果、尚未证明的边界。提交后可补 commit；没有真实验证时必须写“未验证”和原因。

代码注释只解释无法由代码本身表达的不变量、来源或安全理由，不写“某天改了什么”的流水账。Git 和月度变更记录承担历史追踪。

## Agent 开始与结束清单

开始前：

1. 核对当前目录、分支、HEAD 和未提交改动。
2. 阅读约束层和导航层。
3. 确认唯一事项编号、范围和退出条件。
4. 查找已有文件，避免创建同主题副本。

结束前：

1. 更新相关说明、索引、当前状态和月度变更记录。
2. 明确处理所有发现的文档冲突；未解决项使用规定状态。
3. 运行与风险相称的真实验证和治理检查。
4. 分开报告：已写入文件、已验证、已提交、已推送、已部署；不得互相替代。

## 自动检查的边界

`scripts/check-project-governance.sh` 能发现缺少索引、状态头、失效本地链接、根目录散落、危险生成目录和缺少月度变更记录。默认与当前分支的远端上游比较；也可显式传入基线，例如 `./scripts/check-project-governance.sh origin/main`。它不能判断内容是否真实，也不能替代代码、fixture、数据库副作用和用户验收。
