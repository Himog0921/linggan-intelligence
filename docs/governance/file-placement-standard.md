# 文件分类与放置标准

> 状态: 权威当前
> 最后核对: 2026-08-21
> 适用范围: 全仓库文件创建、生成、移动、重命名、归档与删除
> 事实来源: 当前项目结构、`AGENTS.md` 与项目生命周期
> 冲突时以谁为准: `AGENTS.md`；具体技术事实以真实代码和运行结果为准

## 核心原则

每个文件都必须像图书馆藏书一样具备：明确分类、固定书架、稳定书名、索引入口、权威状态和可追溯来源。不能回答这些问题时，不创建文件。

创建前必须确认：

1. 是否已有文件承载同一主题。
2. 它属于权威当前、活跃计划、完成计划、审计报告、进度记录、历史归档还是临时/生成物。
3. 下一个 Agent 会到哪个目录寻找它。
4. 哪个索引必须同步更新。
5. 它与现有文件是否冲突，谁负责裁定。

## 固定书架

| 位置 | 允许内容 |
|---|---|
| 根目录 | 入口文件和工具配置，例如 `README.md`、`AGENTS.md`、Cargo/Git 配置 |
| `apps/` | Rust 可执行程序组合入口；MODEL-PI-001 明确授权 `apps/pi-adapter/` 为固定官方 Pi 的窄 Node 适配入口，不承担业务/持久主账。均不存放计划或报告 |
| `crates/` | Rust 模块源码，不存放一次性分析材料 |
| `database/` | 全新 PostgreSQL migration、脱敏 fixture、数据库边界说明 |
| `docs/agents/` | Agent 工程技能的仓库级配置、任务追踪规则、标签映射和领域文档消费规则；不得复制产品或架构真相 |
| `docs/context/` | 当前项目背景和来源盘点 |
| `docs/product/` | 产品定义、用户工作流和验收标准 |
| `docs/design/` | 已获准的 UI 设计手册入口、跨页面规则、经验证模式、组件/页面执行规格、设计参考登记与验收表单；不得复制产品/数据/权限真相 |
| `docs/architecture/` | 当前或目标架构与模块边界 |
| `docs/data-contracts/` | 经审计后确认的字段、接口、状态和版本合同；需要时再创建 |
| `docs/decisions/` | 可长期生效的 ADR 决策 |
| `docs/governance/` | 文件、文档和 Agent 协作规则 |
| `docs/runbooks/` | 可重复执行的环境、运维和恢复步骤；需要时再创建 |
| `docs/plans/active/` | 已确认且正在执行的事项计划 |
| `docs/plans/completed/` | 已完成事项的范围、验证和遗留记录 |
| `docs/audits/` | 一次性来源审计、调查和可行性报告；需要时再创建 |
| `docs/progress/` | 按月维护的重要变更记录 |
| `docs/archive/` | 被替代但仍需保留的项目文档；需要时再创建 |
| `references/` | 只读历史证据、固定源码快照、旧合同与 handoff |

不创建没有内容的“预留目录”。当第一个真实文件产生时再建立对应目录并登记索引。

### UI 设计手册的分责

- `docs/pages/` 决定页面服务的用户任务、事实含义、状态语义与行动后果；`docs/design/` 只规定在这些已确认边界内如何一致表达和验收，不能反向改写产品语义。
- 字段、读写、版本、权限和回执的可执行合同进入 `docs/data-contracts/`；设计文档只能引用，不能为视觉需要新增或改写。
- UI Agent 的读取、执行、停工和交接规则进入 `docs/agents/`；长期设计例外或跨页面取舍进入 `docs/decisions/`；实际变更历史进入 `docs/progress/`。
- `docs/design/` 下的 foundation、patterns、components 和 pages 等子目录只在首份已批准、确有内容的对应材料出现时创建。不得为了目录完整性预建空书架。

## 命名与状态

- 权威当前文档使用稳定、无日期的英文小写连字符名称，例如 `target-architecture.md`。
- 计划文件使用事项编号，例如 `env-001-development-environment.md`。
- 一次性审计或报告使用主题加日期，例如 `xhs-producer-audit-2026-08-20.md`。
- 禁止 `最新版`、`最终版`、`final-final`、`copy`、`temp`、`draft2` 等无法表达生命周期的名称。
- 重要 Markdown 顶部必须包含：状态、最后核对、适用范围、事实来源、冲突时以谁为准。

允许状态：`权威当前`、`代码事实优先`、`活跃计划`、`已完成计划`、`一次性报告`、`历史归档`、`草案`。

## 生成型文件

生成型文件包括构建结果、代码生成结果、导出报告、测试证据、日志、截图、数据库备份和临时数据。

规则如下：

1. 生成前先查 [`generated-artifacts-registry.md`](generated-artifacts-registry.md)。
2. 已登记产物只能写入登记位置；不得为了方便改写输出目录。
3. 未登记产物默认使用操作系统临时目录且不得提交。需要长期保留时，先补登记再生成。
4. 构建缓存、秘密、数据库 dump、未脱敏 Evidence 和运行日志不得进入 Git。
5. 必须提交的生成代码或派生文件，要记录唯一来源、生成命令、负责人、是否允许手改和一致性检查。
6. 生成物与来源冲突时，来源文件优先；重新生成，不手工修补生成结果。

## 移动、替代与删除

- 移动文件必须同步修复索引、链接和引用。
- 新文档替代旧文档时，旧文档默认保留，并在状态头或总索引标记“被谁替代”；不能静默留下两个权威入口。
- 历史证据不因过时而改写；使用当前文档解释其适用边界。
- 删除前必须确认没有入口、代码、测试或决策仍引用它，并在变更记录中写明原因和恢复方式。
- 临时文件可清理，但清理目标必须精确；不得对仓库根目录或不明确路径执行递归删除。

## 入库检查

所有新文件都要通过：

1. 最近索引已更新，重要文档进入 `docs/README.md`。
2. 状态头完整且与目录生命周期一致。
3. 当月 `docs/progress/YYYY-MM.md` 已登记。
4. 生成物登记、忽略规则和秘密边界一致。
5. `./scripts/check-project-governance.sh` 通过。
