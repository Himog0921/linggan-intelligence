# 前端设计治理协议

> 状态: 权威当前
> 最后核对: 2026-09-02
> 适用范围: Linggan Intelligence 的 UI 设计规则、页面/组件规格、实施变更、评审与例外处理
> 事实来源: AGENTS.md、docs/governance/、docs/agents/ui-execution-contract.md、用户确认的 DESIGN-001 范围和已确认产品/领域边界
> 冲突时以谁为准: 用户最新确认、AGENTS.md、真实运行/代码/合同、ACCEPTED 决策与当前 SCOPE；冲突时停止受影响工作

## 目标

本协议把“设计”限制为一组可追溯、可组合、可验证、可替代的界面合同。它的目的不是降低创造性，而是阻止 Agent 在信息不足时把合理猜测包装成页面事实、交互承诺或长期视觉规则。

任何规则的价值不在于文字本身，而在于下一个 Agent 能回答四个问题：

1. 这条规则从哪里来；
2. 它适用于什么，不适用于什么；
3. 它如何被实现和验收；
4. 与它冲突时谁有权裁定。

## LIDS 的治理地位

[LIDS v7.0](lids/README.md) 是 Linggan 的唯一设计表达标准。所有未来 UI 工作必须按 `Token → Primitive → Component → Pattern → Page` 选择和记录设计决策，Motion / Scene / Data Truth / 材料 / 壳层区位 / 数据边界为横向约束。它已是执行约束，但成熟度保持 `PROPOSED`：不得把标准存在误写为主题 CSS、组件、真实页面、真实状态、3D、部署或用户验收已经存在。

**规则状态与运行时状态必须分开陈述。** DESIGN-010（2026-09-02）把标准升级到 v7.0，但运行时代码未迁移。任何文档、Issue、PR 描述或验收记录在引用 LIDS 条款时，必须能回答"这条是规则已采纳，还是代码已符合"——两者混写是本项目已记录的失真方式，见 [lids/decisions.md](lids/decisions.md) 的两栏状态表。

LIDS 只能回答“在已获批准的产品含义下如何一致表达”。来源包及其 V3 原型中的模拟内容、技术建议、文件路径、动态效果、数据数值和运行状态都不是本仓库的事实或实现许可。真实代码/合同优先。运行时 Token 唯一真源为 `apps/api/src/local_web/lids_tokens.css`；`lids/tokens.md` 第 3 节是其受校验镜像，第 2 节的 v7 三层架构是新工作的选值依据但尚未进入运行时，两者不可互相冒充。

## 两类问题，两个优先级

UI 工作必须先区分“现在实际发生什么”和“是否获准这样设计”：

| 要回答的问题 | 首要来源 | 不能用什么替代 |
|---|---|---|
| 当前页面、接口或状态实际怎样运行 | 真实运行结果、真实代码、版本化合同、测试证据 | 设计稿、预期截图、聊天描述 |
| 某种产品含义、权限、状态或行动是否获准 | 用户确认、ACCEPTED 决策、当前 SCOPE、权威产品不变量 | 现有代码、旧页面、模型建议 |
| 在既有含义下界面怎样一致地表达 | 状态为“权威当前”的设计基础/模式/组件/页面规格 | 通用审美、参考图、临时实现 |

发生冲突时，不做平均、不静默选择、不把一层内容复制到另一层。按 docs/governance/agent-collaboration.md 的事实漂移、决策冲突、来源不足或需要产品选择四类方式处理。

## 设计来源优先级

从高到低，只有在不与更高层冲突时，较低层才能提供实施依据：

1. 用户最新确认与 AGENTS.md；
2. 真实运行结果、当前代码、版本化合同和可复现测试；
3. ACCEPTED 决策与当前 SCOPE；
4. docs/README.md 登记为“权威当前”的产品、领域、数据合同与设计文件；
5. 已获批准的事项计划和已完成计划中的实际证据；
6. 状态为“草案”的页面/架构/设计材料；
7. references/、旧系统、截图、外部产品和通用设计惯例。

第 6–7 层只能帮助提出候选或核对历史，不能单独授权实现。任何缺少第 1–4 层支撑的具体规则都必须保持草案，或被标记为 DECISION_REQUIRED。

## 闭集执行

UI Agent 只能组合本次事项明确引用的、仍为“权威当前”的页面职责、基础规则、模式、组件规格和数据合同。

以下行为一律禁止：

- 因为页面“看起来缺东西”新增导航、功能区、状态、数据字段或行动入口；
- 因为某种视觉效果常见，就把参考图或旧系统实现当作当前规范；
- 用加载态、空态、成功提示、颜色、图标或文案压平不同的业务状态；
- 为了组件复用而把产品判断、权限判断、数据修复或行动授权藏进前端；
- 用局部实现反向宣布一个新的设计体系、页面结构或产品承诺已经成立。

规则不存在、来源相冲突、数据合同缺失、状态含义不明或验收方法未定义时，必须停止受影响部分并在当前事项中记录 DECISION_REQUIRED。

## 变更分类与最小授权

每个 UI 变更必须在实施前分类。分类决定 Agent 能否继续，以及需要哪些来源。

| 类型 | 说明 | 最少依据 | Agent 不得越过的边界 |
|---|---|---|---|
| 展示 | 已有信息、层级或容器怎样呈现 | 页面规格加相关设计规则 | 不改数据范围、状态含义或行动后果 |
| 交互 | 用户怎样展开、筛选、确认、返回或恢复 | 页面规格加交互模式 | 不发明新业务状态、权限或后端动作 |
| 状态/语义 | 页面怎样区分已知、未知、处理中、受限、失败或部分结果 | 页面文档加数据/状态合同 | 不用视觉便利改写事实或资格 |
| 权限/行动 | 页面怎样申请、授权、执行、撤回或展示敏感材料 | 产品/权限/行动合同与当前 SCOPE | UI Agent 不得自行授权或伪造已执行结果 |

一个变更同时触及多类时，按风险最高的一类处理。无法分类不是“默认展示调整”，而是 DECISION_REQUIRED。

## 可追踪规格

所有获准执行的设计规则使用稳定 ID：

- DS-xxx：跨页面基础规则；
- PAT-xxx：经过验证的模式；
- CMP-xxx：组件合同；
- PAGE-xxx：页面组合规格；
- ACC-xxx：验收项。

ID 只用于追踪，不替代来源。每一条可执行规则至少说明：

- 来源与适用范围；
- 正向要求和明确非目标；
- 受影响的页面、模式、组件或数据状态；
- 可接受的例外与冲突处理方式；
- 最小验收方法；
- 该规则尚不能证明什么。

页面、组件和变更事项应分别使用本目录 templates/ 下的模板；不得复制出第二套模板或用聊天记录替代正式规格。

## 实施与验收门

每个 UI 事项按以下顺序推进：

1. 读取：完成 UI execution contract 要求的读取，并写出来源清单；
2. 定义：填写 UI change manifest，固定范围、非目标、变更分类与停止条件；
3. 规格：确认每个被实现的元素可回链到 PAGE、PAT、CMP、DS 或数据合同；
4. 实施：只写当前获准的最小切片，不顺手扩张；
5. 验收：分别验证任务可用、状态诚实、视觉一致、动作后果真实；
6. 收口：更新相关索引、实施追踪、变更记录和未证明边界。

截图、类型检查、测试通过、HTTP 成功或出现 toast 都不能单独通过第 5 步。验收模板必须写明本次各层实际验证结果与未验证原因。

## 例外、替代与废止

局部且临时的偏离必须在当前事项的变更清单中注明：偏离的规则 ID、原因、影响范围、复核触发条件和回退方式。

会影响多个页面、组件或未来实现的偏离，必须在实施前形成 docs/decisions/ 中的长期决定；不得把例外埋在 CSS、组件分支、注释或截图中。

新规则替代旧规则时：

1. 旧规则保留，并明确替代者；
2. 受影响的页面/组件清单必须可查询；
3. 未迁移的实现如实标为未完成，不以文档升级掩盖；
4. 变更记录说明实际验证层级和未证明范围。

## 对设计参考的约束

设计参考只能在 reference-register.md 中登记后使用。登记必须明确来源、可借鉴的层面、明确不继承的层面、是否需要重新核验，以及它不能成为实现授权的原因。

参考不具有以下权力：改变产品任务、添加页面、修改事实语义、扩大敏感材料展示、授予行动权限、决定前端技术方案，或让草案自动变成“权威当前”。
