## 4. 走查中发现并修正的问题

1. **导出当天被当成完整的一天**：10-12 的每日数据还没人填，按日历算时本周、本月到处是「下降 100%」。改为只算到导出日的前一天，上期按同样天数对齐；一天都没迁入时写「—」，不比、不提醒（PAGE-OPS-002 §2.1）。
2. **矩阵的长账号名压到旁边的平台列** → 账号名省略、悬停看全名；横向滚动时账号列固定在左边，表头固定在上面。
3. **手机宽度下图表文字被等比缩到约 5px**（图按 640 宽画好再整体缩小） → 图按容器实际宽度画，宽度变化时重画；坐标文字保持 Token 字号（`--lgi-text-calibration`，9px）。
4. **长趋势第一个日期被裁掉一半** → 靠边的坐标文字改为左对齐或右对齐。
5. **窄屏下时间段一行被截断** → 改为换行。
6. **排行的「下一步」写「查看排行并复盘下降原因」**：在排行里自指，还挤成三行。改为短句并写明是哪一项（「复盘发布下降」「复盘链接打开下降」「补阅读量」等）。接口为此在排行行里加了 `riskMetric`。
7. **读取失败时，新页签下还留着上一个时间段的数字**，标题也停在「本周加微」 → 五块收起，只留原因和重试；标题跟随页签。
8. **目标对话框的单选框排在文字上方** → 与文字同一行。
9. **「别人先改」之后，修改记录还是旧的** → 重新读取并显示。
10. **当前目标还没读回来就能保存**（会被服务端判为「别人先改」）；切换周期时，慢回来的另一个周期可能盖住当前周期 → 读到之前不允许保存，只认最后一次读取；保存途中切了周期，回执不落到对话框上。
11. **原样保存后的「目标没有变化。」被随后的重读清掉** → 重读完成后再显示。
12. **只有一天的时间段写成「10-12 ~ 10-12」** → 只写一天。

## 5. 规则反证

临时改坏一处规则，确认对应证明变红，再按备份逐字节还原并核对哈希。用的是随机命名的隔离 PostgreSQL，结束即删除。

| 改坏的规则 | 变红的证明 |
|---|---|
| 上期取整个上月或上周，不按同样天数 | 本月、本周、导出日三项总览证明 |
| 没有每日数据时，链接打开、加微按 0 比较 | 「缺每日数据不算下降」单元测试与本月总览证明 |
| 去掉「看到的不是当前记录就不写入」 | 目标回执证明与并发保存证明 |
| 导出当天算作完整的一天 | 「导出日之后的日子是未知」证明 |
| 不查请求号，重复请求再保存一次 | 目标回执证明（重复请求应返回第一次的回执） |
| 去掉按周期加锁 | 并发保存证明（两个同时的保存应一个成功、一个「别人先改」） |
| 本期每天都记 0 也算下降（10-14 改动之前的规则） | 「全记 0 是待确认、不是下降」单元测试与对应的总览证明 |

## 6. 真实数据里看到、需要 Mog 决定的事

1. **「0」和「没填」分不开**（已决定，见下）：每日数据默认填 0。副本上 10-01～10-11 有 4 位运营人仍在发帖，链接打开和加微却每天都是 0；其中 2 位 9 月上旬还有数、9 月 23 日以后一直是 0。另有 1 位 9 月 24 日以后没有发布登记，名下仍有 12 个账号。下降规则与工作台相同，所以今日必须处理的前 5 项都是后面这几位的「下降 100%」，自动结论也点了其中两位「需今天复盘」。这可能是真的掉了，也可能是没填。
   **Mog 2026-10-14 决定**：不算下降，单独列为「本期记的都是 0 · 确认是否漏填」，不算进「需今天复盘」。改完后这几条排在真实下降之后、被折进「另有 N 项」，Mog 又决定让「另有 N 项」可以在原处展开。两项都已实现并复核（第 2 节）。
2. **「节奏正常」的说法**：沿用工作台的判断（时间进度比完成率高出 20 个百分点以上才算「有缺口」），月初会出现「节奏正常：按当前节奏预计完成 48%」这样读起来矛盾的句子。**Mog 2026-10-14 决定**：预计完不成时不说「节奏正常」，只写预计完成多少。已实现并复核。
3. **默认的「本周」在两次迁入之间常常是空的**（已告知 Mog，未改）：数据只到最近一次迁入的前一天，本周还没有完整的一天时，打开总览看到的都是「—」，要切到「本月」或重新迁入工作台的导出才看得到数。
