## 1. 首版用户任务

| 任务 | 操作入口 | 用户看到的结果 |
| --- | --- | --- |
| 邀请运营 | 团队成员 → 邀请成员 | 管理员可复制设密链接。受邀人签收后，名册显示已启用，并提供「分配账号」。 |
| 分配账号 | 成员行的「分配账号」，或运营账号行的「交接」 | 管理员可确认接任人。运营看到当前负责的账号，可从账号行打开「待补阅读量」。 |
| 停用 | 团队成员 → 选中成员 → 停用 | 管理员可在计划离职时一次完成交接和停权，或选择立即停用。 |
| 接管 | 停用结果 → 去接管 | 现有账号台账打开该成员留下的待接管账号。每个账号分配后，可查到实际接任人。 |

沿用现有邀请制、角色和分组范围。首版名册可读分组信息，并处理最后一名组长离职时的临时代管。分组创建、重命名、调组、调岗、回聘和自助找回密码另列。小红书／抖音平台登录态、设备和插件工位按各自权限处理。

## 3. 邀请和分配账号

1. 管理员创建普通运营邀请，复制一次性设密链接并通过现有渠道交付。成员行区分待签收、已过期、已撤销、已启用。生成链接和签收各有状态。
2. 受邀人签收并设密后，管理员从成员行打开账号台账。可以将未分配或待接管的账号分给该成员。已有负责人的账号沿用交接确认。签收前、已停用或选中离职者本人时，服务端拒绝作为接任人。
3. 分配完成后，运营在账号台账看到本人当前负责的账号。原有同组管理权限仍按有效成员与当前组判定。管理员可跨组分配，确认时显示接任人及分组。

现有邀请和会话规则继续适用。普通运营只能管理获授权的账号和本人业务记录。组长保留现有同组操作范围。管理员管理邀请、离职和待接管账号。 [内部团队会话合同](../data-contracts/ops-auth-001.md) · [团队责任合同](../data-contracts/ops-team-responsibility-001.md)

## 4. 停用和接管（D01 已确认）

两种操作共用「团队成员 → 停用」入口。页面先显示成员及停用后果。计划离职展开账号和接任人，紧急停用可直接确认。

| 情况 | 管理员操作 | 系统结果 |
| --- | --- | --- |
| 计划离职 | 查看仍在运营的账号，为每个账号选择接任人，点击「确认交接并停用」。 | 服务端在同一事务内转移这些账号、停用成员、撤销会话和待用令牌、保存回执。提交时账号清单、责任、在营状态或接任资格有变化，整体拒绝并指出受影响项。 |
| 紧急停用 | 选中成员，填写原因，点击「立即停用」。 | 服务端提交停用、会话及待用令牌撤销和停用回执。账号清单可在停权后查询。仍指向该成员的在营账号立即失去有效负责人，管理员可从回执打开待接管列表。 |
| 后续接管 | 从回执点击「去接管」，在账号台账选择有效接任人。 | 复用单账号责任命令，核对账号版本，记录接任人。未接管的账号仍在列表里。已退出运营的账号按现有生命周期展示。 |

最后一名有效组长离职时，计划离职也允许由管理员临时代管。确认时提示组长空缺，成员名册和回执显示「组长空缺，管理员代管」。管理员沿用已有管理权限，接任账号的运营仍使用原角色。最后一位有效管理员继续受停用保护。

计划离职的账号预览只需显示账号名称、平台、当前负责人和拟接任人。跨组分配要能看出组别。服务端比对完整账号集合、责任版本、在营状态及影响此次分配的组关系，并在事务内复核接任人是否仍有效。密码修改、组改名和同步状态变化无需重做预览。紧急停用根据稳定成员引用和当前权限判断，成员改密后仍可停用。预览有变化时保留仍有效的选择，要求重新确认变动项。零个账号可正常停用。紧急停用可在账号清单读取失败时独立提交。

紧急路径保留原负责人引用供追溯。对仍在运营的账号，服务端发现该负责人已停用，即按无有效负责人处理。读取、负责人展示、组长权限与账号写入须使用这条规则。待接管列表按原成员筛选，区分从未分配的账号。管理员完成分配时写一条实际责任变更。历史停用如果缺少与账号的关联，显示已知事实和可处理账号，以现存记录为准。

**例子。** 小陈有两个账号，拟交给小周和小林。如果两人都已启用，计划离职一次完成两个账号的转交和停权。如果小林仍未签收，计划提交整体拒绝。需要当场撤销小陈访问时，管理员可立即停用，再把其中一个账号分给小周，另一个留待小林启用。

## 5. 迁入发布和待补阅读量（D02 已确认）

| 记录 | 接任人能做什么 |
| --- | --- |
| 当前负责账号下的有效原生发布 | 查看并按现有规则补录阅读量。 |
| 当前负责账号下的有效迁入发布，台账账号关联明确，最新历史归属为 `matched` | 查看并补录阅读量。原发布人和来源记录保留，新增阅读量记实际填报人。 |
| 迁入发布的账号关联待核、历史归属待核或有冲突 | 由管理员核对和处理。 |
| 离职成员的历史日报 | 继续按原填报人和现有权限读取。接任人填报自己的日报。 |

发布台账列表、列表计数、导出、封面和直链使用同一发布可见条件。单条和批量补录都要验证发布可见及该账号可补录。现有的本人历史读取资格继续按原规则判断。账号再次转交后，随当前责任授予的访问和补录资格随之转移。个人日报中的发布篇数和历史归属继续使用原发布人。

账号行提供「待补阅读量」，以稳定账号引用打开发布台账的该账号待补列表。发布人筛选默认不限，避免漏掉前任的发布。保留现有待补规则。一次成功补录后，该发布从待补列表移出。若没有可补记录，显示「当前没有可补录的发布」。 [现有发布读取](../../crates/intelligence/src/ops_ledger/read/publications.rs) · [个人日报统计](../../crates/intelligence/src/ops_ledger/read/daily.rs)

## 6. 已提交的发布同步（D03 已确认）

已进入共享工单的同步按原有机器授权继续接受检查。人发起同步，工单按自己的授权和租约执行。离职和账号转交保留工单、发布范围和真实发起人。

| 交接时的同步事实 | 处理 |
| --- | --- |
| 未准入、被拒绝或尚未提交 | 无可继续执行的工单。离职者的会话失效后，拒绝其新同步和重放请求。 |
| 已接纳、仍排队或正在执行 | 仅在原有授权、租约、发布身份与执行输入条件仍满足时推进。条件失效时按现有规则阻断。 |
| 已有合格回包 | 保留实际回包和原链路，按当前发布可见范围展示业务结果。 |

精确同步允许多个请求合并到同一个尚未认领的工单。若需要停止某一任务，管理员先从同步回执核对具体工单及其他请求，再按已支持的采集控制操作处理。详细任务状态从现有同步入口查看。发布可见或可补录的权限由 D02 确定，机器同步的提交和回执权限仍按现有合同判断。 [同步准入与工单复用](../data-contracts/ops-publication-sync-001.md#2-当前决定词典) · [同步回执入口](../../apps/api/src/local_web/ops_sync_api.rs)

## 7. 实现与回执恢复

- **写入复用。** 扩展现有停用命令区分计划和紧急模式，复用账号责任命令的服务端校验和写入逻辑。停用回执记录实际操作者、目标成员、原因、时间、请求 ID 和结果。计划转交的各账号事件可引用这条停用回执。账号后续接管继续使用原责任记录。现有调用入口须落到相同规则。
- **并发验证。** 服务端从当前会话取得操作者。停权、账号分配、发布登记、阅读量补录和日报写入在事务内复核与动作有关的会话及权限。并发写入若使用离职者的旧权限，要么在停权前提交，要么在停权后被拒绝。计划交接与其他账号转交使用一致的锁顺序，接任资格和账号版本在提交前复核。
- **紧急提交独立于账号处理。** 紧急停用的成功条件只包括成员状态、会话和待用令牌撤销，以及停用回执落库。通过成员是否有效派生当前账号待接管状态。停用回执可独立查询，账号读取失败时显示「成员已停用，待接管账号暂未读取」。账号数为零只用于查询已确认的结果。
- **刷新后查同一次操作。** 提交前在当前浏览器标签页临时保留请求 ID 和原请求参数，供同一管理员在刷新后按 ID 查询。原因只填写简短业务说明。收到原回执后展示当时的处理结果，并链接当前账号台账。超时或暂未查到回执时显示「结果未确认」，管理员可以用同一 ID 和原参数重试。相同 ID 的有效重放返回原结果，载荷不同时返回冲突。确认结果后清除临时提交内容。名册的最近回执仅供回看。
- **交付范围。** 团队成员页、账号台账与发布台账沿用现有 React 和 LIDS 外壳。管理员从停用回执进入账号台账，接任人从账号行进入待补发布。新增关联使用现有停用与责任记录。变更采用增量迁移，回退保护已撤销会话、责任历史和审计记录。 [协作协议](../governance/agent-collaboration.md) · [部署手册](../runbooks/local-runtime-deployment.md)

## 8. 开发顺序与验收

先验证邀请、签收和账号分配。随后完成两种停用路径、回执恢复、待接管和 D02，再用隔离 PostgreSQL、Axum 与实际桌面 React 页面验证完整路径。

| 场景 | 通过条件 |
| --- | --- |
| 邀请已发出、过期、撤销或重新生成 | 显示真实状态。旧链接失效。仅签收并启用的成员能接管。 |
| 计划离职将两个账号交给不同人 | 两个账号与停权一起生效。旧会话失效。任一接任人失效或账号被别人先转交时，整次提交无部分结果。 |
| 紧急停用时账号预览或后续责任处理失败 | 停权回执仍可查，旧会话不能继续读写。账号查询失败有独立提示，恢复查询后可继续分配。 |
| 最后一名有效组长离职、最后一位管理员被选中停用 | 组长可停用并显示管理员代管。最后一位有效管理员受保护。 |
| 请求已提交，客户端超时后刷新，期间另一管理员也尝试操作 | 可用原请求 ID 查询同一次操作。原样重放不重复写入，另一次操作的回执不会覆盖它。 |
| 交接账号包含原生发布、已核实迁入发布、待核及冲突记录 | 从账号行进入待补列表。前两类可补录，后两类仅管理员可访问。直链、封面、导出和写入一致。 |
| 接任人给前任的迁入发布补录阅读量，账号随后再次转交 | 成功补录后退出待补列表。前任发布人保留，记录实际填报人，接任人的发布篇数不增加。基于账号责任的权限随再次转交更新。 |
| 同步已排队、执行中或已有合格回包 | 验证原机器资格仍有效时可继续推进，资格失效时阻断。保留发起人、共享工单、机器资格和回包各自的事实。 |
