# REAL-CANARY-002 · 让同一个发现面走完新的授权链

> 状态: 草案
> 最后核对: 2026-08-27（Mog 已核验 §3 十项；关键词已定为 ADHD）
> 适用范围: 一次受控的小红书搜索页 discovery，全程经过「申请 → 授权 → 准入 → 工单 → 租约 → 派发」
> 事实来源: `capture-control-contract` §12、`arc-001` 的 `first-producer-canary`、`local-001` 的 `001C-1`、`collection-monitoring-rules`、本仓库已实现的控制链代码
> 冲突时以谁为准: 用户最新确认、`AGENTS.md`、`domain-invariants.md`、采集控制合同；本文不授权 001C-2 或 001C-3

## 1. 这份 SCOPE 为什么存在

采集控制合同 §12 列了进入真实 Canary 的 7 条退出门。其中**第 5 条**是：

> 服务端能实际执行 Authorization → Admission → Work Order → Attempt/Lease → Package/ACK 的控制，而插件不能绕过。

这条门到今天为止**只在合成数据上成立过**。控制链已经写完并逐段实测（授权、准入六问、工单、租约、派发闸门），但它从未在一次真实的平台访问上被端到端执行。

本 SCOPE 只做一件事：**让一个已经获准过的发现面，原样再走一次，但这次全程经过新的控制链。**

## 2. 为什么不是 001C-2

`001C-2`（内容详情与媒体 acquisition）是 `first-producer-canary` 裁定的下一段，但它的停止条件明写：

> 没有独立通过的 Capture、媒体生命周期、私密保存/读取和删除传播合同，或没有明确的最小对象/字节预算时，001C-2 不得开始。

`media-lifecycle-contract` 在 `arc-001` 中当前状态为 **open（未回答）**。因此 001C-2 不得开始，本文也不为它开任何口子。**不把「控制链已经建好」当成「媒体可以开始」**——那正是 `first-producer-canary` 警告的「让 discovery 冒充媒体完成」的变体。

| **Need（证据需要）** | 一个当前可见的 ADHD 搜索发现面，用于确认控制链的每一段都在真实链路上留痕 |
| **Authorization（授权）** | 本 SCOPE 经 Mog 签署后，在系统内表现为一条 `collection_acquisition_authorization`（平台 xhs / 关键词 / patrol lane）与一次显式开闸 |

| **账号镜头** | Mog 本机浏览器的当前登录态。**不读取 Cookie、不注入账号、不切换身份**；登录态只作为「页面能否打开」的事实，不作为可配置参数 |

| **访问** | 结果只写入本机 PostgreSQL，只经 loopback API 读取。不出本机、不进 Git、不进普通日志 |
| **处置** | 材料按现有 Evidence 规则保留。本次不产生媒体字节，因此不涉及媒体保留策略 |

## 4. 与 001C-1 的差别（这是本次唯一的新事实）

001C-1 已经跑过（REAL-CANARY #52），它证明的是「插件能把一个发现面安全交付到本地库」。

本次**不扩大任何平台足迹**——同一个平台、同一个入口、同样 ≤20 条、同样不碰详情与媒体。唯一的差别是**路径**：

```text
001C-1：插件自行发起  → 本地接纳
本次  ：人签署授权 → 准入六问 → 工单 → 租约（有到期时间） → 闸门 → 派发 → 插件执行 → 回执
```

**新事实只有一个：控制链在真实访问上成立，且插件拿不到未经授权的任务。**

## 5. 证明目标（可证伪）

以下每条都必须由真实数据库行或真实 HTTP 响应支持，静态文档、mock 与「API 返回 200」都不算：

1. 闸门关闭时，插件请求派发得到 `execution_gate_closed`，**且拿不到任务规格**；
2. 闸门开启后，插件拿到的任务规格 `source=scheduled`、`riskPolicy=server_authorized_leased`、`maximumQuota=20`，且 `capabilitiesRequested` 恰为 `["discovery_search"]`；
3. 插件自行提交 `source=scheduled` 的任务被拒（HTTP 403），**证明插件不能自签派发**；
4. 租约到期后，同一任务不再被派发，且租约留下 `expired` 而非静默消失；
5. 本次实际入库条数计入该工位当日额度，页面与准入读到同一个数；
6. 若实际可见少于 20 条，已取得材料仍入库，页面如实显示实际观察范围与缺口，**不把未观察位置伪造成不存在**；
7. 全程没有产生任何媒体字节、OCR/ASR 记录或详情记录。

## 5.1 开工前必须先修的一个缺口（2026-08-27 查实）

核对语料库既有 41 张卡时查到：4 个发现面采集包中，有一个对应的任务规格写着 `maximumQuota: 10`，而插件交回的包是 `observed 20 / acquired 20`。**执行端超出了任务给的上限，服务端照单全收。**

追查确认：`maximumQuota` 目前**只在读投影里被用来显示**（`producer_runtime.rs` 的 `coverage_maximum_quota`），**提交路径上没有任何校验**。页面因此显示「20/10」——一个可见数大于上限的组合，它在自陈边界，而那个边界并未被执行。

这与合同直接冲突：

> 止损条件是工单的一部分，不允许执行端自行放宽。
> lease 只允许当前工位在有效期内进行规定访问，不能修改 Work 的 lane、目标、观察身份或止损边界。

**这个缺口必须在本 Canary 前修掉**，否则 §5 的证明目标 2（「`maximumQuota=20`」）毫无意义：插件返回 40 条也没有任何东西会拦。修法是在提交路径上把「acquired 超过任务 `maximumQuota`」判为拒绝或隔离，而不是静默接纳。

既有那 41 张卡不因此作废——它们是安全取得的材料——但**其覆盖显示应当如实标出「本次超出了任务上限」**，而不是把 20/10 当成正常读数。

## 6. 停止条件（任一成立即不得触发真实访问）

- 插件实际加载版本与 `releases/` 中的包无法核对；
- 闸门未由人显式开启，或开启时未写明本 SCOPE 编号；
- 工位无在岗安装，或当日额度已触顶；
- 存在任何生效中的风险暂停；
- 页面或 API 无法显示 Coverage；
- 本机 PostgreSQL 未就绪；
- **§5.1 的配额校验缺口未修**。

## 7. 明确不授权

- 不授权 001C-2（详情与媒体）、001C-3（OCR/ASR）；
- 不授权 `deep_archive` lane、不授权创作者深度建档；
- 不授权任何自动巡检、定时调度或连续运行——**本次是一次性的，闸门 30 分钟后自动关闭**；
- 不授权外部 Agent 读取、不授权部署、不授权抖音。

## 8. 未证明边界

本 SCOPE 即使全部通过，也只证明「控制链在一次真实发现面访问上成立」。它**不**证明：媒体链路、OCR/ASR、详情采集、巡检节奏、爆款判定、Coverage 在详情层的语义、平台兼容性、长期稳定性，也不证明 Linggan 已可用于日常真实研究。
