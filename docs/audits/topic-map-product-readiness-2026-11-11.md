# 主题图谱：产品、UI、UX、功能与上线准备度审查

> 状态: 一次性报告
> 最后核对: 2026-11-11
> 适用范围: Intelligence `/topics` 桌面页面、相关前后端、研究入口及运营交接；真实数据重点为 ADHD 领域。
> 事实来源: 本机 3001 页面走查、只读 HTTP 回包、当前部署源码、产品与设计决策、隔离源码测试。
> 冲突时以谁为准: 当前运行与 owning code 决定实现事实；已确认产品决策决定目标。本报告建议尚未成为批准的设计或部署许可。

## 1. 结论

主题图谱已经有较多真实底层能力，但尚未成为可持续使用的业务工作台。当前“半瘫”主要由五个问题叠加造成：

1. **研究前置条件没有就绪。** 四阶段任务全部关闭，模型与预算未配置；页面只显示失败与待完成为零，没有解释无法开展研究的原因。
2. **主题目录与研究结果为空。** ADHD 有 3,274 篇材料，主题定义、候选方向和研究运行记录均为零；界面缺少清晰的首次建立路径。
3. **研究操作停留在技术控制面板。** 从数千篇作品逐个勾选，提交后手动刷新阶段，再手动刷新图谱，用户需要自行理解执行过程。
4. **下游没有闭环。** 人工备选有保存和导出能力，但没有进入运营选题池；我方覆盖也没有接通完整运营发布事实。
5. **读取性能和加载反馈不稳定。** 热读取较快，但真实走查出现长等待，视图切换期间主区域被加载状态替换。

推荐保留现有主题概览、五阶段旅程、共享材料与来源资格体系，在其上完成业务闭环。上线工作应围绕“从材料中确定可做方向，并把有依据的选题交给运营”，不要以增加图表数量或通过前端测试作为完成标准。

## 4. 优先问题清单

优先级定义：P1 为正式可用前必须解决，P2 为重要的产品与体验完善。这里不把所有问题称为 P0，也不声称存在数据丢失或安全事故。

### P1-01：研究不可运行，页面没有给出原因

**事实：** 四阶段均未启用、未绑定模型、预算未配置；页面只提供“去 AI 设置”及失败/待完成数字。

**影响：** 用户无法判断没有结果是没运行、正在等待、配置缺失还是研究失败。通过逐个尝试按钮寻找原因会产生认知负担。

**建议：** 页面显示明确准备度：可研究材料范围、四阶段模型/预算/许可状态、当前阻塞原因和直达修复入口。未就绪时仍允许阅读材料，研究按钮说明具体原因。不能仅把 disabled 按钮变成 enabled。

**验收：** 分别覆盖未配置、关闭、材料不足、可开始、等待、运行、失败、部分完成、完成；每个状态给出准确下一步。

### P1-02：首次建主题目录没有清晰任务路径

**事实：** 目录、候选均为零；左栏只说明“尚未建立主题定义”。结构调整依赖已有叶主题，只支持合并/拆分，不能解决空目录。研究候选的代码存在，不等于首次业务流程已经可用。

**建议：** 沿用既有方向经营决策，提供“整理首批方向 → 查看依据与边界 → 人工确认 → 归入目录”的路径。方向必须有定义、正例、反例/边界和来源。目录初始数量应服务区分能力；既有决策中的 20–40 个方向是设计参考，不能为凑数制造方向。

**验收：** 空领域和已有材料但无主题两种起点均可完成；候选、正式方向、未归材料可区分；能退回修改，不靠开发者手工写库。

### P1-03：研究弹窗无法适应真实材料量

**事实：** 3,274 篇作品被直接渲染成复选框长列表；没有搜索、分页、选中项托盘。开始与刷新按钮位于整个列表之后。研究入口传入 `snapshot.works`，并非材料搜索后的显式选择。后端还有最多 50 个窗口的限制，前端只解释最多 10 篇。

**影响：** 找作品、确认范围、启动和查看进度都困难。作品数不能充分说明实际处理量。

**建议：** 材料列表勾选进入研究；弹窗保留可搜索/分页的追加入口、已选项与范围说明、材料缺口和窗口预估。固定操作区；明确用户此次提交哪些作品、是否包含评论及哪些材料仍缺失。费用未知时显示未知，不能伪造估算。

**验收：** 在当前 3,274 篇规模完成筛选、选择、移除、提交；不会把视图之外的作品暗中加入；超过处理边界在提交前解释。

### P1-04：提交、进度、结果更新没有连贯反馈

**代码事实：** `TopicResearchFlow.start()` 解码 runRef 后只设置提示，不纳入任务列表；进度靠手动刷新，完成后还要求手动刷新图谱。研究状态的 commandRef 只在组件 useRef 内保存，关闭弹窗会丢失未确认请求身份。

**影响：** 提交成功后用户可能看不到任务；关闭弹窗后无法沿用同一未确认请求。重复执行风险属于代码推断，本轮没有发起付费请求验证。

**建议：** 提交回执立即进入任务列表；展示作品级进度和阶段详情；任务完成后刷新受影响结果。保存未确认命令身份，并从服务端回执恢复；异常时先核对是否已提交。标题不要把“成功阶段数”称作“接纳数”，应区分阶段、作品、方向。

**验收：** 提交后关闭/重开、刷新页面、断网、取消、部分阶段失败均可恢复；不因未知回执自动另发新请求；完成结果能从任务进入并定位依据。

### P1-05：研究结果与既有内容理解缺少明确消费边界

**事实：** 主题投影读取 `linggan_topic_research_result`；单篇分析写入 `linggan_note_analysis_result`。已有单篇分析不会自动成为主题结果。研究 v6 已有场景、旅程与角度等输出，不能误判为这些后端全部未开发。

**建议：** 先明确主题需要消费哪些已接受的事实及其版本。复用当前共享材料和底稿；如果接入单篇分析/Content Card，必须新增显式映射与来源/版本资格检查。不要把尚在实验或未验收的统一理解方案当成已可用依赖，也不必等待它重做整个系统后才能恢复主题基础功能。

**验收：** 同一材料的已有分析、主题研究与最终归属能解释相互关系；不重复声称“已分析”，不把旧版本或不合格结果自动视为当前事实。

### P1-06：备选不能进入运营选题池

**事实：** 人工表单及“我的备选”文案明确说明“运营选题池尚未接通”；现有能力主要是保存、复核来源、导出交接。

**建议：** 补齐一个明确动作“加入选题池”，复用运营的选题实体与入口，保留来源作品、主题定义版本、角度、要回答的问题、边界和人工说明。返回创建/已存在的回执与打开链接；备选和正式选题的状态要可追踪。

**验收：** 一条真实来源材料可从图谱进入选题池并被创作读取；重复提交不生成重复选题；编辑选题不改写原始证据。来源撤回或变化时，下游能看到限制。

### P1-07：读取波动与大回包削弱可用性

**实测：** 一次 summary 完成约 27.73 秒；后续热读取 summary 0.386 秒、overview 0.762 秒。另一次服务 `/health` 0.23 秒返回正常，但 summary 在 12 秒读取上限内未返回，页面仍处于加载状态。这不是统计意义的 P95，也没有证明所有慢请求属于同一个原因。

**数据量：** summary 仅 12 篇作品却约 1.34 MB，仍携带 1,517 个来源统计项；overview 为 3,274 篇，约 6.50 MB。这里是读取到的 JSON 字节数，不是浏览器压缩后传输量。

**代码风险：** 每次读需要来源版本检查；缓存失效时在全局构建锁内重建。来源指纹扫描当前 schema 的大量表；summary 截取发生在完整投影构建之后。已有背景预热和缓存优化，但没有把完整构建成本消除。

**建议：** 先记录慢请求的 DB/构建/资格复核耗时与失效原因，再缩小不必要读取。将首屏摘要、分页材料、来源分布、详情分开按需获取；保留准确全量统计。对资格撤回仍需立即生效，不能靠延长缓存并展示失效证据来换速度。读请求提供明确超时、重试和可恢复状态；视图切换尽量保留仍合格的现有内容。

**验收：** 分别测首进、缓存命中、失效重建、切领域、带筛选、后台有写入时的读取；报告中位数及慢样本。建议桌面正常读取首屏目标 2 秒内，超过 5 秒给出可操作反馈；具体性能门槛在实施时用本机基线确认。

### P1-08：材料覆盖口径不足以支撑研究决策

**事实：** 可读 3,255 中有 863 篇没有正文证据片段。阅读首条作品时，标题和 10 条评论可读，原文仍显示无可读取片段。

**建议：** 将“材料存在”“有正文/媒体文本”“底稿完整性”“研究覆盖率”分别表达。底稿缺口先定位到来源缺失、抽取缺失、资格限制或当前消费者未取用；不默认重采或重跑 OCR。原文阅读应复用共享底稿，并保留作者内容与评论归属。

**验收：** 从完整材料、仅标题、纯图片、视频、评论丰富、来源受限等不同状态分层抽样；随机样本判断普遍性，已知难例只做回归。

### P2-01：零结果状态仍展示大量“完成态”界面

旅程以五个“0 / 0.0%”为主要视觉，“待分析 3,255”放在次要区域；内容格局多个空块重复；新方向无候选却仍突出结构调整。文字已有边界提醒，这是优点，但主视觉仍容易误导。

建议主区域先说明“尚未形成旅程结果，待处理材料 3,255”，提供下一步；保留五阶段结构作为说明或次级预览。有结果后恢复完整图谱。不能把未知改成零，也不需要删除用户已确认的五阶段设计。

### P2-02：信息层级和材料列表影响桌面效率

首屏上部统计与点赞分布占据较多空间，“昨日新增”等长期未知位置没有帮助用户完成下一步。材料行高、左右距离和大段文本使首屏可扫读条数偏少；主题工作缺少视觉主操作。研究弹窗的勾选框与标题呈纵向分离，滚动量过大。

建议保留现有 LIDS 视觉语言与概览统计，压缩常驻占用，使用清楚的研究准备/覆盖状态。材料行稳定呈现标题、作者、可读状态、关键表现和就近操作；复用共享材料阅读组件。不要只更换字体、颜色或装饰图形。

### P2-03：功能概念与设置口径漂移

- “主题 / 方向 / 讨论 / 场景 / 角度 / 备选 / 选题”需要明确实体关系和动作后果。
- 当前样本爆款规则为点赞 ≥100；较新的主 Job 决策写外部 ≥200、我方阅读 ≥5,000。可能是后续保存配置，不能在审查中直接改回；上线前须统一显示保存值、适用对象与规则来源。
- 我方账号当前由 topic-map 自身身份表决定，发布覆盖基于采集作品；需要与运营账号/发布事实建立明确映射，不能把未采集当未发布。
- 多份历史计划、旧研究合同与新四阶段同时存在。实施入口应明确当前责任与被替代项，历史文档保留。

### P2-04：生产工作区仍暴露较多调试概念

离线预演与真实研究并列，原始版本号、窗口阶段与部分错误码直接进入普通工作流；通用关闭按钮的无障碍名称在原文、备选弹窗也叫“关闭对话框，保留研究任务”。

建议保留诊断信息但放入详情，普通状态用作品与任务表达；离线预演明确独立环境；不同弹窗给出准确名称。已有 heading、button、label、status 和原生 dialog 基础可继续复用。完整键盘顺序、焦点恢复和对比度尚未做系统验证，不能声称 WCAG 通过。

## 5. 功能与 UX 推荐方案

### 5.1 页面服务的主要任务

用户进入主题图谱，应能回答四个问题：

1. 这个领域已经观察到哪些内容，研究覆盖到哪里？
2. 哪些稳定方向值得经营，它们的依据和边界是什么？
3. 同一方向下，哪些场景、问题、讲法有材料支持，我方覆盖在哪里？
4. 下一篇准备做什么，怎样携带证据交给运营与创作？

主题图谱负责方向与研究依据；运营选题池负责具体选题的经营；创作工作台负责内容生产。三个模块共享来源，不重复维护三套材料事实。

### 5.2 建议保留并完善的布局

- 左栏：领域主题树、待归材料及明确的建立/整理入口；目录版本与结构维护进入次级操作。
- 主区顶部：当前方向、研究准备度/覆盖度、一个明确下一步；现有统计保留但降低常驻高度。
- 主区：保留“主题概览 / 用户生命旅程”。概览各视图围绕材料、研究发现、表现与来源、我方对照组织；无结果时提供有动作的空态。
- 研究面板：已选作品、准备度、处理范围、任务进度、结果回执。调试明细可展开。
- 结果阅读：方向定义、场景与问题、支持/挑战/边界证据、来源原文、人工确认/修正。
- 下游动作：保留备选、加入选题池、查看已进入运营的选题。状态和回执可回查。

下一阶段先制作一个基于真实数据形状的桌面交互 Demo，覆盖无目录、处理中、已有结果三种状态。Demo 用于确认任务路径与视觉关系；业务验收仍必须用真实接口。

## 6. 实施顺序与上线门槛

| 批次 | 交付内容 | 收口条件 |
|---|---|---|
| A：恢复可操作基础 | 研究准备度、首次目录路径、可搜索分页选材、持久任务回执；定位长读取；修复加载恢复 | 用户能看懂阻塞并完成一组明确材料的选择；无数千复选框；失败/未知回执可恢复 |
| B：完成一条真实研究链路 | 配置四阶段运行条件；小批真实材料→研究→候选/归属→人工确认→主题与旅程展示 | 不靠手工写库；每项判断可回原文；无评论冒充作者结论；失败和材料缺口不被掩盖 |
| C：接通经营闭环 | 方向下保留角度→加入运营选题池→创作可读取；我方账号与发布事实口径统一 | 具体选题及冻结来源可追踪；重复提交不重复创建；不把保存当发布 |
| D：全页面与规模收口 | 内容格局剩余能力、来源/旅程/我方视图完整验收；桌面视觉、查询规模、错误恢复与文档整理 | 当前材料规模可用；各可见功能均有真实结果或准确空态；完成发布及目标运行环境回归 |

其中 A 与 B 应紧邻推进，尽早形成纵向真实链路。A 不是完整上线；B 也不能替代 C、D。可拆小 PR 交付，但不能把“第一批已部署”描述为整个页面完成。

建议的完整上线验收对象是一项用户任务：选择领域和材料，建立/确认方向，查看依据与旅程，形成有边界的选题，进入运营并被创作读取。至少同时覆盖正常流程、部分材料不足、部分研究失败和重开恢复。最终内容质量与桌面体验由 Mog 判断。

本轮不建议全库运行。先用覆盖不同材料状态的有界样本证明链路与语义，再确定增量范围和费用边界；已获得的回包优先离线复核，避免反复调用模型修补前端或解析问题。

## 7. 工程复用与风险

优先复用四阶段 executor、冻结输入与配置、结果来源资格、结构影响预览、幂等命令、已有材料读取和运营选题实体。它们是已有资产，不能因为当前页面难用就全部推倒。

前端主要复杂度集中在 `engine.tsx`、`topicOverview.tsx`、`topicDialogs.tsx` 和页面样式；React 内混合较多事件委托与状态控制。只围绕本轮更改抽出研究状态和列表职责，避免先做全量框架改造。共享底稿或运营身份的变化可能跨模块，应按 L3 做影响分析；局部布局、状态文案与分页选择可独立交付。

性能修复必须保持来源资格：禁止将已撤回、权限变化或不再可复核的内容作为仍有效依据。不同版本结果可以保留历史，但不能悄悄参与当前覆盖统计。
