## 1 · 结论

- **整体迁入**：账号管理、发布记录、每日数据、目标、总览、导入导出、四种角色与人员分组。**等选题池上线后一起重做**：团队执行、管理周报。**不迁**：「运营中心」，它是系统日志，不属于运营模块。
- **迁的是用户任务、已验证的页面和业务规则；实现全部在 Linggan 重写**。旧 Prisma 表结构、旧 ID 语义、旧回流引擎和旧选题库链接都不迁。历史记录经导出文件一次性迁入新表，并保留来源。
- **三条规则改变**（Mog 确认）：
  - 帖子由系统每天从我方账号主页自动发现，运营只补阅读量；
  - 阅读量每篇必填，发出满 7 天未填就提醒，≥5000 自动记为爆款；
  - 有效发布改由系统确认。
- **Linggan 要新建四件事**：登录与对外访问、我方账号身份与自动发现、阅读量填报记录、账号的业务领域归属（含暂时没有账号的卢叔数学领域）。

## 5 · 能力继承四分类

### 5.1 直接继承

用户任务、已验证的交互和业务规则原样保留，实现仍在 Linggan 重写。

| 能力 | 继承内容 |
|---|---|
| 发布记录页 | Mog 确认的最终版。列依次为：日期、平台、标题、数据状态、发布链接、媒体、正文、账号、运营人、操作、浏览量、点赞、收藏、评论、封面点击率、复盘。表头指标为：运营中账号、本月发布、有效发布、本月加微、本月爆款。保留运营人页签、总数据/抖音/小红书切换、新增/编辑/删除、批量选择和重复链接标记 |
| 账号管理 | 平台、账号名、状态（使用中/违规停用/养号中）、是否保留、健康度（观察/低效/暂停）、负责运营、负责人、粉丝数、主页链接、设备、IP 属地、备注 |
| 每日数据 | 每人每天一行；手填链接打开数和加微数；发布数由发布记录自动算，不手填 |
| 目标 | 周、月加微目标 |
| 总览结构 | 五块：加微目标与自动结论 / 漏斗、转化率、爆款数 / 长趋势、每人每日产出、今日必须处理 / 运营人排行 / 平台占比与热力矩阵 |
| 业务口径 | 转化率 = 加微 ÷ 链接打开；业务日按北京时间切分；账号停用不删历史；导入兼容现有表格列名 |
| 角色与分组 | 主编、资深运营、一线运营、实习生四种角色；人员分组 |

### 5.2 语义继承、实现重写

| 旧实现 | Linggan 做法 |
|---|---|
| Prisma 四张运营表与人员分组 | 在 Linggan 新建表，不搬旧表结构和 migration。旧记录号只作为来源编号保存 |
| 「数据状态」列（显示回流同步状态） | 显示系统确认状态（已在主页看到 / 本次未看到 / 未检查）和阅读量填报状态（待补 / 已填） |
| 「有效发布」= 回流成功 | 系统在我方主页确认看得到。自动发现上线前显示「未接入」，不能显示 0。迁入的旧标记按旧含义保存为历史，不换算成新口径 |
| 「本月爆款」= 手填爆款数之和 | 按单篇阅读量 ≥5000 自动计数，表头与总览同一口径 |
| 「复盘」列：有关联选题时显示「查看选题」（指向旧选题库），历史上只有 1 条有值 | 列保留；选题池上线后指向该帖对应的选题（DEC-0009：按标题识别复用），之前显示「—」 |
| 「同步数据」按钮（触发旧回流） | 自动发现上线后改为「立即检查我方主页」，受采集额度约束；之前不可用，并说明原因 |
| 今日必须处理的执行状态（未完成 / 待同步 / 数据异常 / 需复盘 / 可表扬） | 按新口径重定规则：「待同步」改为「待补阅读量」或「待系统确认」，「可表扬」不再读手填爆款数。标签集在总览交付的页面规格里确认 |
| 运营人页签（按发布人姓名） | 新帖按账号归属的负责运营归人；历史记录保留原发布人 |
| 数据范围（一线运营默认只看自己或本组） | 作为权限表的默认提案，做登录时请 Mog 确认 |
| 导入导出 | 重写，列名别名保持兼容 |

### 5.3 Linggan 新增

| 能力 | 说明 |
|---|---|
| 登录与对外访问 | 每人一个账号；经 Mac mini + Cloudflare 对外（部署形态见 [`collection-monitoring-rules.md`](../product/collection-monitoring-rules.md)）；影响全局的改动按角色限制 |

### 5.4 明确废弃

- 发布记录里没人填过的 10 个栏目：选题、选题关键词、配图、帖子类型、内容定位、单篇引流/加微、爆点分析、问题分析、备注、关联选题。填写率均为 0–0.5%，历史值不迁。
- 每日手填的「当日爆款数」，以及用它求和的爆款口径。旧值（5 月 2、6 月 3、7 月起 0）只在本报告留档，不迁。
- 只写在规格文档里的「超过基线 3 倍」「单篇超过 1 万」两种爆款口径，由 DEC-0009 的 ≥5000 统一。
- 旧回流引擎、旧同步任务，以及指向旧选题库的链接。
- 「运营中心」（系统日志）。
- 旧 Next.js / Prisma / better-auth 实现、旧表结构和旧 migration。

### 5.5 延后

团队执行和管理周报这次不迁。它们的旧逻辑依赖旧选题库，以及填写率为 0% 的单篇引流、单篇加微，等选题池上线后一起重做（④）。

## 6 · 必须守住的不变量

1. **不两边同时录**。切换前，内容工作台是唯一录入处，Intelligence 里的运营数据只读；切换后只在 Intelligence 录入（`AGENTS.md`：禁止双写）。
2. **历史不推断现状**。迁入的「使用中」「有效发布」等只说明迁入时旧系统里是这样，不证明账号现在可用、帖子现在可见。
3. **未填不等于 0**。没填阅读量的帖子算「待补」，不算「没爆」，也不计入命中率的分母。
4. **没看到不等于删了**。主页检查只说明当时看到了或没看到；「本次未看到」不能直接判为删除或违规。
5. **两把尺子不混用**。我方帖子看阅读量，外部帖子看点赞（DEC-0009）；我方帖子不进入外部爆款候选。
6. **人工写操作按请求记回执**。补阅读量、增删改发布记录、账号和每日数据都按请求留回执：重试不重复，多人同时改不互相覆盖，无变化的请求也留回执。
7. **对外开放后全部页面都要登录**。高赞原话库的评论原文仍只给内部人员看（DEC-0009 例外），其余原文约束不变。
8. **导出文件和真实运营数据不进 Git**。导入工具只读本机文件，测试只用合成数据。

## 7 · 风险与未证明边界

- **采集额度**：自动发现要每天巡查 60 个小红书主页，再给新帖补详情。规则文档规定单工位每天 200 篇笔记的上限，实际会占多少，要在自动发现交付开工前算清楚给 Mog 看。
- **抖音**：历史 759/761 条是短链；插件能不能巡查抖音主页、短链能不能解析，都还没核实。
- **13 个账号没有主页链接**，补齐之前没法自动发现。
- **51 条小红书记录**（短链或其他格式）不联网就对不上作品编号。
- **历史标题只有 42%（近 90 天 27%）**：历史上的复用关系只能在有标题的记录里识别；命中率的「过去水平」只能用有阅读量的 688 篇小红书记录来算。
- **阅读量只有账号本人看得到**，系统没法核对运营填的数。
- **真实发帖量**要等自动发现跑起来才知道，约 7 倍的差距目前只是 Mog 的口径对比记录。
- **人员对照没做**：周/月目标和人员分组不在导出里；运营人姓名 9 个，负责人编号 10 个，不是一一对应；每日数据历史上出现过 12 个运营人。迁移时要逐一对照，已离开的保留为「历史运营人」。
- **每日发布数**：9 月旧值 553，按现存记录重算是 388。迁入后按现存记录重算，对账时向 Mog 说明这个差异。

## 8 · 本报告不证明什么

- 不证明 Linggan 已经具备任何上述能力，也不授权实现、migration、部署、真实采集、共享库写入，或对内容工作台的任何改动。
- 不证明旧数据真实、完整或有代表性：填写率、阅读量和发帖量都只是导出当时旧系统里的样子。
