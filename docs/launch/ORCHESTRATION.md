## 4. 波次

默认同时写代码的不超过两名（含协调者），这是协作协议的上限。

| 波次 | 并行的包 | 进入条件 | 结束标志 |
|---|---|---|---|
| 1 | L0、L1a；U1 与 D1、D2 可由另一名只读或文档角色同时做 | 本文合入 | L0、L1a 的 PR 可审 |
| 2 | L1c、L1d | L1a 合入 | 两个 PR 可审 |
| 3 | L2a、L2b | L1d 合入（L2b 可在波次 2 期间用样例快照先行） | 两个 PR 可审 |

| 5 | G2 验收 | L2b、L2c 合入；本机运行库已迁移并部署 | Mog 验收 |

## 5. 共享文件规则

以下文件同时被机会卡工作包和本线修改，冲突风险最高：

- `scripts/local-runtime.sh` 的迁移列表
- `apps/api/src/local_web/full_schema_fixture.rs`
- `crates/intelligence/src/ai_foundation.rs`（`TaskKey`）
- `crates/intelligence/src/ai_foundation/executor/service.rs`
- `crates/intelligence/src/lib.rs`

规则：

1. 迁移编号不提前占用。开发时用占位编号，合入前同步主线，取当时的下一个，再更新两处装配。
2. 改共享装配文件的包，一次只合入一个；后一个在前一个合入后重新同步再送审。
3. 不移动、不重命名机会卡模块里的任何文件。统计函数直接调用，见[勘察记录](RECON.md) 2.3。
4. 发现需要改动别的工作包正在改的文件时，停下并写入 `QUESTIONS.md`，不自行合并对方未合入的成果。

## 6. 分支、目录与记录

| 项 | 约定 |
|---|---|
| 分支 | `<agent>/content-lens-<包号小写>`，例如 `codex/content-lens-l1a` |
| worktree | `.worktrees/content-lens-<包号小写>/`；不在共享主目录里改代码 |
| 一个包一个 PR | PR 描述用机会卡手册附录 C 的模板，写明依赖的现有符号及出处 |
| 进度 | 每个包结束时在本目录的 `PROGRESS.md` 追加一段：做了什么、验证命令的实际输出摘要、未验证的边界 |
| 疑问 | 写入本目录的 `QUESTIONS.md`，把包标为阻塞；不“先按合理假设写一版” |
| 勘察 | 用到 `RECON.md` 里没有的现有符号时，先补进去再引用 |

### G1 的判定

Mog 已认可 2026-11-13 的手工标签，它们因此成为人工认可的参照。G1 用它们代替再抽看 30 条：

- 产品里的复标一致性：各主维度 kappa ≥ 0.75。
- 产品标签与参照标签的一致性：时刻与给什么两个维度 kappa ≥ 0.70。
- 两项都达到即通过。任何一项不达到就停下，把差异最大的取值对列给 Mog，由他决定改提示词、换模型或调整体系。

## 10. 给外部 agent 的开工说明

把下面整段交给执行 agent。每个包开工时，把“本次工作包”一行换成具体的包号。

```text
你要在 Linggan Intelligence 仓库里实施一个工作包。先读，再动手。

必读，按顺序：
1. AGENTS.md —— 协作、分支、worktree、安全的硬规则。
2. docs/launch/ORCHESTRATION.md —— 你的包的范围、依赖、车道、共享文件规则。
3. docs/launch/06-content-lens-playbook.md —— 唯一规格来源。读完第 1、2、3 节，再读你的任务卡和它引用的附录。
4. docs/launch/RECON.md —— 现有代码的事实。里面没有的现有符号一律视为不存在；要用就先补勘察。
5. docs/launch/DECISIONS-REQUIRED.md —— 已裁定的事项，不要重开。
6. docs/opportunity/playbook.md 第 3 节 —— 防幻觉工作协议，在这里同样有约束力。

本次工作包：<包号，例如 L1a>

工作方式：
- 在独立分支和 .worktrees/ 下的独立 worktree 里工作，不在共享主目录改代码。
- 开工先记录现有测试的失败基线。
- 迁移只在隔离库里跑；不碰本机运行库，不调用真实模型，不读取我方笔记正文。
- 遇到规格与代码现实冲突、需要新依赖、需要改别的工作包正在改的文件，立即停下，写进 docs/launch/QUESTIONS.md，不要自行假设。

- 结束时在 docs/launch/PROGRESS.md 追加一段。

完成的标准是 ORCHESTRATION.md 里该包“完成的证据”一栏，以及手册任务卡的验收标准。测试通过不等于完成；不得为了通过而修改测试或放宽断言。
```
