# 架构与 AI 手册

> 状态: 草案
> 最后核对: 2026-11-13
> 适用范围: 内容理解引擎、AI 任务的统一形状、工程结构的现实与建议、上线前必须解决与不必解决的事
> 事实来源: 2026-11-13 对 `crates/`、`apps/`、`database/migrations/` 的只读走查与本机库模型调用账本的聚合查询；[Content Card 合同](../data-contracts/content-card.md)；[统一内容理解规格](../product/unified-content-understanding-v1.2.md)；[DEC-0011](../decisions/0011-ai-generation-one.md)
> 冲突时以谁为准: 真实代码、合同与运行结果；Mog 最新明确决定；本文是建议

## 1. 总体判断

【判断】Rust 加 PostgreSQL 的模块化单体、React 前端、插件作为采集执行端，这个选择是对的，不需要动。问题不在技术选型，在于每一层都按最强的治理强度建设，重量和实际使用量不匹配。本文的建议几乎都是“少做”和“收口”，不是“重构”。

## 2. 内容理解引擎

### 2.1 三层的职责

| 层 | 现在实际是什么 | 位置 | 建议的一句话定义 |
|---|---|---|---|
| L0 | 材料就绪检查；领域归属继承自采集目标 | `crates/evidence/src/research_dossier/readiness.rs` | 这篇作品具备被理解所需的材料 |
| L1 | 一次调用产出 Content Card 的 Core | `crates/intelligence/src/ai_foundation/content_understanding.rs`、`executor/service/content_understanding.rs` | 一篇作品、一份材料快照、一个方法版本，一份 Core |
| L2 | 按问题手动深化，追加到 Deep | `content_understanding/generate_deep.rs`；接口在 `apps/api/src/local_web/content_understanding_api.rs` | 针对一个具体问题，在已有 Core 上追加有依据的发现 |

【事实】L0 的说法有三个版本：Mog 口述是“质量与领域筛选”，产品规格写“只判断材料就绪，不做第二次语义领域筛选”，合同写“通过 L0 领域和材料质量筛选”。实现与产品规格一致。

【事实】ADHD 领域 2,749 篇有详情的作品里，标题加正文命中 ADHD 相关词的占 68%；32% 的文字不足 30 字。真正跑题的比例未知。

【判断】先把三处文档改成同一句话（见待裁定事项 DR-03）。是否需要相关性筛选，等 L1 放量后直接看卡片的主议题分布就知道了，不必先建一层。

### 2.2 L1 的形状是对的

【事实】L1 的流程：冻结输入、一次调用、结构校验、程序绑定来源与版本、文字引句逐字核对（`crates/intelligence/src/content_understanding.rs` 的 `accept`）。73 张成功的卡里有 1,273 条逐字核验的文字依据和 76 条标为模型识读的图片依据。

【判断】这是全项目最值得保留的一段设计。新的 AI 任务都应当照这个形状做，见第 3 节。

### 2.3 失败

【事实】102 次请求里 29 次失败：

| 原因 | 次数 | 观察 |
|---|---|---|
| 供应商失败 | 11 | 这些请求的平均输入约 11.9 万 token |
| 结构不合格 | 9 | — |
| 文字引句不逐字 | 7 | 一条引句不符，整张卡被拒 |
| 主议题或依据来源不合格 | 2 | — |

失败调用消耗了约 40% 的输入 token。

建议按下面的顺序处理，每一步都先看再改：

1. **超大输入**：先查这 11 篇是什么（长视频转写的可能性最大）。给输入设一个明确上限，超过的标为“材料过大，待处理”，不发起调用也不计为失败。
2. **引句不逐字**：先把 7 个案例里不符的那条引句对应的单元找出来，看它是不是这篇的关键内容。如果多数是次要单元，再考虑“只丢该条”；如果是关键单元，改为带着校验意见重试一次。直接放宽会削弱证据保证。
3. **结构不合格**：核对是否已经把完整结果规范作为模型可见输入（切片 A 修过同类问题）。

### 2.4 成本

【事实】实际模型返回名为 `deepseek-flash`；L1 输入中位数 2.5 万 token，90 分位 5.7 万，最大 36.9 万；平均耗时 35 秒；缓存命中 640 / 425 万 token；账本里的费用字段为空。

【判断】按第三方页面所列的价格量级（未核对官方价目），全量 L1 的费用是几十美元级别。钱不是瓶颈。所以不值得为省 token 做任何设计；值得做的只有一件小事：把价格填进账本，让系统自己知道花了多少。

### 2.5 质量评估

【事实】库里没有任何人工判定或评测结果的表。多轮评估的历史以叙事形式写在合同文档里；验收靠 Mog 通读样本；其间评判口径改过一次。

【判断】这正是“标准在评分过程中才成形”的典型情况。先存人工判定，再定规则。

最小做法：

- 冻结 50 篇左右的评测集，材料快照固定。
- Mog 对每张卡的每个知识单元给一个判定：对、错、无依据、遗漏了关键点。判定存成数据文件，放私有目录。
- 每次换提示词或模型，重跑并与判定对比，输出一张差异表。
- 这件事等 L1 有第二个下游时再做。在那之前，Mog 通读样本已经够用。

### 2.6 Content Card 的消费

【事实】读卡的只有两处：底稿展示、主题研究（`topic_map_research/source.rs`、`topic_research_automation/`）。评论研究、创作、机会卡不读。

【事实】仍在代码里的旧单篇路径：`note_analysis`、`note_interpretation_offline`，以及任务键里的三个 `legacy_*`。

【判断】“一次提取、多次消费”目前是一次提取、一处消费。让它成立的办法不是推广，而是出现第二个真正需要它的读者；最自然的是外部作品对照（内核手册第 7.1 节）。旧路径按 DEC-0011 的约定在专门的清理 PR 里退役，不与新功能混在一起。

## 3. AI 任务的统一形状

任何新的 AI 任务，包括回溯看板的归纳和标注，都按下面七步做。它是对 L1 现有做法的归纳，不是新框架。

| 步 | 要求 |
|---|---|
| 1 冻结输入 | 输入是一份可哈希的清单；同样的输入哈希不重复调用 |
| 2 最小输入 | 只给完成任务必需的字段；会污染判断的字段（例如结果数据）在构造输入的代码里就拿不到 |
| 3 一次调用 | 一个任务一次调用；需要多步时拆成多个任务，各自可重跑 |
| 4 结构校验 | 输出先过结构规范；不合格即丢弃并记原因，不当作“无” |
| 5 程序绑定 | 身份、版本、来源、哈希由程序填，不接受模型给的 |
| 6 可核验的依据 | 凡是能逐字核对的就逐字核对；不能的明确标为模型判断 |
| 7 版本化结果 | 结果行带方法版本、提示词版本、模型配置、输入哈希；只追加 |

新任务需要提供的只有四样：输入构造函数、结果规范、校验函数、结果表。队列、准入、额度、回执复用 `ai_foundation` 现有的。

【事实】`ai_foundation` 是 intelligence crate 里最大的模块（非测试约 1.5 万行），留存的调用账本约 190 条。

【判断】不要再给它加新的准入维度或额度类型。新任务只往 `TaskKey` 枚举里加键（`crates/intelligence/src/ai_foundation.rs`），其余照已有任务接。

## 4. 工程结构

### 4.1 模块边界的现实

【事实】设计里的 `domain`（20 行）和 `observation`（4 行）是空壳；实际代码集中在 `evidence`（约 8.8 万行）和 `intelligence`（约 9.7 万行）。

【判断】不要按名字补造。新代码在 `intelligence` 里以独立目录存在即可。回溯看板建议放 `crates/intelligence/src/ops_content_lens/`，只读 `ops_ledger` 的发布与阅读数据。

### 4.2 统计函数共用

【事实】Wilson 区间在 `crates/intelligence/src/opportunity/stats.rs`。

【判断】看板是它的第二个使用者，长期应当提取到共享位置（例如 `crates/intelligence/src/stats.rs`）。但机会卡阶段 1 正在开发，现在搬动会让两个工作包同时改同一个文件。所以看板先直接调用现有函数，置换检验与 kappa 写在自己的模块里；等机会卡阶段 1 结束，再用一个单独的小改动把三者提取出来。

### 4.3 SQL

【事实】非测试代码里有约 2,013 处运行时 SQL 字符串，没有编译期检查；有 389 行超过 300 字符。API 层里有 158 处 SQL。

【判断】长行很可能是 100 行函数硬门把 SQL 挤成了单行（推测）。不要回头重构旧代码。新代码遵守三条：

- SQL 放进独立的 `.sql` 文件，用 `include_str!` 引入（已有先例：`topic_research_automation/candidates.sql`）。
- 每条 SQL 至少被一个隔离 PostgreSQL 测试执行过。
- API 层不写 SQL，只调用 crate 里的函数。

### 4.4 特性开关

【事实】没有通用的特性开关机制；机会卡按 D-006 用环境变量，取值严格等于 `enabled` 才开启。

【判断】看板沿用同样的约定。这是第二个开关，可以顺手提取一个读取函数，两处共用；不需要更多。

### 4.5 前端

【事实】主题页的三个文件各有 2,600–3,400 行。

【判断】新页面按块拆文件，单文件不超过 400 行左右；图表先查 `apps/web/src/pages/ops/Charts.tsx` 是否已有可用的。

### 4.6 文档

【事实】79 份活跃计划；标为“权威当前”的合同里混有多轮实验的叙事；阶段总表最后核对于 2026-09-01，内容已与现状不符。

【判断】防止谎报完成的文档体系自己在漂移，这是最需要减重的地方。建议见待裁定事项 DR-11。本手册集自己也遵守：规格写在手册里，运行记录写在审计报告里，不混。

## 5. 上线前：必须、可以带着、不要做

| 类别 | 事项 |
|---|---|
| 必须解决 | L1 的三类失败看清并处理；L0 定义统一；成员登录（圈 B 之前）；观察恢复时的最小面板与风控确认 |
| 可以带着上线 | 两个大 crate 的内部边界；旧 SQL 的写法；L1 缓存未命中；账本缺价格；旧单篇路径尚未退役 |
| 不要做 | L2 自动路由；新的准入或额度机制；图数据库、向量库；为假想规模做的调度；全仓风格重构 |
