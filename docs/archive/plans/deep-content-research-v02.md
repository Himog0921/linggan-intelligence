# 0. 执行摘要

本规范把现有
L2「人工指定问题的单篇深化」升级为可被运营使用、可复核、可累积的 **Deep
Content Research**。

本轮不重写执行器，不建立新 Skill 包，不增加独立任务队列或 Token 服务。

保留现有六种
`FindingType`，但它们只是研究发现的分类，不是每次分析必须填写的六个栏目。

L2 采用三个标准研究任务：

1.  **内容设计研究**：研究作品如何组织信息、叙事和表达。
2.  **内容价值研究**：研究作者实际提供什么、内容承诺与交付如何对应、读者能带走什么。
3.  **创作方法研究**：提炼具体可迁移的方法、适用条件和调整方式。

同时保留自定义研究问题。

本轮最重要的技术修正：

-   当前 L2 只把 Core 摘要、Knowledge Units 和 Core Evidence
    发送给模型；它没有按问题读取完整正文、选定图片或视频片段。
-   当前 L2 的校验草稿包含 `questionFocus`、逐字 `support.quote` 和
    `presentationOrder`，但持久化 Finding 会丢弃这些字段。
-   当前底稿读取接口只返回同一 Core、同一领域下最新一条 Deep。
-   当前底稿前端只读，不提供 Deep 生成入口。
-   L1 已有图片传输能力；L2 可以复用现有图片物化与
    `prepare_with_images_in`，但需要增加按研究问题冻结和选择材料的逻辑。
-   当前视频链路可提供已有 ASR 与帧文字；不能据此宣称 L2
    已能理解完整视频动作、镜头节奏或音画关系。

因此，V0.2 的核心不是增加更多分析字段，而是建立：

**研究任务 → 定向材料 → 证据快照 → 研究发现 → 可追溯保存 →
多次研究可读取**

## 2.2 已确认缺口

### A. 生成入口缺失

`DossierUnderstanding.tsx` 当前只读取、展示 L1 与已有 Deep。

`DossierUnderstanding.test.tsx` 明确断言页面不出现「分析／生成」按钮。

API 已有：

-   `POST /api/local/content-understanding/deep`
-   `POST /api/local/content-understanding/deep/generate`

但当前研究底稿没有对应的运营发起闭环。

### B. L2 输入只使用 Core

当前 `deep_grounding::payload()` 主要发送：

-   研究问题；
-   Core summary；
-   Core knowledgeUnits；
-   Core evidence；
-   响应 Schema。

没有按问题重新读取完整正文，也没有把选定原始图片作为 L2 输入。

### C. 校验信息没有完整持久化

当前 DraftFinding 有：

-   `questionFocus`
-   `support[{ evidenceRef, quote }]`
-   `presentationOrder`

程序用这些字段进行校验，但最终 `Finding` 只保存：

-   `id`
-   `findingType`
-   `statement`
-   `basisUnitIds`
-   `evidenceRefs`

因此，问题对应片段、精确支持摘录和顺序依据没有完整进入 Deep 结果。

### D. 多次研究只能读取最新一条

`content_understanding::latest()` 对同一 `core_ref + domain_ref` 的 Deep
使用 `ORDER BY revision DESC LIMIT 1`。

数据库允许追加多条 Deep，但读取接口只返回最新一条。

### E. 图片与视频材料能力不对称

L1 已通过 `research_call::prepare_with_images_in()` 传递图片，并通过
`source::images_in()` 读取图片物化。

L2 当前调用 `prepare_in()`，没有图片输入。

`source::Packet` 包含正文、标题、ASR、帧文字和图片清单。L2
可以复用这些来源，但必须新增定向材料选择和快照。

当前没有证据证明 L2 已经支持原始视频片段或完整音画分析。

### F. 历史真实模型结果不是质量通过

历史记录包含一次真实 L2：

-   DeepSeek Flash；
-   High；
-   输入 1,284 tokens；
-   输出 2,050 tokens；
-   生成 8 条 Finding。

该次结果发现引用覆盖不足、先后关系缺少依据、出现题外信息。随后进行了离线修订，但不能把人工修订结果当成修订后真实模型通过。

修订后的 L2 仍需新一轮有界真实复测。

# 3. G1：统一研究方法

## 3.1 核心定义

L1 回答：

**这篇作品讲了什么、作者表达了什么、提供了什么。**

L2 回答：

**这篇作品具体采用了什么内容设计？这些设计提供了什么价值？哪些方法值得运营迁移？**

L2 不重复写一遍 L1 摘要。

L2 的每条 Finding 必须对本次研究问题提供增量。

## 3.2 三种标准研究任务

三种任务共用一个 L2 Executor、一个 Finding 合同和一套证据规则。

它们不是三个独立 Skill，也不是三次固定调用。

### 任务 A：内容设计研究 `content_design`

**研究目标：** 理解作者如何组织信息、叙事和表达，使读者理解作品内容。

默认研究问题：

> 这篇内容通过哪些具体安排组织信息并引导读者理解？请结合实际标题、开头、正文结构、案例、图片或视频文字中有依据的部分，找出值得研究的内容设计。

重点观察：

  --------------------------------------------------------------------------------------------
  观察方向                具体问题
  ----------------------- --------------------------------------------------------------------
  标题与开头              标题提出了什么问题、承诺或冲突？开头怎样承接？

  信息组织                信息按什么顺序展开？是问题---解释---方法，还是故事---观点---结论？

  内容结构                正文、案例、步骤、清单如何组织？

  叙事设计                作者怎样使用人物、场景、经历和转折？

  表达机制                作者如何使用对比、数字、具体动作、比喻或例子？

  图文关系                图片与正文是补充、解释、举例还是推进？
  --------------------------------------------------------------------------------------------

不要求每篇覆盖全部观察方向。

只输出材料实际支持、且对研究问题有价值的发现。

典型 Finding Type：

-   hook
-   structure
-   expression_mechanism

### 任务 B：内容价值研究 `content_value`

**研究目标：** 明确作者实际提供什么，以及内容承诺与实际交付如何对应。

默认研究问题：

> 作者通过这篇内容实际提供了哪些信息、解释、方法或解决方案？标题和开头承诺了什么？正文具体交付了什么？读者能够带走哪些明确内容？

重点观察：

  观察方向   具体问题
  ---------- ------------------------------------------
  内容承诺   标题、封面或开头承诺了什么？
  实际交付   正文真正提供了什么？
  问题回应   作者具体回应了什么问题？
  方法价值   是否提供可执行步骤、判断方法或具体工具？
  信息价值   是否提供重要数字、条件、案例或解释？
  价值差异   作品中真正有辨识度的内容是什么？

必须区分：

-   作者声称提供的价值；
-   正文实际交付的内容；
-   研究者对潜在读者价值的解释。

不能仅凭单篇正文断言读者已经获得效果。

典型 Finding Type：

-   value_delivery
-   structure
-   expression_mechanism

### 任务 C：创作方法研究 `creation_method`

**研究目标：**
把单篇内容中的具体做法转化为运营可理解、可调整、可迁移的方法。

默认研究问题：

> 这篇内容有哪些值得迁移的创作方法？请说明方法具体是什么、在作品中怎样使用、适用于什么内容场景，以及迁移到其他选题时需要怎样调整。

重点观察：

  观察方向     输出要求
  ------------ ----------------------------
  方法         用一句明确的话说明具体做法
  原作品用法   指出作者在哪里、怎样使用
  操作步骤     将方法拆成可执行动作
  适用条件     什么主题、用户或场景适合
  迁移调整     换主题后哪些内容需要改变
  不适用情况   什么情况下不应机械照搬

禁止输出：

-   「标题要有吸引力」；
-   「内容要有情绪」；
-   「结构要清晰」；
-   「多使用数字」。

这些不是可执行方法。

示例：

> 把抽象困难转换为一个可立即执行的最小动作。原作品先描述孩子迟迟不开始作业，再给出一个具体的启动动作。迁移到其他家庭教育主题时，应先找到用户真正卡住的第一个动作，而不是机械套用三步结构。

典型 Finding Type：

-   transferable_method
-   structure
-   expression_mechanism

### 自定义研究问题 `custom`

运营可以直接提出问题。

自定义问题仍使用同一 L2 规则：

-   明确本次问题；
-   根据问题选择材料；
-   只产生相关发现；
-   不强制覆盖六种 Finding Type；
-   不允许题外背景挤占结果。

## 3.3 六种 Finding Type 的职责

保留现有枚举，不新增重复类别。

  -------------------------------------------------------------------------------------------
  Finding Type              定义                         例子
  ------------------------- ---------------------------- ------------------------------------
  `hook`                    标题、封面、开头的切入设计   先呈现家长熟悉的具体困境

  `structure`               信息、段落、步骤或叙事组织   先给场景，再解释原因，最后提供动作

  `value_delivery`          作者实际提供的价值           提供三项可执行的启动动作

  `expression_mechanism`    具体表达手法                 用具体动作替代抽象概念

  `engagement_hypothesis`   对参与或传播机制的假设       具体问题可能更容易引发读者回应

  `transferable_method`     可以迁移的创作方法           将复杂任务拆成最小启动动作
  -------------------------------------------------------------------------------------------

`engagement_hypothesis` 不是默认输出项。

单篇内容可以研究作者设计的互动入口，但不能用评论数量直接证明互动机制，也不能仅凭单篇数据推导因果。

跨作品表现差异研究属于后续独立专项研究，不纳入本轮单篇 L2。

## 3.4 断言性质 `assertionKind`

Finding Type 解决「发现属于哪类内容」。

Assertion Kind 解决「这条发现属于什么性质」。

两者不能合并。

建议增加四种：

  ----------------------------------------------------------------------------------
  assertionKind      定义                         示例
  ------------------ ---------------------------- ----------------------------------
  `observation`      原材料直接呈现的内容或结构   正文先描述问题，再列出三个动作

  `author_claim`     作者明确表达的主张           作者表示这种方法能够帮助孩子启动

  `interpretation`   对内容设计的研究解释         三个动作把抽象任务转成具体起点

  `hypothesis`       对潜在作用机制的假设         具体动作可能降低读者的行动门槛
  ----------------------------------------------------------------------------------

要求：

1.  作者主张必须保留作者归属。
2.  观察不能擅自升级成因果判断。
3.  解释可以直接表达，不需要附加无意义免责声明。
4.  假设应指出具体推理对象，不要写空泛的「可能有效」。
5.  一条 Finding 尽量只表达一个主要判断，避免把多个性质混在一句话里。

# 4. G2：研究输入与材料选择

## 4.1 输入原则

L2 不应该永远只读 Core，也不应该每次重新发送所有原始材料。

采用：

**Core 定位 + 问题所需材料 + 精确证据快照。**

Core 用于定位重点。

原始材料用于支持判断。

定向补充用于解决 Core 未覆盖的内容。

## 4.2 研究任务与材料配置

  ------------------------------------------------------------------------------------
  研究任务           默认输入                         按需补充
  ------------------ -------------------------------- --------------------------------
  内容设计研究       Core、标题、完整正文、相关       封面、选定图片、完整图片顺序
                     OCR/ASR                          

  内容价值研究       Core、标题、正文、方法相关证据   提供具体方案的图片或视频帧文字

  创作方法研究       Core、完整方法上下文、相关正文   方法所在图片、步骤图、具体案例

  自定义问题         Core + 问题相关证据              根据问题由操作者选择
  ------------------------------------------------------------------------------------

不要为了让模型分析完整而无差别发送所有媒体。

## 4.3 材料类型

### A. `core_reference`

-   Core summary；
-   Knowledge Units；
-   Candidate Labels（仅作为检索线索，不作为事实依据）。

### B. `text_material`

-   原生标题；
-   完整正文；
-   正文片段；
-   标签；
-   已保存的口播转写；
-   已保存的画面文字；
-   可用时间和位置。

### C. `image_material`

-   原始图片引用；
-   图片版本；
-   图片字节 SHA256；
-   图片顺序；
-   图片用途；
-   本次选择状态。

L2 可复用现有 L1 图片物化及 PiAdapter
图片传输能力，但必须按本次研究任务选择图片。

### D. `performance_context`

只有当前系统存在可读取、来源明确的表现快照时才提供。

包括：

-   指标名称；
-   实际值；
-   观察时间；
-   作品发布年龄；
-   比较组标识；
-   比较组计算口径。

如果没有曝光或播放分母，不得计算虚构的曝光转化率。

没有可比较的同组数据时，不生成相对排名。

### E. 视频材料边界

本轮可以复用：

-   已保存 ASR；
-   已保存帧文字；
-   已有时间位置。

本轮不宣称支持：

-   完整视频动作理解；
-   完整镜头节奏分析；
-   音画同步研究；
-   未提供帧的画面内容。

如果研究问题要求这些能力，界面不应将该问题伪装成已支持的研究类型。

## 4.4 证据选择方式

由程序按研究模式生成默认材料集合。

运营可以在发起前查看和调整材料选择。

第一版不需要开发复杂的可视化证据编辑器。

建议先支持：

-   使用默认材料；
-   补充封面；
-   补充选定图片；
-   补充正文或口播上下文；
-   查看本次将发送的材料种类和数量。

具体图片与文本引用必须来自当前作品、当前领域和当前材料版本。

## 4.5 输入冻结

每次 Deep 请求必须冻结：

-   `coreRef`
-   `domainRef`
-   `workRef`
-   `materialSnapshotIdentity`
-   `researchMode`
-   `question`
-   `selectedEvidenceRefs`
-   `selectedMediaRefs`
-   `sourceVersion`
-   `blobSha256`
-   `displayOrder`
-   `taskConfigRef`
-   `taskRevision`
-   `methodVersion`
-   `promptVersion`
-   `inputFingerprint`

提交后不可静默替换材料。

模型调用前检查当前来源仍然有效。

结果保存前再次检查：

-   Core 仍匹配；
-   材料快照仍匹配；
-   来源权限仍允许；
-   任务配置及外发许可仍有效。

来源变化时，不发布基于旧材料的结果。

# 5. Deep Finding V0.2 输出合同

## 5.1 设计目标

当前 Finding 已有：

-   id；
-   findingType；
-   statement；
-   basisUnitIds；
-   evidenceRefs。

V0.2 应增加能够解释研究过程和实际使用价值的最少字段。

建议结构：

``` json
{
  "id": "F01",
  "findingType": "structure",
  "assertionKind": "observation",
  "statement": "作者先呈现家长催促的具体场景，再给出一个可立即执行的启动动作。",
  "questionFocus": "内容如何组织场景与方法",
  "basisUnitIds": ["KU01", "KU03"],
  "support": [
    {
      "evidenceRef": "DE01",
      "supportType": "verbatim_text",
      "excerpt": "先把书本放到桌面上。"
    },
    {
      "evidenceRef": "DE02",
      "supportType": "visual_observation",
      "observation": "图片中展示了对应的作业启动步骤。"
    }
  ],
  "application": {
    "method": "将抽象困难转成一个可立即执行的最小动作。",
    "steps": [
      "定位用户当前无法开始的任务",
      "找出最小的第一步",
      "用具体动作表达"
    ],
    "whenToUse": "用户知道自己有问题，但不知道从哪里开始行动。",
    "adaptation": "根据具体主题替换任务动作和用户场景。",
    "avoidWhen": "问题本身需要先处理安全、资源或复杂决策条件。"
  }
}
```

以上为结构示例，不是真实作品结果。

## 5.2 字段说明

  ----------------------------------------------------------------------
  字段                   必要性                 说明
  ---------------------- ---------------------- ------------------------
  `id`                   必须                   单次 Deep 内唯一
                                                ID，由程序校验

  `findingType`          必须                   复用现有六种类型

  `assertionKind`        必须                   observation /
                                                author_claim /
                                                interpretation /
                                                hypothesis

  `statement`            必须                   直接回答研究问题

  `questionFocus`        必须                   本条发现回答的问题片段

  `basisUnitIds`         必须                   引用已有 Core 知识单元

  `support`              必须                   精确支持材料

  `application`          条件必需               仅 `transferable_method`
                                                使用
  ----------------------------------------------------------------------

## 5.3 Support 类型

  ----------------------------------------------------------------------------------
  supportType            适用材料               校验方式
  ---------------------- ---------------------- ------------------------------------
  `verbatim_text`        标题、正文、ASR、OCR   逐字匹配原文

  `visual_observation`   原始图片或实际视频帧   绑定具体媒体来源，人工评审视觉判断

  `model_read`           已保存的 L1 视觉观察   引用对应 L1 Evidence
  ----------------------------------------------------------------------------------

注意：

图片视觉观察不能伪装成原文引句。

视频口播不能替代画面证据。

模型对图片的描述不能伪装成精确 OCR。

## 5.4 Deep Evidence Snapshot

这是 V0.2 必须补充的结构。

当前 Deep Finding 只能引用 Core 的 Evidence ID。

当 L2 定向补充了 Core
之外的正文、图片或媒体材料时，当前存储结构无法完整记录这些来源。

因此建议每次 Deep 保存独立的 `evidenceSnapshot`：

``` json
{
  "id": "DE01",
  "sourceRef": "source-ref",
  "sourceVersion": "source-version",
  "materialKind": "body",
  "inputCitationId": "body-01",
  "displayOrder": 1,
  "orderState": "known",
  "quote": "先把书本放到桌面上。",
  "mediaSha256": null
}
```

图片证据示例：

``` json
{
  "id": "DE02",
  "sourceRef": "image-source-ref",
  "sourceVersion": "image-version",
  "materialKind": "image",
  "inputCitationId": "image_2",
  "displayOrder": 2,
  "orderState": "known",
  "quote": null,
  "mediaSha256": "sha256-value"
}
```

要求：

1.  Evidence ID 在单次 Deep 内唯一。
2.  Deep Evidence Snapshot 不改变 Core 原有 Evidence。
3.  每条 Finding 引用本次 Deep 的 Evidence Snapshot。
4.  每个来源绑定 sourceRef、sourceVersion 和实际材料类型。
5.  图片引用绑定实际媒体哈希。
6.  未知顺序不编造顺序。
7.  历史 Deep 必须能够使用当时保存的证据快照重新展示。

## 5.5 兼容策略

不要破坏旧 Deep 数据。

旧记录仍按原结构读取。

新记录增加：

-   `researchMode`
-   `assertionKind`
-   `questionFocus`
-   `support`
-   `application`
-   `evidenceSnapshot`
-   `inputFingerprint`

现有 `evidenceRefs` 可以由 `support` 派生，也可以在兼容期保留。

旧数据不应被伪造补齐新字段。

# 6. 研究发现的质量规则

## 6.1 研究相关性

每条 Finding 必须直接回答本次研究问题。

删除：

-   与问题无关的背景信息；
-   对 Core 的重复摘要；
-   仅仅复述标题的发现；
-   仅为了填充 Finding Type 而生成的内容。

## 6.2 研究增量

每条 Finding 都要比 L1 提供更多信息。

例如：

L1：

> 作者提供三个作业启动动作。

L2：

> 作者把复杂任务拆成三个具体动作，并先安排不需要思考的准备行为，再进入实际作业。这种顺序体现了先降低启动门槛、再进入任务的组织方法。

第二条提供了内容结构和方法解释。

如果 L2 只是换句话重复 L1，就没有研究增量。

## 6.3 证据支撑

-   文字引句逐字匹配；
-   图片发现绑定实际图片；
-   数字保留原始指标、单位和条件；
-   作者主张保留归属；
-   先后关系必须有真实顺序依据；
-   并列内容不能写成先后关系；
-   单篇表现不能直接推出传播因果。

## 6.4 输出长度

建议每次产生 1--8 条高价值 Finding。

不要求固定数量。

不为了完整覆盖六个类型而制造内容。

如果当前材料无法回答问题，按现有
`content_understanding_deep_insufficient_evidence`
机制处理，不生成虚假发现。

## 6.5 表达规范

-   先写结论，再给具体依据。
-   一条 Finding 只表达一个核心判断。
-   避免「内容很好」「结构清晰」「值得学习」等空话。
-   不输出模型自我评价。
-   不输出泛化免责声明。
-   不输出冗长的局限性章节。
-   研究发现直接表达，证据和研究性质由结构字段记录。

# 7. 多次 Deep 结果的保存与读取

## 7.1 现有问题

数据库允许追加多个 Deep。

但 `content_understanding::latest()` 只读取最新一条。

这不满足长期研究积累的需求。

## 7.2 V0.2 目标

 ├── Deep 03：创作方法研究

每个 Deep 都独立绑定：

-   Core；
-   domain；
-   researchMode；
-   question；
-   methodVersion；
-   inputFingerprint；
-   evidenceSnapshot；
-   findings；
-   invocationRef；
-   createdAt。

## 7.3 数据库建议

优先在现有表上做增量扩展。

建议评估：

### `linggan_content_understanding_deep_request`

增加：

-   `research_mode`
-   `input_manifest`
-   `input_fingerprint`

保留现有不可变请求记录。

### `linggan_content_understanding_deep`

增加：

-   `research_mode`
-   `evidence_snapshot`

现有 `findings` 保存 V0.2 Finding 结构。

不要另建第二套 Deep 表。

## 7.4 读取接口

`analysis.deepAnalyses[]`

-   `researchMode`

# 9. G1/G2 验证方案

## 9.1 第一轮：3--5 篇真实作品

目的：检查研究问题和方法是否有效，不宣称统计意义上的总体质量。

建议样本：

  样本                         研究任务
  ---------------------------- --------------
  高表现教程                   内容设计研究
  多图活动清单                 内容价值研究
  观点型笔记                   内容设计研究
  故事型笔记                   内容设计研究
  普通表现但有研究价值的作品   创作方法研究

不要求每篇执行全部三种任务。

## 9.2 每条 Finding 的评价标准

每项 0--2 分：

  维度         0 分         1 分                 2 分
  ------------ ------------ -------------------- --------------------------
  问题相关性   没有回答     部分回答             直接回答
  证据支撑     证据不支持   部分支持             关键判断均有支持
  内容具体性   空泛套话     有具体内容但不完整   具体、清楚
  研究增量     重复 Core    有少量新信息         提供明显新理解
  运营价值     无法使用     可参考               可以指导具体创作
  归因准确性   错误归因     部分准确             作者、材料与推断区分准确

硬性拒绝：

-   虚构原文、图片或视频内容；
-   作者和第三方观点混淆；
-   数字或条件被改写；
-   无依据的顺序或因果；
-   引用与结论无关；
-   把 Core 复述当成深度发现。

通过要求：

1.  关键证据支撑必须为 2 分。
2.  问题相关性不得为 0。
3.  研究增量不得为 0。
4.  不出现硬性拒绝项。
5.  创作方法研究必须说明具体方法及适用条件。

不要只计算总平均分掩盖关键错误。

## 9.3 L1/L2 对照

每篇同时保留 L1 Core。

对照回答：

-   L1 已经知道什么？
-   L2 新增了什么？
-   新增内容是否有证据？
-   新增内容能否指导运营？
-   哪些内容只是重复？

## 9.4 Token 与成本

每次记录：

-   输入 Token；
-   输出 Token；
-   推理 Token（如接口提供）；
-   缓存 Token；
-   请求耗时；
-   实际账单（只有可核实才填写）；
-   发送的文本数量；
-   发送的图片数量；
-   研究模式；
-   结果质量。

推理 Token 不与总输出重复相加。

不要把供应商价格估算写成实际账单。

## 9.5 评测方法

人工阅读是内容质量的最终验收依据。

LLM-as-a-Judge 可以辅助：

-   发现重复 Finding；
-   检查问题相关性；
-   对照证据引用；
-   标记可能的错误归因。

但不能单独决定研究结果通过。

3--5 篇用于研究方法校准。

之后建立约 20 篇试验集，并保留未参与 Prompt 调整的验证样本。
