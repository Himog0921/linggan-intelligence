## 1 · 迁入值能证明什么

迁入值只说明「导出那一刻，内容工作台里是这样记的」。它不证明账号现在可用、帖子现在可见、阅读量准确，也不是 Linggan 自己的观察。系统观察（自动发现我方帖子）由 D5 另行接入，不覆盖这些表里的迁入值。

切换（D6）之前，内容工作台是唯一录入处，这些表是它的只读镜像：重新导入较新的导出会更新镜像，Linggan 里不录入、不修改。

## 2 · 表

| 表 | 一行是什么 | 身份 | 要点 |
|---|---|---|---|
| `linggan_ops_import_batch` | 一次已执行的导入 | `batch_ref`；预览指纹唯一 | 只追加。记导出时间、三份文件的 SHA-256、规则版本、业务领域和各类插入/更新/未变计数 |
| `linggan_ops_account` | 一个我方账号 | 来源系统 + 原账号号 | 必有业务领域（`observation_domain`）。`ledger_state`：`in_ledger` 来自账号导出；`absent_from_export` 是已在工作台删除、只从发布记录重建的账号，旧状态未知（`status` 为空），页面显示「已停用」。小红书主页链接可解析出用户号 |
| `linggan_ops_publication` | 一条发布登记 | 来源系统 + 原记录号 | 作品编号与对号状态、发布时间与日期状态（业务日按北京时间生成）、重复登记合并去向、旧回流字段（按旧含义保存）、不在最新导出中的标记。不含阅读量列 |
| `linggan_ops_view_report` | 一次阅读量填报 | `report_ref`，`report_sequence` 定先后 | 只追加。一条发布登记的当前阅读量是它最新的一次填报；最新一次是「清空」或从未填报，都表示未知 |
| `linggan_ops_daily_report` | 一个运营人一天的链接打开数与加微数 | 来源系统 + 原记录号；在最新导出中的行按运营人名 + 业务日唯一 | 旧系统中这两列默认为 0，0 与「没填」分不开，按旧值保存；不在最新导出中的行保留并标记 |

三张镜像表（账号、发布登记、每日数据）可以被重新导入更新，但禁止删除；导入批次与阅读量填报禁止修改和删除。这些由数据库触发器保证。

旧系统的用户编号（负责人、创建人）只作为来源编号保存，不是 Linggan 的人员身份；运营人名保持工作台里的写法。人员对照和登录账号在 D4 处理。

## 3 · 导入规则 `ops-import.v1`

### 3.1 输入与校验

- 输入是内容工作台「导入导出」页导出的三份 JSON：`data-management-accounts.json`、`data-management-publications.json`、`data-management-daily-metrics.json`。文件只在本机读取，不进 Git。
- 每行的字段集合必须完全是已知集合（含下文明确丢弃的字段），类型、值域、时间格式逐项校验；三份文件必须属于同一个工作区。原记录号在各自文件内必须唯一；每日数据的「运营人名 + 业务日」必须唯一。
- 任何一处不符合，整批拒绝，不部分导入。错误信息只给文件、行号和字段名，不回显内容。
- 导出时间由执行人给出，必须带时区；不能早于三份文件里最后一条记录的修改时间，也不能晚于现在。实际取三份文件中最后保存那份的保存时间（精确到毫秒），因为工作台在导出请求里会自动补建当月的空每日数据行，这些行的创建时间只比文件保存早零点几秒。

### 3.2 账号

- 账号导出中的 95 个账号逐个迁入，`ledger_state = in_ledger`。保存平台、账号名、小红书号、状态（`active` / `violation_disabled` / `warming` / `paused` / `archived`）、是否保留、负责运营、负责人编号、粉丝数、主页链接、设备、IP 属地、备注、审核状态和原创建/更新时间。
- 健康度（观察/低效/暂停等）是工作台按发布数据现算的，不迁；D2 按继承的规则重算。
- 发布记录指向、但账号导出里没有的账号（已在工作台删除），按原账号号重建一个账号：平台和账号名取自它名下的发布记录（必须一致），`ledger_state = absent_from_export`，状态、负责运营等未知字段留空。
- 业务领域：第一次迁入时归入导入命令指定的领域（ADHD）。领域归属是 Linggan 自己的决定，之后重新导入不会覆盖。迁入工具不新建领域。
- 主页链接（规则 `ops-link.v1`）：小红书 `xiaohongshu.com/user/profile/<24 位十六进制>` 解析出用户号，`profile_link_state = parsed`；其余链接（短链、抖音、其他网址）为 `pending_match`（待对号）；没有链接为 `missing`。

### 3.3 发布登记

- 每条记录按原记录号迁入。保存账号、平台、发布链接、规范化链接、发布时间、标题、正文、发布人名、负责人编号、点赞、收藏、评论、封面点击率、来源方式（手工/表格导入/选题同步）、审核状态和原创建/更新时间。发布记录的平台必须与所属账号一致。
- 作品编号（规则 `ops-link.v1`）：小红书先从发布链接、再从规范化链接解析 `xiaohongshu.com/explore/` 或 `/discovery/item/` 后的 24 位编号；两处都能解析但编号不同记 `conflict`。抖音一律记 `pending_match`，短链要等 D5 核实。
- 日期状态（规则 `ops-date.v1`）：发布时间在 2024 年或更早的记 `suspect_year`（日期存疑），其余 `as_recorded`。时间按原值保存，业务日按北京时间切分。
- 旧回流字段按旧含义保存，不换算成新口径：`legacy_effective_publication`（旧「有效发布」，等于回流成功）、`legacy_data_synced_at`、`legacy_data_sync_status`。
- 点赞、收藏、评论、封面点击率是工作台里的记录值（多数来自旧回流），只作为迁入旧值展示，不当作 Linggan 的观察。

### 3.4 重复登记合并（规则 `ops-dedupe.v1`）

- 同一平台下，作品编号相同，或规范化链接完全相同，视为同一篇帖子的重复登记。
- 每组留一条为主记录，其余记录的 `merged_into_ref` 指向它；原记录不删除，自身字段保持原样。主记录的选法依次为：有阅读量的优先；已填字段（阅读量、点赞、收藏、评论、封面点击率、标题、正文）多的优先；发布时间早的优先；创建时间早的优先；原记录号小的优先。
- 计数、页面和爆款只看主记录。同组记录的阅读量、发布日期不一致时，在预览里单独计数。
- 每次导入按最新导出重新分组，合并关系随之更新。

### 3.5 阅读量填报（规则 `ops-views.v1`）

- 导入时把每条发布登记（含被合并的）在导出里的阅读量，与它在 Linggan 里最新的填报比较：
  - 第一次见到、有值：追加一次填报；
  - 值变了：追加一次填报；
  - 以前有值、现在为空：追加一次「清空」；
  - 其他情况：不追加。
- 迁入的填报记为 `source_kind = workbench_import`，带导入批次与导出时间；工作台里是谁填的未知。D2 起的人工填报另记填报人。
- 抖音的播放量照样迁入，但不必填、不判爆款（Mog 2026-10-13 确认）。

### 3.6 每日数据

- 每行按原记录号迁入：运营人名、业务日、链接打开数、加微数、负责人编号、备注、审核状态和原创建/更新时间。
- 只接受「每人每天一行」（工作台里平台为 `all`、账号名为空）；出现按账号或按平台拆分的行，整批拒绝。
- 工作台在读取或导出每日数据时，会为当月还没有行的运营人自动补建空行（两列都是 0）。这些行照样迁入，它们的 0 同样表示没填。
- 旧「发布数」是工作台按发布记录现算的派生值，不迁；对账时与重算值比较（见 §4）。每日手填的「当日爆款数」与当月累计等派生值不迁。

### 3.7 不迁的字段

- Mog 确认废弃、填写率为 0–0.5% 的栏目：选题、选题关键词、配图、帖子类型、内容定位、单篇引流、单篇加微、爆点分析、问题分析、备注、关联选题。
- 工作台内部或旧回流引擎字段：平台作品编号（从未填写，由 Linggan 自己解析）、内容资产、内容编码、原始链接、同步原因、同步观察时间与修订键、最近同步任务、重复链接标记（由 §3.4 重算）、媒体。
- 媒体：510 条记录的封面存在工作台本机，导出里只有工作台内部地址，迁不过来；历史封面怎么显示在 D2 前确定。
- 预览会列出这些字段里非空值的条数，便于发现切换前有人新填的内容。

### 3.8 预览、执行与重跑

- 先执行 `preview`：校验三份文件、生成导入计划、与数据库现状比较，输出对账与差异（只含聚合数）和预览指纹。预览不写库。
- 再执行 `apply` 并带上预览指纹：重新生成计划，指纹不一致就拒绝；一致则在一个事务里写入，任何一步失败全部回滚。同一时间只能有一个导入在执行。
- 预览指纹由三份文件的 SHA-256、导出时间、业务领域和规则版本决定。同一指纹已经执行过时，返回原回执，不再写入。
- 重新导入较新的导出：新记录插入，变化的记录更新，没变的不动。Linggan 里有、新导出里没有的发布登记和每日数据，标记为「不在最新导出中」并记下是哪一批发现的，不删除；它们不再参与合并、计数和页面。账号不在新的账号导出里时改为 `absent_from_export`，保留最后已知的字段。再次出现在导出里的记录取消标记。
- 预览会列出这次将要标记的条数。导出被筛选过（例如只导出了一个平台）时，这个数字会异常地大，执行前必须核对。D6 切换后不再导入。

## 4 · 对账口径

预览和执行回执输出以下聚合数，作为 D1 的新旧对账表：

- **账号**：导出条数、迁入条数（按平台、状态）；重建的已删账号数及其名下记录数；主页链接三种状态的数量。
- **发布登记**：导出条数、迁入条数（按平台、北京时间月份）；重复登记组数与被合并条数、合并后条数；作品编号各状态数量；日期存疑数；账号未知数。
- **阅读量**：有阅读量的条数（按平台）；小红书主记录中最新阅读量 ≥ 5000 的条数（按月）。
- **每日数据**：导出行数、迁入行数；逐月链接打开数、加微数与导出合计一致；逐月旧「发布数」合计、按发布人名重算的发布数、发布登记条数，以及差异原因。
- **差异**：本次与数据库现状相比的插入/更新/未变数量；数据库里有、本次导出里没有的记录数。

### 旧「发布数」的已知差异

工作台的每日「发布数」按「发布人名等于运营人名，**或**负责人编号相同」计数。一个负责人编号挂在多个运营人名下时，这个编号名下的帖子会在每个运营人的行里各算一次。2026-09 有一个编号同时挂在多个运营人名下，旧合计 553，去重后 387，发布登记 388 条（差的 1 条没有对应的每日数据行）；2026-10（至 12 日）同理，旧值 128，发布登记 111 条。

Linggan 的每日发布数按发布人名和业务日计数，不按负责人编号扩展，所以不继承这类重复计数。

## 5 · 给 D2/D3 的读取约定

- **爆款**：小红书、主记录（未被合并）、最新阅读量填报值 ≥ 5000。抖音不判爆款。
- **待补阅读量**：小红书主记录，从未填报，或最新一次是「清空」。满 7 天提醒从发布时间按北京时间计算（D2 定页面表达）。抖音播放量选填，不进待补。
- **未知不等于 0**：没有填报的阅读量、空的点赞/收藏/评论、重建账号的未知状态，都显示为未知，不能按 0 参与求和、比率或命中率分母。
- **有效发布**：`legacy_effective_publication` 只表示旧回流成功；D5 之前页面显示「未接入」，不能用旧标记冒充系统确认。
- **每日发布数**：按发布人名和业务日从主记录计数。
- **只看在最新导出中的记录**：`missing_since_batch_ref` 为空的发布登记和每日数据才参与页面和统计。

## 6 · 不变量与反例证明

| 不变量 | 证明（隔离 PostgreSQL，合成数据） |
|---|---|
| 重复执行不产生重复记录 | 同一预览执行两次，第二次返回原回执、各表行数不变 |
| 指纹不符不写入 | 预览后改动任一文件，执行被拒绝且数据库无变化 |
| 整批原子 | 构造在写入中途失败的批次，所有表无残留 |
| 未知不变成 0 | 无阅读量的记录没有填报行；空粉丝数、空点赞保持为空 |
| 镜像可更新、不可删除 | 更新较新导出时只更新变化的行；导出里消失的记录被标记而不是删除；删除被触发器拒绝 |
| 领域归属不被覆盖 | 在 Linggan 里改过领域的账号，重新导入后领域不变 |
| 填报只追加 | 值变化追加新填报、清空追加「清空」；修改或删除填报被拒绝 |
| 历史不推断现状 | 重建账号状态为空；旧「有效发布」单独成列 |
| 合并不丢原记录 | 被合并的记录仍在，字段原样，只多一个合并去向 |
| 输入结构不符整批拒绝 | 多出未知字段、枚举越界、时间格式错、平台与账号不一致、每日数据按账号拆分，都整批拒绝 |

## 7 · 不证明什么

- 不证明迁入数字真实或完整：阅读量是运营手填，点赞等来自旧回流，发帖只登记了一部分（审计 ①）。
- 不证明作品编号对应的帖子现在可见，也不证明重复登记组里哪个日期是真的。
- 不包含目标与人员分组（工作台导出不含），不包含页面、登录与采集。
