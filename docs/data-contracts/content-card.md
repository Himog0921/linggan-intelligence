# Content Card 合同

> 状态: 权威当前
> 最后核对: 2026-11-10
> 适用范围: `content-card.v0.2` 持久化结果的设计；不是供应商输出协议，也不改变现有运行时行为
> 事实来源: Content Card v0.1 冻结原件、V1.2 产品决定及 2026-11-10 已确认的独立分支开发指令
> 冲突时以谁为准: 最新明确授权决定范围；本合同与配套 Schema 定义 v0.2；实际是否接入以代码与运行证据为准

## 1. 版本与本次变化

当前设计合同为 **`content-card.v0.2`**，完整机器约束见 [`content-card.v0.2.schema.json`](content-card.v0.2.schema.json)。采用 JSON Schema Draft 2020-12；验证时必须启用 `uuid`、`date-time` 的格式检查。文件是人工维护的合同源，不是从生产类型生成的产物。

相对 v0.1 仅改变：

1. 合同标识、Schema 身份及说明升级至 v0.2。
2. `sourceSnapshot.includedKinds` 增加 `image`，数组上限由6变7。
3. 同一份 `evidence` 清单的条目使用 `oneOf`：原文字精确证据分支原样保留，新增图片识读分支。

Core 九字段、其类型与长度约束、文字证据字段、Deep、generation、身份与其他外壳约束均不变。不是两套 Core，也不引入双写或字段回退。旧结果不能只改版本号就冒充已完成来源与内容核验的新结果。

本合同只确定结果格式和责任，不授予模型外发、生产开发、入库、部署或扩大试点许可。v0.1 的三个私有冻结原件及历史结果保留不改；它们是旧版设计与实验基线，不是第二套当前目标合同。

## 2. 保持不变的共同结果

同一作品、同一材料快照及同一核心理解方法版本只形成一份 Core：逻辑身份仍为 `(workRef, materialSnapshotIdentity, coreMethodVersion)`。跨领域复用同一 Core，不因领域复制卡片；底稿引用同一结果，L2 只追加 Deep，不覆盖 Core。`coreMethodVersion` 是该逻辑键中基础方法版本的含义，不新增同名外壳字段。

外壳仍包含 `schemaVersion/workRef/analysisRef/sourceSnapshot/core/deep/evidence/generation`。身份、快照、来源与执行元数据由程序绑定，不接受模型编造 UUID、版本、位置或哈希。

`generation` 的版本引用沿用非空字符串约束：未绑定 Skill 时 `skillVersionRef` 为 `none`，不伪造版本身份；其余引用取本次冻结配置。`providerReturnedModel` 取实际供应商响应，不用请求的模型名替代。

| Core 字段 | 含义（不变） |
| --- | --- |
| `summary` | 摘要正文与依据的单元 ID |
| `contentType` | 主内容类型，不是视频／图文媒体形态 |
| `mainTopicUnitId` | 主要议题单元，不是正式 Topic 身份 |
| `audienceUnitIds` | 有依据的受众与处境单元，可空 |
| `authorPositionUnitIds` | 作者明确立场单元，可空 |
| `provisionUnitIds` | 具体方法、解释、信息、案例单元，可空 |
| `readerValueUnitIds` | 读者能够带走的内容价值单元，可空 |
| `knowledgeUnits` | 各自有证据的原子化内容单元 |
| `candidateLabels` | 带单元依据与检索用途的候选标签，不是正式 Topic/Problem/Tag 身份 |

知识单元仍包含 `id/unitType/statement/assertionKind/speakerRole/evidenceRefs`。八类 `unitType` 为 `discussion/audience_context/author_position/provision/reader_value/answer_form/expression/participation`；`observation/author_claim/interpretation` 是断言种类，不是单元类型。说话人仍为 `author/quoted/unknown`，不能互换作者主张、画面观察与分析解释。

摘要及分类数组引用同一组单元，不另写重复语义。主议题须是主要 `discussion`；本次不将隔离实验“取第一个 discussion”的组装约定升级成所有实现的选题算法。

所有数量、枚举和长度沿用 v0.1 的机器约束，包括知识单元1–12、单元陈述1–280字符、候选标签0–12、证据1–64。原设计“优先3–8个高价值单元、不凑数”是生成建议，不能绕过 Schema 的上限。

L1 仍只覆盖通过 L0 领域和材料质量筛选的作品，热度不是默认准入门槛。评论及表现数据不进入 L1 内容事实；聊天或评论截图仍是笔记图片材料，不自动变成数据库中的真实评论。L2 触发、图谱跨篇归并和评论研究保持各自职责，本次不新增其执行规则。

## 3. 文字证据：原分支不变

必填字段仍为 `id/inputCitationId/sourceRef/sourceVersion/sourceKind/start/end/quote`，不接纳额外字段；`sourceKind` 仍为 `material`。

- 程序根据实际输入及 canonical 材料绑定来源身份、版本和 Unicode 文字位置，核对引句逐字存在、位置与范围正确；Schema 的数字范围不替代这项检查。
- `quote` 是精确文字引句，不接收模型读图文字；不能为图片编造 `start/end`，或把模型识读冒充程序逐字匹配。
- 文字分支不增加 `anchorKind` 或 `verification`；原有文字校验不因图片扩展而放宽。

## 4. 图片证据：同一清单的新分支

下列11个字段全部必填，不接纳额外字段。没有读到的文字或画面观察用 `null`；两项至少一项有实质内容。

| 字段 | 约束与责任 |
| --- | --- |
| `id` | 本结果内局部证据 ID，沿用 `^[A-Za-z][A-Za-z0-9_-]{0,31}$`；供 `evidenceRefs` 引用 |
| `inputCitationId` | 沿用1–500字符；程序绑定本次实际发送的图片别名，不能凭空增加图片 |
| `sourceRef` | 沿用 UUID 格式；程序绑定真实材料身份，不能为了格式合格而编造 |
| `sourceVersion` | 沿用1–160字符；程序绑定该图片材料的实际版本 |
| `sourceKind` | 固定为 `material`；不新增 `vision` 来源类别 |
| `anchorKind` | 固定为 `image`；整图为依据，不代表已经有区域定位 |
| `blobSha256` | 实际发送图片字节的小写64位十六进制 SHA256，由程序计算核对，不由模型提供 |
| `modelQuote` | 模型读到的图中文字，`null` 或1–500字符且至少含一个非空白字符；不是精确匹配引句 |
| `observation` | 可见内容的模型观察，`null` 或1–500字符且至少含一个非空白字符 |
| `speakerRole` | `author/quoted/unknown`；结合整篇语境整理，作者产品／操作展示可用author，不要求外部证明截图身份；明确第三方发言不混作作者观点 |
| `verification` | 程序固定为 `model_read`，不表示人工核验、逐字匹配或事实已被证明 |

两项内容均为 `null`、空串或空白占位时拒绝；即使另一项有内容，也不能用空白字符串代替 `null`。图片分支禁止 `start/end/quote/bbox/exact/verified`。合法人物枚举只证明格式合法，不证明归属正确。

`sourceSnapshot.includedKinds` 允许 `title/body/tags/ocr/transcript/frame_text/image`。`image` 表示实际使用图片；它不是新的识读方法种类。保留枚举中的 `ocr` 不授权恢复本地图片 OCR，亦不依赖已删除的历史图片 OCR；已有视频 ASR 与视频抽帧 OCR 仍保留。

图片关键事实、方法、数字、条件可以进入同一 Core，并关联图片证据；仅在图片说明中记录、Core 中遗漏，不满足底稿与卡片共同复用目标。原文和已有完整读本保留，不以摘要替换。不新增“机器读图”“未经人工核对”等前台泛化标签，不增加内容旁的原件入口；实质缺失、错误或不清仍须如实处理，后台真实来源与核验状态不因此省略或改写。

## 5. Schema 之外必须验证的规则

下列是采用 v0.2 时必须完成的校验，不是本次已实现的生产能力：

1. **身份与输入一致**：图片属于同作品、同快照，别名映射到本次实际发送的字节。相同字节的来源别名不丢失，不跨作品、跨图或跨版本拼接；隔离验证已核对原五篇的正式媒体投影与22图实际字节，真实复测前又只读核对当前底稿版本未变、无restricted材料；这不是全部权利、撤回路径或生产接入的验证。
2. **快照范围准确**：快照身份须覆盖实际使用的图片及版本、顺序资格和已知缺口，不能命中仅含文字的旧缓存冒充图文结果。隔离输入已使用单独标识的实验快照；正式底稿修订号与文字输入快照不是同一层，生产快照算法未改。
3. **引用、整理与内容分别检查**：单元、标签、摘要及证据引用须存在；人物枚举关系、标签跨单元类型与重复标签仅作整理提示，不因这些细分问题拒绝整篇，不自动改写模型内容。内容另看是否抓住整篇用途、有无明显曲解、关键用途遗漏、无依据添加或明确第三方观点混淆；不审计原帖真实性，不要求穷尽界面细节。文字匹配、图片非空和哈希一致只证明相应结构／来源事实，不认证语义。
4. **不补造缺失**：未取得、失败或关键部分不清时不产对应事实。只选了部分材料或已知缺图时不宣称完整覆盖；逐图处理及缺口沿实验材料记录保留，不往 Core 新加重复字段。
5. **资格按用途重核**：来源权限、撤回与用途资格仍按当前时点核对，缓存命中及历史可读都不授予继续展示或外发原材料的权利；遵守[安全与领域约束](../agents/safety-invariants.md)。

Schema 只验证结构、范围、枚举及启用的格式。它不能核实 UUID 是否对应真实图片、哈希是否来自实际字节、引用是否存在、说话人是否正确或内容是否真实；生产持久化与消费链也未在本次验证。
