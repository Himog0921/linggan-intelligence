## 0. 先区分决定、设计与事实

### 0.1 信息权威与冲突处理

1. 本次用户明确确认的方向：进入评论研究先看到整体看板；继承高共鸣、高冲突、用户需求、解决方案、金句、故事和社区热词；从概览深入原声和用户问题；沿情报逻辑建设，不导向选题或内容生产。
2. 本合同冻结这些方向的产品表现、数据口径和工程边界。新增的数值门槛、布局尺寸、性能目标均是**首版实施默认值／验收目标**，不是已被真实数据验证的行业标准。
3. 当前真实实现以 Agent 读取到的运行代码、数据库、接口、浏览器为准；现有产品行为不自动等于目标规范。冲突应记录后改进，不能不声不响覆盖合同。
4. 最新用户决定优先于旧设计稿。例如 v7 的旧 `.drawer{top:0}` 不能推翻本轮“抽屉从面包屑下沿开始，不遮挡一级导航”的决定。
5. 不把前文“领先一代”“大多数产品只有孤立文本”等表述当作已证实的竞品事实。本轮构建的是可衡量的差异化能力，不承诺独创算法或竞争领先。

### 0.2 本次能核实与不能核实的内容

| 项目 | 来源及状态 | Agent 必须采取的处理 |
|---|---|---|

| 真实模型语义质量、实际吞吐与费用 | 尚无本次测量 | 必须试跑与评测；合成测试不能替代 |

### 0.3 完成定义

完整交付不是“有四个 Tab”。必须跑通：

> 真实评论进入 → 原声可检索 → 上下文可查看 → 基础清洗 → 多维分析 → 稳定的问题归并 → 共鸣／分歧与社区词 → 样本变化 → 每日观察 → 原声回溯与人工更正。

模型缺失时原声与已存有效研究结果可用；分析失败时已有事实可用；数据不足时显示不足，而不是编造结论。分包是开发顺序，不是把已确认能力无限延期。

## 2. 最终信息架构与用户路径

```text
语料 → 评论研究
       │
       ├─ 概览（默认）
       │    评论规模与分析覆盖 / 用户声音走势 / 值得注意的观察
       │    六类研究视角 / 用户问题 / 社区热词 / 代表原声
       │
       ├─ 原声
       │    检索、筛选、收藏 / 评论表格 / 右侧评论检查面板
       │
       ├─ 用户问题
       │    稳定问题列表 / 问题详情 / 观点与经历 / 来源与原声
       │
       └─ 每日观察
            本次新识别的观察 / 固定批次结果 / 研究设置与运行记录
```

主路径：概览发现 → 进入对应筛选结果或问题 → 阅读评论与作品上下文 → 收藏或纠正 → 返回原位置。

研究动作：以「研究当前结果」「研究这篇讨论」为主；选择评论是试跑和精确限定范围的辅助手段，不能删除这项能力。

### 2.1 旧功能去向

| 旧入口／功能 | 新位置 | 数据处理 |
|---|---|---|
| 原声浏览 | 原声 | 复用记录、搜索与评论 ID |
| 问题分组 | 用户问题 | 尽量保留现有组 ID；改名不等于重建 |
| 语料资产 | 原声 →「仅收藏」 | 保留收藏人、时间、备注及历史来源；旧 URL 重定向或带筛选打开 |
| 每日研究 | 每日观察 → 研究设置／运行记录 | 调度与预算能力保留，不藏到找不到 |
| 有效信号数／信号密度／信号质量分 | 不进入概览主体 | 如确需排查，收进运行详情；不能另造复合分数 |
| 需求复核队列 | 问题详情与原声的纠正动作 | 不要求用户日常先审核一批卡片才能研究 |
| 资产使用结果／待晋升／使用许可 | 本轮不增加 | 历史字段只读保留；收藏不等于获得公开发布许可 |

旧收藏没有可解析评论 ID 时，以「历史收藏」显示并保留出处文本，不伪造关联；仅未解析项不计入可回溯评论统计。

## 3. 全模块统一的范围、时间与计数

这是所有 UI 和算法共同依赖的合同。不能每个组件自己解释“最近”“总量”“增长”。

### 3.1 查询范围

概览、原声、用户问题继承同一领域、作品范围、时间范围、研究视角和搜索条件。进入每日观察时继承领域，但以明确的批次日期／批次范围为准；必须显示差异，不把“最近 30 天”套成一个批次的定义。

默认：最近 30 天，按**首次观察时间**；截止当前返回的 `as_of`。可以选择 7 天／30 天／自定义。原声额外支持「按评论发表时间」，但只有真实可解析发表时间的评论进入对应筛选。

统一逻辑查询对象（不是指定代码类型／数据库列）：

```text
scope = {
  workspace_or_current_scope, domain_id?, work_ids?,
  from, to_exclusive, time_basis,
  search_text?, lens_filters[], problem_id?, term?, bookmarked_only,
  sort, cursor?, page_size,
  result_revision?, as_of
}
```

- 领域安全隔离必须在后端执行。作品归属、评论问题主题是不同概念，不能用作品标题直接决定评论问题。
- 搜索提交可按 Enter；「查询」可保留为单一搜索按钮。不要同时存在多个含义重复的刷新／查询按钮。
- 视角之间默认 OR；视角与领域、作品、时间、问题条件之间 AND。高级多标签 AND 非本轮必做，不擅自追加复杂查询语言。
- 一条评论匹配多个标签、多个语义片段或多个关键词，结果列表只出现一次。
- 搜索结果默认按首次观察时间倒序；提供点赞倒序。语义相似排序只有实际实现且测量后才能显示。
- 标题／正文／OCR／ASR 的跨字段搜索复用已有语料搜索；若本次查询包含这些字段，显示「命中作品正文」等命中位置。不能把“命中所属作品”谎称为“评论包含此词”。
- 点击统计数字、词云、问题数量，必须带上同一查询范围。不能概览是领域 A，详情突然变全库。

### 3.2 时间口径

| 时间 | 用途 | 禁止事项 |
|---|---|---|
| `published_at` + 原始时间文本 + 解析精度 | 评论真实发表时间；不可靠时只显示采集时原文 | 用今天解释一周前采集的“15 分钟前” |
| `first_observed_at` | 本库第一次观察到评论；默认规模／趋势依据 | 每次重复采集或迁移重新入库都刷新成“新评论” |
| `last_observed_at` | 本次点赞等快照的新鲜度 | 当作评论出生时间 |
| `analyzed_at` | 研究处理进度、每日新研究结果 | 当作用户讨论突然出现的时间 |
| `context_version`／内容指纹 | 追踪作品／父评论上下文变化 | 仅点赞变动触发全量语义分析 |

所有时间存储按现有规范，日历展示和批次规则用 `Asia/Shanghai`。区间统一为 `[from, to)`。旧数据没有可靠首次观察时间时保留 `legacy_import` 来源与导入时间；不并入“本库自然新增”比较。

“昨天 21:00”无法恢复绝对时间时，列表写「采集时：昨天 21:00」，详情显示采集时刻。年份缺失不能悄悄猜成当前年。

### 3.3 计数定义

| UI 字段 | 定义 |
|---|---|
| 评论 | 当前范围内去重后的规范评论 ID 数；不是标签数、分析片段数、任务数 |
| 来源作品 | 这些评论实际关联的 distinct work ID 数 |
| 已分析 | 当前有效分析版本产生了可读取结果的 distinct comment ID 数 |
| 待处理 | 分别保留待清洗、待分析、需补上下文、失败等真实状态；首层不展开全部 |
| 分析覆盖 | 已分析 / 当前可分析评论。旁边能展开看到低信息、异常、待清洗及上下文待补数 |
| 某类评论 | 与该类有效结果有关的 distinct comment ID 数；多标签不要求相加等于总评论 |
| 问题评论数 | 与该问题有关的 distinct comment ID 数；同评论含两项诉求可进入两问题 |
| 高共鸣／高冲突视角数量 | 实际作为对应现象证据的评论数；不是问题组数，不把同组所有评论一概贴标 |
| 点赞 | 最新已观察到的值，0 与未知分开；不是实时平台值 |
| 收藏 | 当前工作区／用户按现有权限定义的收藏关系数，不复制评论 |

平台系统自动总结等已确认角色仍保留在原声，但默认不作为用户需求或群体支持证据。作者回复可作解决方案／对话一方展示，不能把作者对多人的重复答复当成多个独立用户支持；角色未知不猜测身份。

未知返回 `null` 与原因；真实零返回 `0`。所有聚合响应携带范围、时间口径、版本、数据截止时间与分析覆盖；不在客户端凭当前页 20 条推算全库。

### 3.4 数字与详情一致

以同一聚合版本和过滤器生成计数与下钻条件。若用户下钻时后台版本已更新，明确显示「结果已更新」，给出新数值；不得展示“186 条”却无解释地只查询另一范围的 97 条。

不为每次鼠标点击建全新事件系统。优先复用已有快照／版本机制；至少保证一个响应内部在一致读事务下取得数据，并有可识别的 `result_revision`。

## 4. UI 总规范：先锁画面，再分包实现

### 4.1 视觉语言

复用 v7 的白底、中性灰、signal orange-red。橙红用于当前导航、关键观察与主动作；六类标签不各分配一种高饱和颜色。

已核对的参考 token：

```text
surface-canvas = white; text-primary = ink-950 (#0b0f12)
text-secondary = ink-500 (#5f6a71)
text-signal / signal-fill = flame-600 (#c63214)
signal-mark = flame-500 (#f24a23)，只作色块，不用作小字
sp-3/4/5/6/7 = 8/12/16/24/32px
fs-300/400/500/600/700 = 13/15/17/21/27px
header-h=72px，context-h=46px（参考值，生产按共享壳层实测）
```

字号职责：页面标题 21px；区块标题 15–17px；原声正文 15px；表格与元数据 12–13px；主要规模数字 27px，不做巨型 KPI。

不引入玻璃拟态、大渐变、每块重边框、词云随机彩虹、装饰性 3D。点阵／ASCII 只沿用已有壳层材料，不铺到评论文字背后。

### 4.2 页面结构和尺寸默认值

- 复用现有全局导航、面包屑、语料侧栏，不借本任务重设计其他模块。
- 内容左右边距 24px；段落区块间 24–32px；网格列间 24px。
- 页面头一行：`评论研究`，右侧 `时间范围 / 研究设置 / 刷新`；模型未配置时只出现紧凑状态与设置入口。
- 下一行四个 Tab；再下是单行范围摘要及必要过滤。
- 桌面可用内容宽度 ≥1100px：主要双栏为 7:5；900–1099px：6:4；不足 900px 堆叠。不能用缩小正文换取强塞两列。
- 桌面 1440×900 与 1920×1080；紧凑 1280×800；缩放 125%／150%；窄宽 768px 都要验收。
- 所有纵向列表可控；正文超过三行折叠，详情展开。不要再把很长的故事占满一屏表格。

| 元素 | 点击结果 |
|---|---|
| 评论 N／来源作品 W | 原声，同范围；作品数入口带来源分组或作品筛选，不跳到无关全库 |
| 待处理 P | 原声，处理状态过滤；可展开具体原因 |
| 六类数字／名称 | 原声＋对应 lens，保留时间与领域 |
| 走势某天 | 原声＋该天区间＋当前 lens；数量／占比使用同批有效结果 |
| 值得注意 | 对应用户问题详情；非问题类观察则进入精确原声证据集 |
| 词云词 | 原声＋规范词与原形匹配规则；显示命中片段 |
| 代表原声 | 右侧评论检查面板 |

**没有可比数据时，标题是「值得注意」，不是强制“正在升温”。** 可以展示“跨作品反复出现”“本库首次观察到”“单篇讨论出现分歧”，但须满足各自规则。

### 4.4 P1 六种状态

| 状态 | 呈现 |
|---|---|
| 原声存在、模型未配 | 评论数与来源数照常；词频可计算；分类／问题处显示“尚未分析”而非0；一个配置入口，不铺六张空卡 |
| 已分析一部分 | 显示覆盖 A/E；先呈现已有结果；趋势比较不满足覆盖要求则降级，不隐藏原声 |
| 没有评论 | 简洁空态＋去采集／清除筛选；禁止演示数据自动填充 |
| 有分析、没有变化 | 展示“本次未发现符合规则的变化”与已有问题；不强凑3条观察 |
| 数据读取失败 | 保留已显示的上次结果并标记时间；可重试；不能显示0条 |
| 历史／模型规则不可比 | 保留两段原始计数，隐藏增长徽章，说明“统计版本不同” |

```text
□  最多3行正文              需求·故事     标题最多2行       12   09-06
   回复：父评论前半句        …+1          作者灰字                观察
□  …

已选 k 条  [分析所选] [收藏] [取消选择]（只在有选择时出现）

```

- 列宽：复选框 36px；原声剩余空间约 40–45%；标签约 15%；作品约 22%；点赞 56px；时间 104px。1280px 下可把标签并入原声第二行，不能让正文只剩十个字宽。
- 行高默认约 72px，上限由三行正文决定；短评论不强撑巨大空白。
- 表头固定在现有壳层与当前工具栏下；正文点击打开详情，作品标题打开作品详情；复选框／收藏点击不误触整行。
- 清洗状态不单独占一列；“待分析／需补上下文／失败”只在没有有效研究结果或需要用户处理时以灰色短文出现。
- 多标签显示最多2项＋`+n`；展开显示全部。收藏用图标＋可访问名称，不需要一列“晋升状态”。
- 选中条目限定到明确 ID；跨页勾选不能隐式变成“全选全库”。“选择当前筛选全部 N 条”必须明确二次动作和预计用量。
- 结果更新时不抢用户滚动位置；提示新增并由用户刷新。

### 4.6 P3：评论检查面板

桌面优先非模态右侧面板：宽 `min(680px, 可用内容宽度×0.55)`，至少保证正文可读。窄屏改为内容区内详情视图，不另开叠层。

位置：共享面包屑**实测底边**作为 top；bottom=0；面板只遮盖工作内容。使用共享壳层锚点／ResizeObserver 维护，不把 118px 写死作为所有屏幕永远正确的值。列表不被面板强行挤成不可读的小列；空间不足改为替换内容。

```text
┌ 评论详情                     [上一条] [下一条] [收藏] [关闭] ┐
│ 完整评论原声                                              │
│ 点赞（快照时间） · 一级／回复 · 评论发表／首次观察          │
│                                                          │
│ 对话上下文                                               │
│ 父评论 → 当前评论；必要时根评论                           │
│ [展开已采集的完整对话]                                    │
│                                                          │
│ 所属作品                                                 │
│ 封面缩略图  标题 / 作者 / 发布日期                        │
│ 原文片段或“AI摘要”明确区分                                │
│ 正文 / OCR / 转录的可用状态      [查看完整作品]            │
│                                                          │

│ 需求·故事… / 具体问题 / 观点对象与立场 / 对应原文高亮      │

└──────────────────────────────────────────────────────────┘
```

必要规则：

- 不从同一作品附近几条评论猜测父子关系。parent ID 缺失就显示“父评论尚未采集”。
- 初始只显示直接父评论、必要根评论；完整展开只读取已存线程，不自动发起采集。
- 不把“@某人”或“回复”字样当成可靠的平台回复关系。
- 作品点击优先复用已有作品详情路由。若当前产品只有抽屉，在同一个面板内替换内容并提供返回，不叠第二个抽屉。
- 打开时焦点到面板标题；关闭返回触发行；Esc 关闭；上下条沿当前列表排序。非模态面板不能设置 `aria-modal=true` 后又允许操作背景。
- 仅当确认／模型配置是真正模态时才锁背景和焦点循环。参考 W3C APG [S4]。

### 4.7 P4：用户问题列表与详情

列表使用表格／紧凑条目，不用大词云代替问题理解。

```text
[搜索问题________________] [领域／时间继承] [排序：评论数 ▾]
问题                           评论    作品   样本内变化       最近原声
家庭干预多久才能看到变化       n       w      +x个百分点/—    “……”
……
```

“用户问题”是明确问题／困难／诉求的稳定归并。故事、金句、观点也可以关联这个问题，但不强迫每个故事都变成需求。尚无合适归属的评论保留未归并，不丢弃。

问题详情是内容区路由／子视图，不与评论面板争夺同一层级：

```text
[← 用户问题]                [收藏问题] [研究相关评论] [更多：更名／合并]
问题名称
n条原声 · w篇作品 · 当前范围 · 最近观察 · [统计口径]

[真实用户怎么说：2–3条代表原声，保留不同观点]

左 7列                                      右 5列
问题的具体差异（最多5项）                   样本内走势
[场景／约束／追问] + 原声数                 按日计数或占比
观点／经验                                 来源作品 Top5
有真实分歧才出现对照                        集中在单篇时明确显示

相关原声表格（复用 P2，按此问题过滤）
```

- 一个问题的“子问题”必须有真实区分点；AI换个说法不能自动变新层级。首版最多一层可读细分，禁止无限树。
- 对照列的标题是具体立场，不是固定“支持／反对”硬套所有问题；“担心风险但愿意尝试”不得自动当作反对。
- 问题更名不换 ID；合并有旧 ID 别名／重定向；拆分需先检查证据归属，首版显式人工确认，不能每天自动打散历史。
- 统计显示“评论数”，不得写“有 n 个家长／n 个人在问”，除非真有可靠去重身份且产品明确需要。


- 可以查看任何已有日期，不把“今天”固定成浏览器当前时间的唯一视图。
- 历史补跑的结论写“本次新分析到的历史评论”，不称“今天新出现的用户需求”。
- 尚未启用：保留历史结果；一个紧凑提示与「研究设置」，不整屏任务面板。
- 没有发现：显示“本批完成，未发现符合规则的新观察”；完成数量仍可查，不生成凑数长文。
- 失败但部分成功：显示成功部分，失败可单独重试；不能把成功结果回滚为不可见。

### 4.9 P6：研究设置与研究确认

「研究设置」复用一个弹窗，含：当前分析模型、自动研究开关、23:00说明、每批数量／调用预算、历史补跑入口、失败处理说明。模型供应商配置留在个人设置，不在研究页重复存 API Key。

「研究当前结果／研究这篇讨论／分析所选」打开同一确认弹窗：

- 范围：多少目标评论、多少来源作品；明确包括什么、不包括什么。
- 已分析／待分析／上下文未齐／低信息／异常数量。
- 默认只处理新增和需要更新的目标；“重新分析有效结果”是单独显式选择。
- 显示实际模型、数量上限和费用估计依据。缺价格写“费用未知，可按条数／token限制”，不显示0元。
- 准备上下文可以带入未被选中的父评论，但标明仅作上下文，不扩大统计目标。
- 点击确认前冻结目标 ID、查询范围与版本；取消不创建任务、不扣预算。
- “保存配置”不调用模型；“测试模型”是合成请求；真实评论试跑必须是单独确认动作。

## 5. 六类研究视角与社区语言：语义合同

### 5.1 分类不是互斥桶

一条评论可含多个语义片段，也可有多个标签。首版把语义片段保存在现有分析结果的数组中即可；不要为了“原子洞察”新建一个通用实体平台。

| 视角 | 纳入条件 | 必须排除的误判 | 基本产生方式 |
|---|---|---|---|
| 用户需求 | 明确提问、困难、期望结果、未满足诉求 | 只要出现问号；复述作品标题；把询问经历强推成购买意图 | LLM结合原文与上下文 |
| 解决方案 | 用户描述具体做法、尝试步骤或方法 | 将用户经验认定为已证实有效；广告口号当效果证据 | LLM提取做法＋用户自述结果 |
| 故事 | 具体人物／经历／过程／场景 | 普通知识概述、平台自动总结 | LLM识别叙事片段 |
| 金句 | 原文有鲜明、凝练、代表性的表达 | 模型改写成更漂亮的句子；凭空制造引用 | LLM提出候选，必须精确回原文 |
| 高共鸣 | 同一经验或判断被多条原声重复支持，并有可解释的重复范围 | 仅因为很长、正面、点赞高；把“同一议题”当“同一观点” | 程序聚合语义等价证据，互动作辅助 |
| 高冲突 | 同一明确议题／命题有相互不兼容的真实立场证据 | 正负情绪；担心与支持被硬分对立；同一人在犹豫被当多人争论 | LLM识别命题与立场＋程序验证结构 |

多标签示例只说明机制，不预判真实评论：一个用户叙述尝试某方法的经历，可同时属于「故事／解决方案」；是否高共鸣要等群体证据，不允许单条 LLM 自封。

所有界面保留用户认可的六个中文名称。后台允许按「表达类型／群体反应」分开存储，但不再给用户增加必须学习的两套导航。

### 5.2 首版高共鸣规则（校准前的产品默认值）

高共鸣首版限定为**跨作品反复表达同一经验／判断**：同一可验证含义至少5条有效原声、至少3篇作品，并排除纯复制刷屏造成的重复。此门槛是防止单例被放大，不是统计学显著性标准。

同时展示：原声数、去除完全复制后的表达数、来源作品数、最新点赞快照。用户可以按点赞排序查看高赞评论，但高赞本身不赋予高共鸣资格。

若旧系统已有不同共鸣规则：T0记录，迁移标签标记 `legacy`；不能悄悄把旧“高赞”结果当本规则计算结果。

后续可评估单作品内明确附和链，但须区分「单篇共鸣」与跨作品复现，本轮不强行用一个分数混合。

### 5.3 首版高冲突规则（校准前的产品默认值）

必须满足：

- 存在同一个明确的命题／决策对象；
- 至少两组相互不兼容的立场，而不是仅情绪不同；
- 每组至少2条不同有效原声；
- 跨作品至少2篇，或同一已采集回复线程里存在明确互相反驳的证据；
- 若只来自一篇作品，UI写“该作品内存在分歧”，不称社区普遍冲突。

不推断缺失的对手观点；无足够证据则保留「有分歧候选」在详情，不在概览伪装为高冲突。

立场检测针对特定对象，不等于情绪分析。SemEval 的任务定义可用于验收标注设计 [S5]。

### 5.4 社区热词

词云继承，但必须可查证：

1. 输入是当前范围的已清洗评论文字，不是作品标题集合，更不是模型自由生成的概念词。
2. 默认按“包含该词的不同评论数”确定字号；单条评论写20遍只贡献1。每词记录原形、规范形式、命中评论数、作品数。
3. 中文分词、领域词典与短语候选结合；优先复用旧词云和词表代码。保留「A娃」「执行功能」等领域词；@名称、链接、纯表情不进入默认词云。
4. 首版最多30词，字号15–32px，横排，不随机旋转；相同数据位置确定，不每次刷新乱跳。文字列表是可访问替代视图。
5. “高频”“本库新见”可显示；“升温”必须遵守第8节的可比窗口规则。
6. 一键屏蔽词属于当前领域词表配置，不改评论原文；保存规则版本，更新词频，不重跑所有LLM。
7. 新词只能说“在可用历史中首次观察到”；导入老评论、分词词典升级不能制造社区新词事件。

## 6. 数据与职责：关系清楚，不新增抽象平台

### 6.1 最小逻辑数据

下列是必须表达的信息，不规定一项一张表。T0输出“现有字段 → 逻辑字段”映射，缺什么才补什么。

| 逻辑信息 | 核心字段／规则 |
|---|---|
| 规范评论 | 稳定ID、原文版本、来源平台／作品、父评论ID、观察时间、发表时间精度 |
| 观察快照 | 点赞与采集时刻；真实角色，如作者回复／普通评论／平台系统评论／未知 |
| 清洗结果 | 规则版本、派生文本、状态、原因、原文映射 |
| 语义结果 | 目标评论、上下文指纹、标签、问题候选、立场对象、引用片段、模型／prompt版本、状态 |
| 问题 | 稳定ID、名称、定义、边界、典型／反例、别名、成员关系、生命周期记录 |
| 聚合／观察 | 范围、时间口径、计数、分母、比较状态、算法版本、证据ID集合或确定性筛选 |
| 收藏／人工更正 | 引用原对象，动作人、时间、旧值、新值、原因、可撤销关系 |
| 研究批次与调用 | 冻结目标集、版本、预算、执行尝试、部分失败、未知用量、暂停状态 |
| 向量（有必要时） | 语义输入指纹、模型ID与版本、维度、对象ID；不同版本不能直接混算 |

不另建 Evidence Graph 数据库。评论→作品→父评论→语义结果→问题→观察之间的外键／关联即足以承载本轮所说的“上下文关系”。

### 6.2 原文与清洗

- 原文永久保留；编码、空白、重复标记、表情占位、链接处理写在派生文本。
- 不按长度粗暴删短评论。「哪里有」「怎么做」有可能是需求；纯@、纯表情可作为低信息保留。
- 相同平台评论重复采集归入同一规范对象；不同人写相同文字仍是不同原声，但计算群体支持时另报复制重复，不能当成无限独立支持。
- 不用用户名／昵称推断跨平台同一人，不推断隐私属性。已知平台作者角色可区分，但未知保持未知。
- 清洗状态区分 `待清洗／可分析／需上下文／低信息／异常`；“需上下文”不必一律阻塞，已有作品／父评论足以理解时可以分析并记录缺口。
- 无上下文确实无法判断时返回“含义不确定”，不强行归类，也不阻断同包其他评论。

### 6.3 上下文组装

```text
目标评论原文（不可缺）
+ 已有直接父评论／必要根评论
+ 所属作品标题与正文相关片段
+ 已完成OCR／ASR的相关片段
+ 作者角色、对话关系等真实元数据
→ 一个冻结、可回查的上下文包
```

作品上下文只帮助理解，不得替代评论本身成为“用户表达”。例如作品写“需要治疗”，评论问“吃药了吗”，不能据此直接命名为“用户希望开始用药”；在证据不足时应保留“询问是否已经用药”。

同作品分包的意义是复用上下文，不是强制把一篇所有评论塞进一个超长请求。达到预算／上下文限制时拆分目标；父评论可作为上下文重复带入，但不重复记为新分析目标。

不能简单拼接整篇长正文、全部OCR、全部转录让它压过评论向量。选取相关原文块，保留原块ID；缺口与截断状态显式记录。超长单条不能静默截断后宣称完整理解。

### 6.4 职责分工

| 执行方 | 职责 | 禁止 |
|---|---|---|
| 插件 | 采集真实页面事实 | 清洗决策、问题归并、AI分析 |
| Rust后端／既有worker | 入库、规范ID、清洗调度、上下文组装、预算、幂等、统计、验证、API | 把密钥返回前端；在HTTP请求线程做全库聚类 |
| 已有Pi适配层 | 经验证的模型调用与输出接收 | 自行创建任务、扩大数据外发范围、假称支持未接通接口 |
| 向量／聚类实现 | 相似候选召回、未归并候选分组 | 仅靠余弦相似度断言同一需求；孤立预测冒充新簇发现 |
| 前端 | 查询、过滤、解释、浏览、确认、纠正 | 重算全库事实、私自拼模型请求、失败回退mock |

嵌入模型是独立能力要求：当前Pi或供应商是否支持 embeddings 必须实际核验。聊天调用成功不代表支持向量接口。需要补配置时仍复用模型设置弹窗，增加真实可用的用途选择，不新造一个向量供应商管理平台。

## 7. 分析管线与技术差异化的具体实现

### 7.1 管线

```text
评论入库
  → 清洗与上下文可用性判定
  → 按作品组织目标包
  → LLM提取表达类型／问题候选／立场／引用
  → 程序逐条校验并保存可用结果
  → 语义向量召回已有问题候选 + 候选归并判断
  → 更新稳定问题成员关系／未归并候选
  → 程序计算共鸣、分歧、词频、样本内变化
  → 生成有证据的观察卡
  → 同一结果服务概览、原声、问题详情、每日观察
```

不额外搭建六个独立“引擎”。差异化来自稳定关系、少误判的语义理解、增量更新和可验证变化，不来自层数。

### 7.2 LLM输入／输出合同

输入只包含：目标local ID、对应文本块、必要上下文、明确任务与允许枚举。评论内容全部视作数据，不执行其中要求“忽略规则”“调用工具”的指令；分析调用不授予搜索、文件修改、外部工具权限。

示意输出（目标结构，必须映射已有adapter；不是要求原样建表）：

```json
{
  "items": [{
    "local_id": "c01",
    "outcome": "interpretable",
    "labels": ["need", "story"],
    "problem_candidates": [{
      "name": "完成任务前很难开始第一步",
      "meaning": "用户描述启动困难，而不是不知道做什么",
      "evidence": [{"block_id": "c01.raw", "quote": "知道要做，就是开始不了"}]
    }],
    "stances": [],
    "memorable_quotes": [],
    "context_missing": [],
    "uncertainty_reason": null
  }]
}
```

约束：

- 模型不生成数据库UUID、评论数量、趋势百分比、点赞数、来源作品数。
- 只输出输入存在的local ID；一个目标一个主结果；未返回项单独标记，不能猜为成功。
- 引用必须匹配指定原文块。程序把精确文本映射回原文区间；多个相同片段不能随便选第一个，应补充块ID／出现位置或判为不明确。
- 原文坐标在持久层采用一致规范；如用Unicode字符区间，必须测试Rust字节与JS UTF-16差异，不能直接互用偏移。
- 标签、问题和立场允许“不确定／没有合适结果”；拒答、截断、缺项、格式错误分别记录。
- 格式校验通过仅代表可读取，不等于语义正确。引用存在也不代表引用支持结论，必须通过评测与人工纠正检验。
- 允许单条失败、其余结果保存。不是一条引用错整篇作品所有结果作废。

### 7.3 问题的稳定归并

首版落实“增量归并＋稳定ID＋别名／变更记录”，不一开始自动运行复杂分裂合并网络。

步骤：

1. 对已验证的问题候选生成语义输入（具体问题＋必要场景／限制），而不是只嵌入“A娃”“教育”之类泛词。
2. 在同一合法领域／范围内召回最多10个相近稳定问题；向量相似仅用于候选召回。
3. 依据问题定义、适用场景、典型证据和反例判断归属。明显匹配走已校准规则；边界模糊使用LLM定向复核；仍不明确保留未归并。
4. 未归并候选按批次聚类、抽查并命名；首版建议≥3条评论形成可浏览问题，单作品问题照样可用但标明“仅来自1篇作品”，不得称跨作品群体需求。单例保留在原声，用户可显式确认成一个待持续观察的问题，不强行凑证据。
5. 新增成员不更换旧问题ID；更名保留成员；人工合并生成别名重定向；拆分先保留历史版本与成员映射，再切换。
6. 不能“昨天20组、今天23组”就把差集当新问题。新问题先查历史别名／旧成员／近邻定义。
7. 对明显重叠的问题、内部语义混杂的问题，系统可自动提出合并／拆分建议，放在现有问题详情的整理动作内。必须附定义差异、成员原声和反例；用户确认后执行。算法负责提出可验证建议，不自动改掉用户已收藏的问题身份；不新增每日必审队列。

算法选择：先复用已有向量与聚类实现。若没有，优先评估现有PostgreSQL内的向量能力，而不是默认新增外部向量数据库。pgvector区分精确检索与近似索引，后者速度与召回要测量 [S1]。

BERTopic已有在线建模及模型合并路线，可作为离线实验基线，不强制改成Python服务 [S2]。HDBSCAN `approximate_predict` 的既有簇分配不能独自承担发现新簇；需要未分配候选处理 [S3]。

### 7.4 增量失效规则

| 变化 | 需要重新做什么 | 不需要做什么 |
|---|---|---|
| 新评论 | 清洗、语义、归并、局部聚合 | 全库重跑 |
| 同评论再次采集，仅点赞变化 | 互动快照、相关排序／展示 | LLM语义重跑 |
| 评论文本变化 | 此评论清洗与语义，影响的关联聚合 | 无关作品重跑 |
| 父评论补到／作品OCR或ASR到达 | 找到依赖此上下文且已标记缺口的结果，重新评估受影响目标 | 所有评论全部重跑 |
| 模型／prompt升级 | 显式创建新版本与评测；授权后重处理选定范围 | 升级当天静默全库收费 |
| 人工改标签／归属 | 当前有效关联、聚合和问题展示 | 修改原文；将新计数写成新用户需求 |
| 词典变化 | 新版本词频／词云 | 重新调用所有LLM |
| 删除／撤回权限 | 撤销可见关联、缓存与聚合 | 保留泄露原文的旧导出或无权限详情 |

后台缺口任务以内容指纹去重；派生文本每完成一块都触发全篇重跑不可接受。允许短暂合并同一作品的连续更新，只执行最终必要版本。

## 8. 变化检测：把“有趋势图”变成能解释的观察

### 8.1 三件事必须分开

1. 本库新增采到多少评论：观察规模变化。
2. 本次新分析出多少已存评论：处理进度变化。
3. 在可比已观察样本中，某种表达的占比和来源分布怎样变：样本内讨论变化。

任何一项都不自动等于市场需求增长。尤其当前每作品默认最多约30条样本，不能声称完整看到了平台讨论。

### 8.2 首版比较口径

- 主图默认显示当前选择范围按日的首次观察评论数；分类图只统计有有效结果的评论，并明示分析覆盖。
- 自动变化观察使用**最近7个完整北京时间自然日**对比之前7个完整日。当天尚未结束的数据可浏览，不进入这组自动比较。
- 每日23:00批次是执行截止，不改变自然日统计口径。09-07 23:00批次的完整日比较截止09-07 00:00。
- 领域、采集规则、分析合同／统计版本需可比。模型混用或中途改规则无法统一时，显示计数但不贴增长徽章。
- 初始启用保护值：两窗口各有至少30条可分析样本；已分析覆盖各≥80%，差异≤10个百分点；每窗口至少5个有正常观察运行的日；当前问题≥5条原声、≥3篇作品。均为待评测校准的V1默认值，不是统计显著性保证。
- 仅达到上述条件仍不表示随机抽样。来源作者／作品构成变化须可展开检查；默认用“样本内占比上升”，不用“需求爆发”。

定义：

```text
n_w = 窗口内此问题的distinct评论数
N_w = 窗口内同一范围、有效版本已分析的distinct评论数
p_w = n_w / N_w
占比变化 = (p_current - p_previous) × 100，单位：百分点
```

示例：前窗10/100=10%，后窗40/400=10%。评论数×4，但样本内占比未变，**禁止生成“需求增长300%”**。

前窗为0，不计算无限增长；只在有效历史足够时显示“本库首次观察到”，否则显示“暂无可比基线”。

### 8.3 观察类型与触发

| 类型 | 触发与表达 |
|---|---|
| 反复出现 | 满足共鸣／重复表达规则，展示具体含义与跨作品证据；不需要虚构增长 |
| 样本内占比上升 | 满足可比条件且变化超过已配置门槛；首版建议至少+5个百分点，不用未经检验的显著性字眼 |
| 本库首次观察到 | 可用历史中没有同义旧问题／词；满足当前最小证据；导入与重分类不算新出现 |
| 来源扩展 | 新增来源作品／作者实际可识别；写“在本库更多来源出现”，不写“全网传播” |
| 出现分歧 | 有真实命题与相反立场证据；说明单篇还是跨篇 |

暂不做自动“消退”强判断：少采／漏采很容易造成假下降。完整范围可比且长期有覆盖后，作为后续受控规则纳入，不在本轮用红箭头补齐对称视觉。

候选排序采用可解释的分项／分级，不用神秘乘积评分：可比状态优先 → 跨作品覆盖 → 占比变化（适用时）→ 评论数；同分以稳定ID排序。用户能从观察看到触发原因。

### 8.4 观察卡的数据合同

每张卡至少包含：一句结论、观察类型、当前／对比范围、评论数、作品数、分母（占比类）、代表原声、下钻条件、规则版本、数据截止时间、必要局限。

叙述中的数值先由程序固定；LLM可改写解释，但不能修改数值。程序校验“3篇”与事实矛盾时拒绝发布该卡，保留基础结果。

“用户解决方案”只代表用户自述，不能把健康、教育方法自动写成专业有效性结论。模型解释不得生成医疗建议或夸大因果。

## 9. 每日运行、费用与并发

### 9.1 批次冻结

- 自动研究默认关闭；关闭不影响入库、清洗和原声浏览。
- 明确启用时记录启用时刻；默认只处理此后首次观察且可研究的增量。历史库存单独“历史补跑”，不能第一次23:00悄悄全库发送。
- 每日23:00冻结 `[上次cutoff, 本次cutoff)` 的待处理目标；启用后的首批从启用时刻开始。边界时刻恰好等于本次cutoff的评论进入下一批，不能重复或漏掉。
- 每条新增目标只进入一个以cutoff日期标识的自动批次身份；后到上下文使用原目标的补处理／显式补跑，不伪装成新原声。
- 某日机器离线：恢复后按原cutoff顺序建立缺失批次，受预算调度；不能每个worker各补一遍。过多积压汇总提示，由用户选择继续或调整额度。
- 冻结候选时记录“待清洗／待上下文”的目标，不因当时还不能分析就永远漏掉。满足条件后从既有待处理记录继续，不依靠下一天的新增时间过滤重新发现。
- 候选超过单批处理上限时，不静默丢弃剩余项。保留待处理身份与原始观察时间，后续调度继续；后批UI明确区分“本期首次观察”与“前批延后处理”，研究统计每条只计一次。
- 批次重启／补跑不能悄悄改变已冻住的范围或模型版本。额度变化只影响未派发工作；已完成结果、未知用量与来源批次关系保留。

### 9.2 幂等与状态

复用既有任务与调用记录。语义工作的去重键至少覆盖：工作区边界＋评论ID＋原文／上下文指纹＋影响语义的分析配置版本（含模型与prompt）。计划／批次关联这份工作，不直接进入去重键制造多份同义调用。显式重新分析创建可辨认的新尝试，不能靠改计划ID绕过去重。

- 同一目标重复请求不重复入库标签、问题成员或计数；被多个计划同时选中时，优先挂接已有有效结果或在途工作，不重复支付相同调用。
- 本地结果幂等不承诺远端模型收费恰好一次。
- 暂停阻止新调用派发；已发出的调用可能返回并计费，返回结果仍应接收。
- 失败重试只针对失败目标，成功项不再收费重跑；重新分析是另一种明确动作。
- 已发送但超时／断连且用量未知：标记未知、保留预算预留，禁止自动释放后无限重试；可通过供应商回执核对或用户明确接受重复计费风险后重试。
- 预留不能永久无解释占住额度：运行记录提供未知调用列表、人工核对／明确调整入口并留审计，不伪造最终账单。

### 9.3 模型与资源

- 连接测试、结构输出测试、真实语义试跑、生产分析分别验收；接口返回200不等于产品可用。
- 测试调用的10秒上限等历史参数不自动沿用为所有正式分析超时。正式超时、分包token与输出上限根据模型真实能力及合成压力测试确定。
- 解析上下文窗口、输出上限等能力必须来自已配置能力和可验证文档；未知时安全限制并明确提示，不编造无限容量。
- 同时存在采集工位、媒体任务和研究任务时，调用既有调度公平性／并发额度；不可在每个模块自建一个无上限队列。
- CPU密集向量／聚类不占用API事件线程；首先通过批量、索引和既有worker隔离解决，不以“技术领先”为由额外部署多套服务。
- 不为吞吐增加任何未经用户批准的第三方数据外发；分析请求中移除不必要的账号、昵称、链接token和密钥。

## 10. 人工反馈、评测与长期积累

### 10.1 用户动作

评论面板：改标签、移入／移出问题、标记“需上下文”、收藏、填写简短纠正理由。问题详情：更名、合并、显式拆分确认。

原文不变。人工修正优先于当前模型结果；默认后续重跑生成建议，不覆盖人工锁定归属。纠正触发关联聚合更新，不能伪装成新讨论信号。

不单独增加“人工审核平台”。日常操作在用户看到错误的位置完成，批量工具仅在确有需要时出现。

### 10.2 评测集

首版目标：选约200–300条真实评论，覆盖至少20篇作品；不足时使用实际数量并说明。另建60条以内精心设计的合成异常用例。采集样本以用户授权为限，不自动外发。

分层包含：短需求、纯@、纯表情、故事、方法、金句、反讽、否定、支持但担忧、父评论缺失、OCR未完成、跨作品同义问题、同词异义、作者／平台评论、旧时间文字、提示注入。

按作品分割校准与留出集，时间变化另用前后窗口回放。不能把相同作品相近评论同时放训练和测试再宣称准确率。

### 10.3 最小对照与目标

至少比较：

- B0：评论原文＋固定模型prompt。
- B1：必要上下文＋同模型＋逐条校验。
- B2：B1＋稳定问题候选召回／归并。

同一批评论、同一模型版本、同一可见范围；记录质量、延迟、用量。强模型复核可作为辅助，不替代人工留出集标准。

首版发布目标（产品目标，不是已测结果）：

| 项目 | 目标 |
|---|---|
| 结构引用映射、对象ID、计数与下钻一致 | 所有确定性测试通过；任何错误都修复，不以总体准确率掩盖 |
| 需求／方法／故事的分类 | 报告各类precision、recall、F1，不只报总体accuracy；核心类precision目标≥0.85 |
| 错误归并 | 留出集审查中≤5%；同时报告未归并率，不能靠拒绝全部归并达标 |
| 高共鸣／高冲突观察 | 独立人工审查precision目标≥0.90；正例不足时标明证据不足，不虚构分数 |
| 上下文增益 | B1相对B0减少明确的上下文错误；实际结果报告，不预设必胜 |
| 用户可用性 | 用户可从任一观察在两次主要点击内到达支撑原声，并读到必要上下文 |

低于目标不冻结整个模块：保留原声与已有可信功能；对应高级发现标记“试验规则”并关闭自动发布，修正后再启用。必须披露未达项，不能宣称完整完成。

## 11. 性能、可访问性与工程边界

### 11.1 性能验收目标

以下为目标而非硬件无关承诺；T0记录机器、数据库规模和已有预算。

- 当前真实数据集与10万条合成评论集分别测量：原声分页查询P95目标≤500ms、概览聚合读取P95目标≤1s，浏览器可交互目标≤2s（本地环境、说明冷／热缓存）。
- 100万条仅做扩容验证或抽样压测，不能在尚未测量时声称支持百万规模实时全量聚类。
- API响应按页返回，默认20可选50；不能一次把全库评论发给浏览器再筛选。
- 聚合按批次或增量更新；不因切一次Tab重做LLM、词频全量与聚类。
- 搜索索引、复合范围索引、向量索引以真实查询计划为依据。使用近似向量索引需有召回对照 [S1]。
- 所有测试隔离数据与生产，限制并发和外部费用。

### 11.2 UI质量

键盘可达、焦点可见、关闭后焦点返回；表格有语义表头；图表和词云有文字替代；颜色不是唯一状态编码；系统减少动效设置生效。

不可把高信息密度解释成11px正文。引用正文15px，元信息12–13px；对比度沿用已核实语义token并测试覆盖样式。

### 11.3 数据变更与发布

迁移必须在读取最新main后选择实际可用编号；已应用迁移不可重命名／改内容。先增量兼容、隔离验证，再按明确授权应用共享数据库和更新运行服务。

验收不只看开发分支：记录合并SHA、数据库迁移台账／hash、实际API及worker版本、接口、浏览器截图和真实试跑回执。详细流程见执行文档。

## 12. 不做什么，以及何时再考虑

本轮不引入：图数据库、单独信号分数服务、跨平台身份推断、情绪饼图、自动创作、全量评论补抓、统一宏大策略DSL、每次重聚全库、未经评测的自动问题拆分／合并。

以下不是遗漏，而是明确选择的实现深度：

- 动态问题：本轮交付稳定ID、增量成员、别名、人工合并／拆分记录；系统自动提出整理建议、人确认执行；完全自动改变问题身份必须有真实错误基线后再增强。
- 变化：本轮交付可比样本窗口、占比、来源解释和首次观察；因果归因、全网趋势不在能力声明内。
- 模型：本轮交付供应商无关的可校验调用与效果对照，不要求自训模型。
- 技术差异化：先证明上下文少误判、归并稳定、增量不重算、发现可解释；没有评测就不写“领先”。

## CI-RUN-002 · 2026-09-08 运行可观察性补充
