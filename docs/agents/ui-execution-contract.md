# UI 协作 Agent 执行合同

> 状态: 权威当前
> 最后核对: 2026-10-23
> 适用范围: 所有创建、修改、审查或验收 Linggan 用户可见 UI、前端组件、页面交互、状态文案、视觉资产和 UI 自动验证的 Agent
> 事实来源: AGENTS.md、docs/governance/、docs/design/、LIDS v7.0、当前 SCOPE、产品/数据合同、用户对 DESIGN-001/DESIGN-002/DESIGN-010 的授权，以及 DEC-0010（网页前端统一为 React）；LIDS-ALIGN-001 本次授权与对齐记录
> 冲突时以谁为准: 用户最新确认、AGENTS.md、真实运行/代码/合同、ACCEPTED 决策和当前 SCOPE；本合同不自行扩大任何授权

本合同的模块读取与本次设计采用状态统一由 [UI Agent 渐进执行标准](../governance/ui-design-execution.md)路由；具体字体、焦点和区域按最新 LIDS 分册执行。LIDS-ALIGN-001 只采用已确认设计原则，不修改业务代码；新候选按待审清单处理。

本合同让 UI Agent 成为已批准设计的执行者和问题发现者，而不是新的产品负责人、视觉总监、权限裁定者或事实来源。

## 工作包内连续执行

UI Agent 按[协作协议](../governance/agent-collaboration.md)在已授权工作包内连续执行。该协议统一决定风险分级、技术拆分、角色、审阅与合并；本文只补充 UI 的语义和验收要求。

进入代码前，在工作包摘要中简要说明下列内容；复杂改版使用矩阵，小型展示修正可用几句话并引用已有规格，无需新增独立计划/清单文件：

1. **表面地图**：此用户结果涉及的页面入口、页面壳、共享 Header/导航/按钮、面板和反馈位置；
2. **状态词典**：常用、空、失败、受限、部分、处理中和真实回执状态各自的用户含义，及禁止互相替代的边界；
3. **依赖地图**：共享组件、样式、数据合同、运行时回执与其他工作包的所有权；包内依赖由协调者整合，跨包授权冲突按协作协议升级；
4. **验收矩阵**：每个表面/状态怎样被自动检查、运行验证或人工验收覆盖。

这四项说明影响范围和证明方式，不要求四份重复文档。新功能、状态、权限或数据语义仍须有权威来源；包内协作与独立审阅沿用协作协议，不重新请求普通技术安排。

## 开始前必须完成

在写代码、设计文档、组件、页面、文案、截图或验收资产之前，Agent 必须：

1. 按协作协议确认工作包、风险通道、分支/worktree 与文件所有权；快车道免建 Issue/Claim；
2. 阅读 AGENTS.md；索引用于定位相关规格，只有运行/发布/跨包依赖核对才读 current-state；
3. 阅读 [../design/README.md](../design/README.md)、[../design/design-governance.md](../design/design-governance.md) 与 [../design/lids/README.md](../design/lids/README.md)；再按本次事项进入相关的 LIDS 分册：

   | 事项涉及 | 必读 |
   |---|---|
   | 任何视觉值 | [../design/lids/tokens.md](../design/lids/tokens.md) —— 注意 §2 是目标态、§3 是运行时现状，两者不可互相冒充 |
   | 背景、纹理、边缘 | [../design/lids/materials.md](../design/lids/materials.md) |
   | 页头或 Context Bar | [../design/lids/shell-zones.md](../design/lids/shell-zones.md) |
   | 承载真实数据的组件 | [../design/lids/data-boundaries.md](../design/lids/data-boundaries.md) |
   | 任何界面文案 | [../design/lids/language-policy.md](../design/lids/language-policy.md) 的 LANG-05 |
   | 想破一条规则 | [../design/lids/decisions.md](../design/lids/decisions.md) —— 先确认这条是否已被决定过 |

   **读 LIDS 时必须分清「规则已采纳」与「运行时已符合」。** 历史 DESIGN-010 的迁移描述只是当时快照；当前按各规则/页面的独立证据核对。字体与字号须另读 [typography](../design/lids/typography.md)，页面区域须读 [regions](../design/lids/regions.md)，未决差异按 review-items 处理；
4. 按任务读取相应的 LIDS Token、Primitive、Pattern、Agent guide 或原型审计；先定 `Token → Primitive → Component → Pattern → Page` 和 L1/L2/L3，后写任何视觉实现；
5. 阅读与本次 UI 事项直接相关的产品页面文档、已批准页面/组件/模式规格、数据/权限/行动合同和当前 SCOPE；
6. 在已有工作包摘要中记录范围、采用规则、分类、依赖、停止条件和验证；复杂 UI 参考 [UI 变更表](../design/templates/ui-change-manifest-form.md)，不重复生成同义文档。

没有完成上述任何一项时，Agent 只能做只读调查，不能开始修改。

## 前端技术与旧页面冻结（DEC-0010）

前端技术已由 [DEC-0010](../decisions/0010-web-frontend-react.md) 决定：所有正式网页统一为 `apps/web` 下的一个 React + TypeScript 应用，由 Axum 同源提供。推进顺序、目标架构与不留双轨的 R1–R7 规则见 [WEB-REACT-001](../plans/active/web-react-001.md)。

- 新页面与迁移中的页面只在 `apps/web` 实现；不得新增原生页面脚本、页面 `.html/.css` 或由 Rust 拼接的页面 HTML。
- 尚未迁移的旧页面冻结，只修阻断使用的缺陷；功能与改版排进 WEB-REACT-001 对应阶段。
- 页面迁移的同一 PR 删除它的旧实现与只服务旧 DOM 的测试，不设新旧切换开关。
- 视觉值只消费 `lids_tokens.css` 的 `--lgi-*`；页面样式用 CSS Modules。迁移期共享外壳的样式仍以 `shell.css` 为唯一来源，React 外壳与旧外壳使用同一份。
- 下文「不得将 LIDS 来源包的 React/Three/Blender 线路直接当作已获准实现」仍然有效：DEC-0010 决定的是前端技术本身，来源包的代码、目录、模拟数据与资产路线依旧不继承。

## 闭集执行规则

Agent 只可实现本次变更清单中明确引用、状态为“权威当前”的规则和合同。没有出处的内容不是“可自由发挥的空间”，而是未决事项。这里的闭集约束保护的是**产品语义和权限**，不是第一次列出的文件名单：为完成既有用户结果所必需的共享依赖由协调者先核对所有权、记录范围后整合；改变业务语义、权限或跨包授权时才升级。

Agent 不得：

- 以改善美观、提升完整感、统一体验或组件复用为理由增加页面、导航、功能、字段、状态、权限或行动；
- 把原型、旧系统、外部产品、截图、通用组件库或模型偏好当作实现规格；
- 把未知、未完成、受限、部分结果、已接纳、已授权、已执行和已获得结果互相替代；
- 用前端本地状态、toast、动画、模拟数据或乐观展示声称真实动作已经完成；
- 绕过后端合同、权限判断、数据来源或当前 SCOPE；
- 在代码中埋入长期设计例外，或顺手重构未列入本次事项的相邻页面。
- 写第二套颜色、字号、间距、圆角、阴影、动效、Header、Button、Status、Surface、Command Dock、Pattern 或组件实现；已有 LIDS 规则/正式 CMP 时不得临时另造。
- 将 LIDS 来源包的原型、模拟数值、运行文字、React/Three/Blender 线路、目录建议或场景视觉直接当作本项目已获准的实现。

## 变更分类

开始实施前，Agent 必须将变更标为展示、交互、状态/语义、权限/行动或混合，并按最高风险类别收集依据：

| 类别 | 继续实施所需的最小证据 |
|---|---|
| 展示 | 产品页面职责和已有设计规则已足以说明不改变含义 |
| 交互 | 页面规格和交互规则说明触发、可见状态与返回路径 |
| 状态/语义 | 产品页面与数据合同同时说明状态来源、用户含义和禁止暗示 |
| 权限/行动 | 当前 SCOPE、产品/权限/行动合同和后端回执边界已经明确 |

混合变更只要包含状态、权限或行动后果，就不得按普通样式调整处理。

## 必须停止并升级的情形

出现以下任一情况，停止受影响部分，保留已确认范围，并标记 DECISION_REQUIRED 或 SOURCE_INCOMPLETE：

- 需要新的视觉原则、布局规则、组件变体或页面结构，而现有规则未覆盖；
- 页面、数据合同、真实代码、当前 SCOPE 或用户确认相互冲突；
- 无法说明某个数字、文案、状态、图标、图表或按钮的事实来源与用户含义；
- 需要新增、扩大或隐藏权限、敏感材料访问、采集、Agent 调用、行动、发布或外部副作用；
- 需要真实数据、账号、截图/录屏、部署或其它尚未获得授权的资源；
- 发现共享文件涉及其他工作包的冲突授权，当前协调者无法在既定边界内裁定；保留有界补丁并报告 Mog。包内普通冲突由协调者按合同解决；新增产品语义、权限、行动或数据范围仍须升级。

升级时应提供简短决策包：已确认事实、缺少的决定、可选方案、影响范围、最小需要的用户选择，以及继续前不能宣称什么。不得把技术排查责任转给 Mog。

## 实施和验收

在已授权工作包内完成 UI 结果，技术拆分按协作协议执行。仅当相应事实改变时维护：

- 页面规格：页面任务或布局合同改变时，用 [../design/templates/page-spec-form.md](../design/templates/page-spec-form.md) 说明本页如何组合已批准规则；
- 组件规格：仅当组件成为真实跨页面合同，用 [../design/templates/component-spec-form.md](../design/templates/component-spec-form.md) 建立；
- 变更清单：复用 PR/工作包摘要；
- 验收记录：在同一回执中分开记录任务、状态、视觉和真实后果；复杂验收可参考 [验收表](../design/templates/visual-acceptance-form.md)。

每个真实数据页面还必须把 Truth、Coverage、Validity、Freshness、Operation 分开表达；`PARTIAL` 不等于 `INVALID`，未知不等于 0。没有真实合同的静态参考必须明确为 synthetic/not-live，不能借 LIDS 状态标签营造假运行感。

验收至少分别回答：

1. 用户能否完成页面承诺的任务；
2. 不同状态是否仍然诚实、可理解且不互相冒充；
3. 声明工作条件下的界面是否符合已批准设计规格；
4. 含动作的页面是否有真实回执，而不是只显示本地成功。

只有实际验证到的层才可写 VERIFIED；未运行、无环境、无权限、无真实输入或未部署时，必须写 NOT VERIFIED 并说明原因。

送审前按受影响状态自查。独立审阅时机与增量复核遵循协作协议；发现同类遗漏时，包内修复完整受影响范围并定向验证，超出授权的语义/权限变化才升级。

## 收口与交接

结束前，Agent 必须：

1. 核对差异属于工作包，直接依赖及所有权已记录，说明未解决依赖对用户结果的影响；
2. 按事实变化更新规格/索引；普通实现记录留在 PR，重要里程碑再更新 progress；
3. 运行设计手册结构检查、项目治理检查及与变更风险相称的其它验证；
4. 在 PR 中报告：已改内容、验证、真实副作用、已证明、未证明、例外和待决项；
5. 完成协作协议要求的审阅与交接，按既有合并/关闭授权执行；不推断部署与业务验收。

本合同不授权前端代码、真实数据、生产部署或业务验收；它只确保未来被批准的 UI 工作不会在模糊边界中发散。


标准件持续同步入口：[组件同步执行合同](../design/lids/component-sync.md)。UI 标准件修改须声明实现修正/共享标准/页面例外，按编号读取合同，再同步真实组件、展示与离线HTML；运行 apps/web 的 lids:check/lids:verify，不把合成示例当成CMP认证。当前 C16 的正式接入消费者为运营发布记录与创作列表；其他页面继续各自已合并实现，不宣称全站已接通。
