# 首批真实 Canary 前的采集控制合同

> 状态: 草案
> 最后核对: 2026-08-22
> 适用范围: ARC-001 `capture-control-contract`；首批真实 producer Canary（已确认同步纳入受限媒体）之前，Linggan 服务端怎样把研究需要变成有限、可停止、可追溯的平台访问
> 事实来源: Mog 已确认的领域不变量、`USER-DEC-02`、ARC-001、固定 V2 的已证明运行经验、现有 Capture/数据架构草案，以及 `media-lifecycle-contract` 草案；本文没有访问真实平台、账号、插件、数据库、媒体或第三方服务
> 冲突时以谁为准: Mog 后续的明确产品、隐私、成本与风险决定；`AGENTS.md`；后续获准的真实 producer 合同和可复现运行证据；ACCEPTED 决定

## 0. 本合同解决什么，不授权什么

Linggan 不能把 AI 或页面的“我还想知道更多”直接变成插件访问。真实平台访问会消耗有限工位、账号、网络、风险预算，并且可能接触儿童、家庭、医疗或可识别媒体。因此，系统需要一个服务端控制层来回答：

> **为什么现在值得再占用一次真实观察能力；由谁、在什么边界内、观察哪一层；拿到的部分材料以后能怎样使用。**

本合同冻结的是上述问题的**责任边界、不可压缩事实和可证伪门槛**。它不冻结数据库表、队列产品、前端、插件目录、调度算法、真实频率或阈值。

它不授权：

- 访问任何真实平台、账号、浏览器工位、内容、评论、私信、图片、视频或音频；
- 创建 Rust、SQL、API、Web、插件、AI Agent、对象存储、OCR、转录、队列或数据库 schema；
- 为真实账号、访问频率、对象上限、预算、风险阈值、恢复窗口、保留期限或样本挑选一个默认值；
- 因为某个 Attempt 结束、收到几个字节或页面显示空白，就断言平台不存在材料、目标已完成、媒体不存在或市场没有变化；
- 将一次 Canary 解释成可规模化采集、可比趋势、用户代表性、合规结论或市场机会。

本文与媒体生命周期合同的关系是：**本合同控制是否值得、是否获准、由哪个 lane 去做一次媒体访问；媒体合同控制候选、字节、Artifact、副本、派生和处置各自意味着什么。** 两者缺一不可，且都不是实际执行授权。

## 1. 从旧问题到新不变量

| 旧问题或高风险捷径 | 新不变量 | 直接后果 |
|---|---|---|
| 一个研究提示直接生成插件大任务 | **研究需要、授权、准入、工作单和实际执行分责。** | Agent 可以提出需要，不能自行扩大观察面或占用工位。 |
| 同一笔记被多个关键词、作者监控和研究反复深采 | **现实对象去重、发现路径保留、Evidence 复用与有意复观测分开。** | 一次详情结果可服务多个合格用途；多个 Discovery 不被丢失。 |
| 目标 100 条只拿到 50 条时，要么整批丢弃、要么显示完成 | **合格成员不因批次缺口连坐；Package 接纳、目标完成和 Claim 资格彼此独立。** | 50 条可保留；其余 50 条不得被写成不存在、失败或已覆盖。 |
| 把最大配额、页面结束和已知对象集合都叫“目标 100” | **目标必须保留语义和计数单位。** | 只有执行前冻结的已知集合，才可以逐成员说未尝试或失败。 |
| 搜索、详情、评论和媒体用一个“采集成功” | **每一个观察 lane 有自己的对象、Coverage、停止和复用边界。** | 搜索看到 50 张卡片不等于取得 50 篇详情；详情成功不等于评论或媒体成功。 |
| 插件自行决定下一步、延长租约或补采 | **服务端拥有准入、排序、工作单、租约、停止与回执解释。** | 插件只执行有界 Work Order，如实回报，不拥有采集策略。 |
| 网络重传、恢复运行和下一次复观测都被当成 retry | **replay、同 Attempt 恢复、新 Attempt 和有意复观测是不同事实。** | 重传不复制 Evidence；新镜头/新执行权不能伪装成旧 Attempt 延续。 |
| 风控中止意味着全部数据无效 | **风险中止限制后续访问，不追溯否定已合格观察。** | 已接纳 Record/Artifact 保留；Coverage 如实记录风险停止。 |
| URL 被当成“媒体已拿到、可读、可给模型” | **媒体候选、下载、字节验证、副本可读和派生处理各自有证据。** | 媒体 lane 不能跳过媒体生命周期合同。 |
| 数据库里有 0 条或 Task 结束，被解释为“没有” | **absence 需要观察资格、Coverage、终止与分析能力共同支持。** | Unknown 不得压缩为 0、完成或不存在。 |

## 2. 最小控制链：谁有权决定什么

下图是责任交接，不是要求立即实现的表或服务数量。

```text
Research Intent / Observation Objective
        ↓ 为什么持续看或主动研究
Evidence Need
        ↓ 还缺哪类材料、字段或观察
Acquisition Authorization
        ↓ 人批准可研究到什么边界
Admission
        ↓ 服务端判断是否值得一次真实访问
Work Order
        ↓ 给某个兼容工位的一张有界工作单
Attempt + Lease
        ↓ 一次受时间、身份和资源约束的执行权
Capture Package + ACK
        ↓ 插件交付与服务端如实接收的回执
Evidence / Artifact / Coverage facts
        ↓ 哪些原料被接纳、哪些仍受限制
Observation / later use
        ↓ 仅在各自资格满足时形成对象观察或支持 Claim
```

| 对象 | 它只回答什么 | 谁拥有/产生 | 它绝不能替代什么 |
|---|---|---|---|
| **Research Intent** | 为什么系统持续观察或要回答一个问题 | 人创建；系统可提出候选 | 不等于采集命令、对象身份或正式 Claim |
| **Evidence Need** | 当前缺少哪类可追溯材料，及允许多旧、需要什么 Coverage | 研究/产品逻辑提出；可由 Agent 建议 | 不等于“必须访问平台”，也不等于全局过期时间 |
| **Acquisition Authorization** | 人允许在何种目的、用途、数据和资源范围内研究 | Mog 或明确授权负责人 | 不等于插件凭据、Work Order、执行成功或材料使用许可 |
| **Admission** | 这次真实访问是否仍值得，且是否有兼容资源和风险余量 | 服务端控制层 | 不定义 Topic、市场结论或自动扩采规则 |
| **Work Order** | 一个 lane、对象集合/上限、时间与停止边界内具体做什么 | 服务端 | 不等于研究问题、长期计划或可无限追加的任务 |
| **Attempt** | 某工位在一次冻结执行身份下实际尝试了什么 | 服务端建立、插件执行 | 不等于 Package 接纳、Evidence、Observation 或目标已满足 |
| **Lease** | 当前谁可执行、执行权到何时有效 | 服务端授予并围栏 | 不等于账号权限、采集授权或已取得的材料失效 |
| **Capture Package** | 一次终态交付包含哪些可枚举成员、Artifact 引用和 Coverage | producer 交付、服务端验证 | 不等于整个平台、对象 Current、所有下游处理成功 |
| **ACK / Receipt** | 服务端对本次 Delivery 的 accepted / replay / conflict / rejected 结果 | Evidence ingress | 不等于 Work 完成、Record 处理或 Claim 有资格 |
| **Evidence / Artifact** | 系统在具体 producer、时间、观察条件下接纳了什么 | 接入与逐 Record/Artifact 合同 | 不证明材料真实、完整、代表性或适合任意判断 |
| **Observation** | 某外部 Source Object 在某时有何被支持的状态 | World/Observation 层 | 不等于 Topic、需求、趋势、意图或市场事实 |

### 2.1 Admission 必须先回答的最小问题

Admission 不是“优先级打分器”，更不是 AI 决定器。每次准备生成 Work Order 时，服务端至少要能解释：

1. **复用：** 已有合格 Evidence 或正在执行的 Work 是否已经满足 Need？
2. **差额：** 若不满足，缺的是发现、详情、评论、回复、媒体候选、下载、读取、派生还是一次有意复观测？
3. **时间：** 延迟是否会明显损失本次目的所需的信息；这不是把“发布 7 天”硬编码成宇宙事实。
4. **边界：** 是否仍在获批 Authorization、数据用途、lane 和对象范围内？
5. **资源与风险：** 是否有兼容工位、账号、版本、预算和风险余量；此前风险暂停是否仍在生效？
6. **可解释性：** 目标语义、Coverage 单位、停止条件和预计的回执边界是否可写入 Work Order？

只要其中任何一项不能如实回答，控制层应拒绝、等待、合并、降级为建议或标记 `DECISION_REQUIRED`；不得用“看起来相关”直接访问平台。

## 3. Coverage：先说明“100”是什么意思

Coverage 是后续解释的边界，不是对已接纳材料的惩罚，也不是一个全局完成百分比。

### 3.1 三类最小目标语义

| 目标语义 | 例子 | 取得 50 个合格结果时可以说什么 | 绝不能说什么 |
|---|---|---|---|
| **已知对象集合（known set）** | 执行前冻结的 100 个稳定 note ID | 对每一个成员可分别记录已尝试、已交付、失败、明确未尝试或仍 unknown | 未访问成员不存在；50 条代表平台全量 |
| **最大配额（maximum quota）** | 本次最多读取 100 篇详情或 30 条评论 | 本轮在明确停止条件下得到 50 条；最多目标尚未耗尽或已因条件停止 | “还有 50 个对象”；“完成 50%”或平台总量 50 |
| **来源终止/时间/风险/探针边界** | 滚动到 producer 实际终止、30 分钟、风险停止、能力探查 | 在精确入口/账号/时刻/终止事实下观察到什么 | 来源穷尽、搜索全量、评论全量或市场不存在 |

最大配额、时间预算和风险预算的差额不是现实对象。只有 known set 才允许列出具体尚未尝试成员；即便 known set 也必须保留其来源、冻结时点与身份解析质量。

### 3.2 Coverage 的最低来源事实

任何 lane 都至少要分开保存其实际可报告的：

```text
目标语义与单位
已知/发现成员（如果 producer 真的知道）
已尝试、已交付、逐成员接纳/隔离结果
已知失败、明确未尝试、仍未知
cursor / page / ranking / slot / reply-depth 等来源位置
开始、观察、停止与接纳时间
终止原因、风险事件与 producer/解析限制
```

不能把不同单位互减。例如 50 张搜索卡片、20 篇详情、80 条评论和 3 个媒体候选不是同一行 Coverage；每一个都需要独立的 lane 语境。

### 3.3 部分结果的使用规则

当一个 known set 的 100 个详情中只有 50 个通过最小来源合同时，正确表达是：

```text
50 个合格材料：可以接纳并在具体用途资格满足时使用
该 Attempt/Work：目标未完整满足，Coverage 有明确缺口
剩余成员：按已知失败、未尝试或 unknown 区分
Trend / market claim：仍需按此 Claim 的可比性与分母另行判断
```

这 50 个可以支持“本次实际捕获的材料中存在某种表达”、用于受限 Corpus 选择、探索结构或形成关于该对象的 Observation；它们不能自动支持“多数人如此”“平台只有这些”“正在增长”“需求很大”。

### 3.4 当前评论采集的完成与重采规则（ADR-0002）

小红书评论的执行回执采用直接、可核对的业务口径：页面明确显示 `N` 条评论，且同一 Attempt 取得 `N` 条唯一评论，即为当前全量评论范围 `COMPLETE`；页面明确为 `0` 且取得 `0` 同样完整。该判定不额外引入关于隐藏面、游标理论稳定性或来源表面等抽象门闸。

标准详情默认附带最多 30 条评论，是 `DETAIL_WINDOW`。窗口采满仅说明该窗口 `COMPLETE`，不表示笔记全量评论已完整。单篇深采的范围是 `ALL_PUBLIC_COMMENTS`；显示 `300`、实际 `200` 即为 `PARTIAL`，但这 `200` 条仍可接纳、检索并用于语料和定性分析，读取面应直接显示 `200 / 300` 与停止原因。

恢复时不得把此前 `200` 条推导为“从第 201 条继续”。每个新的评论 Attempt 必须重新进入指定笔记详情，从评论入口重新遍历当前集合；服务端保留 Attempt 历史，并用稳定 `(platform, content, commentId)` 形成当前去重投影。跨 Attempt 的计数不得相加来声称一次采集完整。

## 4. Lane 不能混用：发现、详情、评论与媒体

| Lane | 要回答的问题 | 常见可接纳材料 | 必须单独保留的 Coverage | 不能替代 |
|---|---|---|---|---|
| **Discovery** | 某入口在某时向这个观察身份展示了什么候选 | 搜索/作者页/关联页卡片、顺序、入口、过滤、可见字段 | query/filter、排名/页/滚动边界、实际可见数、解析失败、终止 | 详情正文、评论、平台总量、Topic 归属 |
| **Content detail** | 指定内容在此时实际呈现什么详情状态 | 标题、正文、作者引用、时间原始表示、指标快照、媒体候选 | 已知对象集合或配额、成功/失败/未尝试、实际 observed time | 评论已采、媒体已下载、长期作者档案 |
| **Comment / reply** | 指定讨论线程中实际取得了哪些一级评论或回复 | 评论/回复原料、关系、展示位置、时间原始表示 | 详情页与评论页边界、层级、分页、折叠、排序、已取/失败/未知 | 评论总数、所有回复、独立用户人数或需求强度 |
| **Media candidate** | 页面/响应当时暴露了哪些可能的媒体入口 | 主体、slot、来源位置、原始 ID/地址/类型提示 | 候选清单、slot、解析失败、未知位置 | 可下载、字节正确、已保存、可读或可转录 |
| **Media download / replica / derivative** | 受限媒体是否被获准取得、验证、保存或处理 | 下载发生、字节 Artifact、副本回执、派生回执 | 允许的媒体类型/对象/字节、每次下载、验证与停止原因 | 内容详情、评论或媒体候选 Coverage；也不自动证明可公开使用 |

一个完整的“研究任务”可以产生多个 lane 的 Work Order，但系统不得把它们塞给插件成为无限长的大任务。Discovery 先扩展候选面；详情、评论与媒体按 Need、准入、资源、时间和风险渐进生成有界工作单。

## 5. 复用、去重与有意复观测

### 5.1 不同层的“重复”不是同一件事

| 情况 | 应做什么 | 不应做什么 |
|---|---|---|
| 同一内容被多个关键词或作者路径发现 | 复用 Source Object（身份足够时），追加每条 Discovery | 删除发现路径，或反复详情采集 |
| 已有详情 Evidence 满足当前字段和时间要求 | 复用，并把新用途留为 Evidence applicability / use relation | 因新研究标题不同而再访问平台 |
| 正在执行的 Work 与新 Need 覆盖相同对象/lane/有效窗口 | 合并为共享 Need 或等待现有 receipt | 两个工位同时跑同一详情 |
| 当前 Need 要的是新评论、当前指标或变化 | 仅补所缺 lane/字段，并形成新的 Attempt | 把旧 Observation 覆盖成新状态 |
| 因生命周期、计划或验证需要再次观察同一对象 | 明确标为有意复观测，保留新观察条件与时间 | 把它当作无意义重复或更新旧 Package |
| 同 Capture Identity + 同 canonical hash 再次提交 | 作为 replay，返回原接纳结果并保留 Delivery 发生 | 再写一次 Evidence/Observation |
| 同 Capture Identity + 不同 canonical hash | conflict，冻结自动下游并调查 | 选择“最后一包”覆盖前一包 |

### 5.2 复用不是永久新鲜度

Evidence 没有全局 `expires_at`。是否足够新，取决于当前 Evidence Need：需要哪些字段、允许多旧、要不要时间变化、要不要某层 Coverage，以及它将支持哪一类 Claim。内容发布后 7 天的流量衰减可以成为未来**可版本化的调度假设**，但在真实实验前，不能被写成所有内容的一刀切重采/停止规则。

## 6. 有限资源、风险与过期重估

### 6.1 服务端必须拥有资源控制权

工位、账号、插件版本、网络、时间、字节、风险预算和人工注意力都是有限资源。插件只报告自己的兼容性、实际运行、风险事件和停止事实；它不能自行改变观察词、对象范围、频率、配额、媒体处理或下一步任务。

Admission 与 Work Order 需要能表达以下边界，而具体数值仍待真实 Canary 决定：

- 可兼容的工位/账号/producer 版本和观察身份；
- lane、目标语义、最大对象数/页数/回复深度/时长/字节或其他明确上限；
- 内容、评论与媒体各自的资源和风险预算；
- 截止时间、执行前重新评估以及不可再执行的原因；
- 风险暂停、立即停止、冷却、人工恢复与版本不兼容的处理入口；
- 已有 Evidence、进行中 Work 和已接纳 Package 的复用边界。

### 6.2 任务会贬值，执行前必须重估

Work Order 创建时合理，不代表排队两天后仍值得执行。领取 lease 前，服务端必须再次检查：Authorization 是否有效、Need 是否已被其他工作满足、对象是否仍处于本次目的的时间窗口、资源/风险是否仍可用、以及该 Work 是否已过期或需要降级。重估可以取消、等待或缩小**尚未执行**的工作；不能篡改已经发生的 Attempt、Package、Coverage 或 Evidence。

## 7. Attempt、Lease、Package 与恢复

### 7.1 执行权不是材料事实

一个 Work Order 可以有多次 Attempt；每次 Attempt 由服务端冻结 Capture Identity 与有限 lease。lease 只允许当前工位在有效期内进行规定访问，不能修改 Work 的 lane、目标、观察身份或止损边界。续租失败后必须停止新的平台访问，但已经取得且可验证的终态原料仍可依 ingress 合同提交。

一份 lease 可以按冻结顺序承载多个单能力 TaskSpec。例如创作者巡检先执行 `author_profile（作者资料）`，其回执接纳后才开放 `profile_discovery（作者作品发现）`。lease 与任务的多对一关系、顺序、领取安装和 `pending（待领取）/in_progress（执行中）/completed（已完成）` 必须由服务端持久记录；派发以原子 claim 独占任务，同一安装丢失 claim 响应后必须幂等取回同一 live task，不能领取第二份工作或一直卡到过期。插件只能用原样下发的 scheduled TaskSpec 创建 Attempt，不能在内容页重建一份 manual TaskSpec。Package 接纳时必须再次锁定并复核 live lease 与领取安装，Package、Receipt、task completion 以及必要的 lease completion 在同一事务提交。单个任务完成不结束整份 lease，只有序列全部形成已接纳回执才以 `completed` 收口；手动采集继续是独立的 manual TaskSpec，不借用 scheduled lease 身份。

若插件已经成功领取 scheduled Task、但尚未创建 Producer Attempt 时页面窗口、标签页或页面就绪读取失败，它不得把任务静默留在 `in_progress` 直到 lease 到期。插件只能以一个受控、无来源正文的失败码和幂等 `failureRef` 回报本机 dispatch failure；服务端在同一事务中锁定当前 live claim、追加一条不可变失败审计并把**同一冻结 TaskSpec**恢复为 `pending`。相同 `failureRef` 只重放既有结果；安装、任务、失败码或执行权不匹配则拒绝，绝不改写其他工位的 claim。这个恢复事实不是 Attempt、Package、Receipt 或 Evidence，不能伪造采集结果；一次分钟级退避后仍由服务端重新派发，正常 Package 接纳路径保持不变。

### 7.2 终态 Package 与部分成功

一个 Attempt 最多形成一个逻辑终态 Package：它包含不可变成员清单、Coverage 来源事实与 canonical hash。传输可分片；分片必须由一个冻结 manifest 统一指向，不能把 Attempt 变成持续追加的事实容器。

Package 接入硬门应只承担包级责任：授权、Attempt/Capture Identity、合同版本、canonical/hash、成员边界，以及每个成员最小 Record/Artifact envelope 是否可枚举和重放。平台字段质量、对象身份解析、评论关系和媒体主体等尽量在接纳后按 Record/Artifact 隔离处理。

因此可能同时成立：

```text
Attempt:     因风险停止，目标未完全满足
Package:     accepted（含 50 个可枚举成员与真实 Coverage）
Record:      45 个可继续处理，3 个重复关联，2 个隔离/可修复
Observation: 仅对满足对象/时间/来源条件的成员形成
Claim:       是否可用，仍按具体主张的资格判断
```

### 7.3 ACK、replay、conflict、retry、recovery 必须分开

| 情况 | 正确回执/动作 | 禁止的压缩 |
|---|---|---|
| 同一冻结 Package 网络重传 | `replay`，返回既有接纳结果 | 新 Package、新 Evidence 或新 Observation |
| 同 Identity 不同 hash | `conflict`，自动下游冻结、转调查 | later-write-wins 或自动选择最新 |
| 单 Record/Artifact 解析或主体错误 | 成员级隔离/待修复；其余成员可继续 | 整包连坐丢弃，或把错误成员当成功 |
| 同 lease、同执行身份、未终态的短暂停顿 | 经明确恢复判定继续当前 Attempt | 自行延长 lease 或无审计续跑 |
| lease 丢失、换账号/工位、镜头改变或终态已形成 | 创建新 Attempt / 新 Capture Identity，或受控 recovery-import | 把新观察挂回旧 Attempt |
| 已获准的补采 | 新 Need/Authorization/Admission 后新 Work/Attempt | 修改旧 Package、旧 Coverage 或旧 Observation |

## 8. 媒体 lane 的硬接缝

Mog 已选择方案 B：首批真实 Canary 同步纳入受限媒体。这并不让 Capture 控制层把一个裸 URL 视为已取得媒体。

控制层对媒体最小负责：

1. 把媒体候选、下载、存储、读取与派生视为独立 lane；
2. 对每一项媒体工作冻结主体、slot、预期来源断言/代次、允许类型、最大对象数/总字节/时长、风险停止与回执要求；
3. 让媒体下载使用同样的 Authorization → Admission → Work Order → Attempt → Package/ACK 链，而不从内容详情任务偷偷扩张；
4. 将媒体 lane 的 Coverage 与内容/评论 Coverage 分开；候选未下载、未尝试、下载失败、字节未验证、副本不可读和派生未运行必须保留区别；
5. 将媒体字节、Artifact、Storage Replica、OCR/转录等派生、访问限制和处置传播的语义交给独立的 `media-lifecycle-contract`（当前为 [Draft PR #15](https://github.com/Himog0921/linggan-intelligence/pull/15)）；控制层不能自行决定可读、保存、发送模型或删除策略。

任何媒体工作若缺少上述预期主体/slot、目的、边界或生命周期合同所需的用途与处置前提，必须停在 `DECISION_REQUIRED`，而不是退化为“先下载再说”。

## 9. 从 Evidence 到 Claim 的适用性边界

控制层的成功最多说明：在具体观察条件下，系统是否以受控方式取得、接纳和保留了哪些来源材料与 Coverage。它不自动提高材料对任何主张的资格。

| 后续用途 | 部分或完整 Capture 可能支持什么 | 仍必须额外检查什么 |
|---|---|---|
| 对象研究 / Observation | 某对象在该时确有这些被接纳字段或可追溯来源材料 | 身份、时间精度、来源关系、字段解析和冲突情况 |
| Corpus / 用户原声 | 在受限用途、隐私与访问许可下选择具体原话或片段 | 去重、片段血缘、脱敏、代表范围和对外可见性 |
| 探索 / Candidate | 在固定输入集合内发现相似表达、内容角度或异常 | 输入集合、模型/规则版本、来源集中度、反例和不确定性 |
| Claim / 市场解释 | 在特定范围内描述观察到的现象 | Coverage、可比性、分母、时间、观察镜头、分析版本与替代解释 |
| 趋势 / 需求 / 机会 / 行动 | 只有另有明确资格时，作为支持或反驳材料之一 | Gate 4–5 可比性实验、需求强度、供给、反例、决策权与行动后果 |

换言之：**Capture 成功不是市场理解成功；部分成功不是无价值；Evidence 存在不是 Claim 自动成立。**
