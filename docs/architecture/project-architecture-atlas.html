01

项目版图：新项目已是独立本地产品，不是旧工作台换一种语言

新系统使用全新的 Rust 与 PostgreSQL，旧工作台、旧插件和旧数据库仍只提供参考证据。变化在于：新项目自己已经拥有本地 Web 入口、证据库读取面、观察目标与浏览器采集运行时；它不再只是未来蓝图。

新旧隔离已确认
你可以这样理解：旧系统像一座已经住过的房子，新项目会量尺寸、查事故、保留好用的五金，但不会把旧房子的墙和管线原样搬进新地基。
展开：这一章的依据与边界
  • 项目 README：Rust、全新 PostgreSQL、旧系统只读参考。
  • ADR-0001：新旧数据库和运行时隔离是已接受决定。
  • 当前系统资产盘点：旧 V2 能证明什么、不能证明什么。
  • 技术架构基线：一个模块化单体、一个主库、API/worker、轻插件与受控 Agent 的长期主干。
  • 本章是导航图，不覆盖上述来源；真实实现变化时应重新核对代码、数据库和运行结果。
02

技术主干：先建一栋可靠的大楼，不提前拆成一座“服务城市”

系统采用一个 Rust 模块化单体：所有业务责任仍清楚分房间，但先在一个代码工程和一个 PostgreSQL 主库里协作。API 负责接待和组合，worker 负责可恢复的后台步骤；插件、模型和未来对象存储都只是受控外部执行端，不能反过来拥有系统真相。

展开：这套技术主干还包含哪些硬规则
  • 持久后台工作：worker 从 PostgreSQL 领取可恢复步骤；崩溃后可以接管，旧执行者不能迟到覆盖新结果。
  • 外部副作用：模型、通知、发布或对象存储使用“意图 + 尝试 + 回执”记录，数据库内完成不冒充外部系统已经成功。
  • 统一入口：Web、CLI、MCP 和 Agent Tool 复用同一产品合同与权限判断，全部禁止绕过模块直接查写数据库。
  • 渐进增强：对象存储、向量、专用搜索、Python 分析进程、微服务和消息平台都必须由真实样本与性能证据触发。
  • 完整权威说明见 技术架构基线；实现时仍须进入对应专题文档和当前 SCOPE。
03

开发协作 Agent：不是一群机器人自由改项目

Mog 负责范围、产品选择与最终验收；Agent 围绕同一个事项分工探索、实现和独立复核。所有结论都要回到代码、测试、数据库副作用或明确文档，Issue 和 Agent 输出都不是第二事实源。

协作规则已建立
用户不需要做的事

不替 Agent 排查技术细节

Agent 应把失败解释成“哪里出错、有什么影响、下一步是什么”，而不是把原始报错交给你判断。

Agent 不可越过的线

Issue 不是授权书

标签、计划或 Agent 建议都不能自动授权真实账号、敏感原文、生产数据库、外部发布或删除。

完成的真实含义

代码、推送、部署、业务验收分开

哪一层真的完成，就报告到哪一层；不能用“文件写完”代替系统已经可用。

展开：开发协作 Agent 与产品内 AI Agent 的区别
  • 本章的 Agent 是帮助 Mog 建设项目的 Codex/工程协作角色，规则来自 Agent 协作协议、Issue 追踪规则 与 领域文档读取规则。
  • 第 07 章的 Agent 是未来产品内部的研究能力；它目前只有设计，没有业务实现。
  • SCOPE-001 还有一份更严格的 Agent 执行合同，用于禁止状态压缩、吞掉 unknown 或夸大证明范围。
04

产品核心模块：按责任分房间，不按页面堆功能

整个产品逻辑上由十个责任模块组成。它们不是十套互相独立的系统；第一阶段仍是一个 Rust 模块化单体和一个 PostgreSQL 主库。图中采集控制、世界观察的局部读取，以及读取模型已经有实际实现；知识、分析、情报、产品内 Agent 和决定学习仍主要是责任地图。

逻辑责任已确认
最重要的设计原则：页面不是事实源，AI 也不是事实源。页面、命令行和 Agent 都只能通过“读取模型”看见已有事实与限制；所有真实写入都必须回到拥有这项责任的模块。
展开：为什么图上模块名不等于代码目录
  • 模块架构明确说明：这是逻辑责任，不要求立刻创建同名 crate、表或服务。
  • 当前代码已不再只是 Bootstrap：Evidence 目录中已有本地 discovery、Producer Runtime、观察目标、授权/准入、工单、租约、工位、巡检与读取模块。它们说明局部责任已经实现，但仍不能直接当成完整长期模块地图。
  • 首个切片只实现真实需要的部分，避免先创建十个空模块和一堆没有调用者的接口。
05

数据生命线：从外部痕迹到可行动判断

系统不把“抓到页面”直接变成市场结论。材料必须经过有目的的采集、证据接纳、来源观察、可追溯读取、固定输入分析，最后才可能形成主张和行动；当前只在“合成采集包合同和接入数据库基础”处开始落第一块砖。

全链责任已确认
为什么这条链很长：它不是为了增加流程，而是为了让你以后能问清楚：“这句话到底来自平台、来自系统计算、来自 AI 推断，还是来自人的决定？”
展开：重要中文术语
  • 采集包（Capture Package）：插件一次执行后冻结的交付物，包含取得的记录、覆盖情况和停止原因。
  • 证据（Evidence）：系统有资格声明“我接收到了这些来源材料”，不代表材料一定完整或真实。
  • 观察（Observation）：基于合格来源材料，对某个来源对象在某个时间的表达。
  • 当前读取（Current Resolution）：按明确规则从历史观察中选择当前可展示值；它可以重建，也允许未知。
  • 主张（Claim）：值得被支持、质疑、修订并可能进入决定的重要判断。
06

事实分层：越往上越接近判断，越不能冒充底层事实

同一份材料在不同层只能承担不同强度的话。系统把“收到什么、观察到什么、现在怎样、可能意味着什么、为什么值得行动”分开保存，防止 AI 或页面把解释写回成历史事实。

领域不变量已确认
例子 A

50 条合格材料已经入库

只能证明这 50 条材料在当前合同下可保留；不能自动证明市场观察完成了 50%，更不能证明剩余对象不存在。

例子 B

AI 总结得很流畅

只要新增了输入里没有直接支持的事实性句子，就必须成为候选主张或无资格草稿，不能写回观察层。

例子 C

用户批准一个行动

批准只让下一责任可以尝试执行；实际有没有发布、有没有结果，仍要由外部证据和结果观察证明。

展开：权威规则来自哪里
  • 领域不变量：证据先行、主张受限、unknown 保留、结果不改写过去。
  • 数据架构：Evidence、Observation、Current、Analysis、Claim、Decision、Outcome 分责。
  • SCOPE-001 Agent 执行合同：低层不能越权产生高层结论，验证范围必须跟随成功声明。
07

采集子系统：从“加入观察”到“受控任务”，主控制链已落地

现在用户可以先把创作者或关键词加入观察名单；这一步只写本机身份，不访问平台。后续采集仍必须经过授权、准入、工单、限时租约和工位匹配。插件不能自己铸造派发任务，只能领取服务端许可的工作，并把结果以可追溯采集包交回本机。

控制链已编码 · 浏览器实采待持续证明
服务端拥有

研究意义与资源分配权

判断能否复用、是否值得新访问、使用哪个工位/账号、任务边界与风险预算。

插件拥有

当前工作单的执行事实

打开真实页面、读取来源、记录风险与停止、冻结并重传同一个采集包。

插件明确不拥有

研究、事实与扩采决定

不能新增目标、把缺失补成 0、把任务结束叫完整观察，或绕开服务端继续采。

展开：当前究竟哪些已经存在
  • Linggan 自有插件已经有工位报到、领任务、定时唤醒、受控窗口与本地提交路径；它不是旧工作台的运行时依赖。
  • 观察目标、授权、准入、工单、租约、风险暂停、日配额和派发均已有当前代码与 migration。调度决策不直接下载、转录或访问平台。
  • 本图仍不把“插件代码能领任务”误画成“真实浏览器采集与回传已经稳定完成”。媒体、OCR/ASR 与多 lane 接纳要各自给出真实证据。
08

产品内 AI Agent：未来是受控研究助手，不是系统超级管理员

一次产品内 Agent 运行必须有调用者、目的、材料边界、工具权限、预算、停止条件和结构化结果。Linggan 自己掌握这些权力；Pi 或其他模型只能作为可替换的“有限研究循环执行器”。Agent 可以读取合格材料、找反例和提出候选，但不能直接改数据库、指挥插件、发布正式知识或执行现实行动。

只有设计 · 尚未实现
这套限制不是为了让 AI 变笨：它让 AI 可以大胆提出假设，同时让系统清楚标记“这只是候选”“依据是什么”“还缺什么”，从而避免流畅表达被误当成事实。
展开：第一阶段产品内 Agent 最多能做什么
  • 按 Agent 架构草案，第一版只考虑 A1–A2：受控读取和候选分析。
  • Pi 当前只是 条件性 Adapter 候选，不是事实内核、权限中心、持久任务主账或正式知识库；当前也没有安装进产品运行时。
  • 它可以基于固定、脱敏材料包生成有引用的候选结构、反例和信息缺口。
  • 采集申请、知识发布和行动申请要等相应模块成熟后再开放；任何正式知识和现实动作始终需要人的决定与原模块执行。
  • 模型供应商、真实样本处理条件、成本和质量 benchmark 目前都未决定。

11

事实基础：F01 仍是可信接纳地基，但不再是项目唯一实现切片

F01/SCOPE-001 负责把“材料为什么可被接纳、能否重放、何时冲突、坏记录如何隔离”这些底层规则证明清楚。它仍是系统的可信地基；但当前项目已在其旁形成独立的 LOCAL / Producer / Collection 产品链。图中两条链必须分开理解：产品可见不等于 F01 全部完成，F01 通过也不等于真实采集、媒体或智能分析完成。

F01 持续作为事实接纳基础
为什么先做这么窄：这条切片专门验证最容易被“看起来成功”掩盖的底层规则——部分结果能否保存、unknown 会不会被吞掉、坏记录会不会拖死整包、每个当前值能否追到来源、并发旧执行者能否被数据库拒绝。
展开：受控开发仍必须守住的五个条件
  • G1 语义唯一：每个测试场景的每一层状态和数据库副作用只有一个正确答案。
  • G2 禁止推断：未列能力有停止规则，Agent 不需要自己补全。
  • G3 负向约束：不仅写“应该出现什么”，也写“绝不能出现什么”。
  • G4 证据边界：每个读取值和业务结果能回到对应 Package、Record、Observation 或规则。
  • G5 证明边界：每次报告同时列出 VERIFIED 与 NOT VERIFIED。
  • 权威范围见 SCOPE-001 活跃计划；执行纪律见 Agent 执行合同。
